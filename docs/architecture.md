# 项目技术基线

状态：2026-09-15 技术基线；第三步工程骨架已落地，验收记录见 [工程验收报告](engineering-verification.md)。

## 1. 目标与当前范围

由用户主导、AI 辅助开发知产案件管理系统。Demo 仍在部门审核，先固定工程选择和模块边界，降低业务调整时的返工。

已知扩展方向：通过大模型 API 识别字段并回填表单；暂按向业财系统单向推送费用、结算数据设计，方向和协议需向业财负责人确认。

前两步已完成规则、文档和版本对齐。第三步已按用户授权建立正式工程骨架、安装依赖并创建独立本地开发与测试数据库。Demo 继续独立维护；业务模块、表和外部对接按确认需求增加。

## 2. 固定技术选择

| 范围         | 基线                                | 使用边界                                       |
| ------------ | ----------------------------------- | ---------------------------------------------- |
| 架构         | 前后端分离、模块化单体              | 单个业务后端，内部按职责划分模块               |
| 仓库与包管理 | 单仓库、pnpm workspace              | 前后端独立包，根目录统一入口和锁文件           |
| 前端         | Vue 3、TypeScript、Vite             | Composition API、`<script setup lang="ts">`    |
| 页面路由     | Vue Router                          | 路由归应用层管理                               |
| 状态管理     | Pinia                               | 跨页面共享状态；临时表单状态留在组件或业务模块 |
| UI 与样式    | Element Plus、CSS 变量、scoped CSS  | 复用 Demo 设计变量；新增视觉约定集中管理       |
| 浏览器 HTTP  | 原生 fetch 的统一封装               | 集中处理基础地址、错误、取消和超时             |
| 后端         | NestJS、TypeScript、Express 适配器  | Controller 接入、Service 业务、模块封装        |
| 数据库       | PostgreSQL                          | 业务持久化；公司指定环境冲突时先修订基线       |
| 数据库工具   | Prisma、Prisma Migrate              | 单一数据访问工具与迁移体系                     |
| 接口         | REST JSON、OpenAPI                  | `/api/v1` 前缀，后端契约为准                   |
| 后端输入校验 | class-validator、class-transformer  | 对外输入运行时校验                             |
| 精确小数计算 | decimal.js                          | 金额等精确小数计算；持久化使用数据库 Decimal   |
| 代码检查     | TypeScript strict、ESLint、Prettier | 建立时落实为配置和可执行命令                   |
| 前端测试     | Vitest、Vue Test Utils              | 逻辑和组件行为                                 |
| 后端测试     | Jest、Supertest                     | 业务逻辑和 HTTP 行为                           |
| 跨端流程测试 | Playwright                          | 已实现的关键用户流程                           |

### 版本和配置的后续落实

第二步的环境检查和版本选择已记录在 [环境报告](environment.md)，准确版本选择以 [版本清单](environment-lock.json) 为准；实际安装由根 `pnpm-lock.yaml` 固定。第三步已实测依赖安装、构建及数据库连接，后续增加依赖仍按清单与变更规则处理，不重新按 latest 选型。

Node.js 与 pnpm 通过项目配置锁定，直接依赖使用准确版本，提交单一 `pnpm-lock.yaml`；数据库镜像如使用容器也固定版本。自动化安装使用冻结锁文件模式，依赖升级单独交付。

前端使用 Vite 的 ESM 模块体系；后端基线使用 NestJS CommonJS 编译方式，Prisma Client 输出与其保持一致。搭建时验证编译及启动，不把两套环境的模块配置相互复制。

## 3. 模块职责和依赖方向

- 前端应用层组织路由和布局；业务模块组织页面与表单；接口层负责 HTTP，组件通过接口层访问后端。
- 后端 Controller 负责协议与输入接入，Service 负责业务规则。数据库访问由数据所属模块管理，跨模块通过该模块公开服务调用。
- `database` 提供连接与数据库基础设施，不集中承载所有业务查询；`common` 仅放已存在复用需求的通用技术能力。
- `ai` 负责识别能力与模型接入。业务模块提交明确的识别任务，AI 模块返回候选字段，业务模块负责字段映射、权限和保存。
- `integrations` 内按外部系统划分对接模块，负责协议适配、字段转换和交互结果。业财对接通过业务模块公开的能力取得数据，不绕过业务规则修改其他模块的数据。
- 较长的 AI 识别和批量推送需按可查询状态的后台任务设计。具体任务落地前确定持久化、超时、重试与恢复方案；本阶段不引入队列或常驻工作进程。
- 暂不引入微服务、Redis、消息队列、向量数据库或 AI 编排框架；需求出现后按变更规则评估。

## 4. 目录规划（到模块层）

```text
dev_cor/
├─ AGENTS.md
├─ demo/                       现有审核原型
├─ frontend/
│  └─ src/
│     ├─ app/                  初始化、路由、布局
│     ├─ modules/              按确认需求加入业务模块
│     ├─ components/           公共组件
│     ├─ api/                  HTTP 封装与接口调用
│     ├─ stores/               跨页面状态
│     └─ styles/               设计变量与全局样式
├─ backend/
│  ├─ src/
│  │  ├─ modules/              业务模块
│  │  ├─ ai/                   AI 识别和供应商接入
│  │  ├─ integrations/         外部系统对接
│  │  ├─ database/             连接与数据库基础设施
│  │  └─ common/               通用技术能力
│  └─ prisma/                 数据模型和迁移
├─ tests/
│  └─ e2e/                    跨端流程测试
├─ docs/
│  ├─ architecture.md         技术与边界的唯一基线
│  └─ conventions.md          代码与交付规范
└─ deploy/                    部署确定后加入配置
```

叶级目录表示职责，不要求立即创建空目录。具体业务模块、文件和内部层次在需求确认后按需添加；就近放置单元和组件测试，根目录 `tests/e2e` 放跨端测试。

## 5. 待确认事项与实施边界

| 待确认         | 确认内容                                           | 确认前可做 / 暂不做                                 |
| -------------- | -------------------------------------------------- | --------------------------------------------------- |
| 身份认证       | 独立账号或公司统一登录、会话机制                   | 文档和接入边界 / 不自行实现登录方案                 |
| 权限与数据归属 | 用户类型、部门范围、客户可见性、组织或租户边界     | 模块边界 / 不固化角色、数据权限和组织表             |
| 部署环境       | 服务器系统、内外网、域名、容器及运维要求           | 本地工具检查 / 不发布或选定生产拓扑                 |
| 附件存储       | 存储服务、类型、大小、访问授权、保留要求           | 文件能力边界 / 不选定生产存储供应商                 |
| AI 接入        | 供应商、模型、输入材料、可发送数据范围、超时和预算 | 接入边界与表单草稿规则 / 不接真实模型或上传业务材料 |
| 业财对接       | 单向推送是否准确、API 或导入方式、认证、防重复能力 | 对接边界 / 不虚构协议、推送条件或记账字段           |
| 业务审核       | 字段、流程、校验、费用口径及报表                   | 工程底座 / 不将 Demo 配置直接定为生产规则           |

待确认事项只限制对应能力，不阻塞无依赖的已授权任务。采用可替换边界，不为未知需求预先设计万能协议。

各待设计项的输入、触发条件、产物和验收状态统一维护在 [后续设计清单](deferred-design.md)。收到字段/规则文档后必须逐项核对，外部条件不能由 Demo 推断补齐。

## 6. 基线变更

新增普通依赖前检查当前工具是否足够，并在交付说明记录理由。替换上述选择、增加同类工具、拆独立服务或改变模块依赖方向，先给出问题、替代方案、影响及迁移方式，由用户决定；明确授权过的变更不重复询问。

变更批准后同步修改本文件、受影响的规范和实际配置。业务需求变化只影响业务说明时，不重复改写技术基线。
