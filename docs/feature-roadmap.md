# 功能开发路线图

更新日期：2026-09-20。业务实现审计基线：`e6caef4`；流程工具的后续变更不改变本表业务完成判定。

本文只回答“已经做到哪里、下一步做什么、之后按什么依赖顺序做”。详细业务规则仍以 [`docs/spec/`](spec/) 为准，技术方案以设计文档为准，当前切片的技术任务以实施计划为准，实际验证结果以 [`docs/project-status.md`](project-status.md) 和 [`docs/spec/v0.1/VALIDATION.md`](spec/v0.1/VALIDATION.md) 为准。

## 状态判定

- `✅ 已完成`：前端、API、后端业务逻辑、PostgreSQL、服务端权限和关键自动化测试均已形成闭环，并有真实浏览器／数据库验证证据。
- `🟡 部分完成`：已有可运行子能力，但该行所述完整业务闭环仍缺 UI、API、规则、权限或关键测试。
- `🔵 已设计待开发`：已有获确认的业务方向或设计，但没有完整正式实现。
- `⚪ 未开始`：仅有范围方向，尚未形成足以编码的切片设计。
- `🔴 阻塞`：已有方向，但外部条件或关键业务决定使该闭环目前不能完成。

“已完成”只针对表中明确写出的切片边界，不把较小切片的完成扩大为整个模块完成。例如“一位准入联系人”已完成，不代表“联系人管理”已经完成；“客户域最小授权”已运行，不代表“人员与权限管理”已经完成。

## 当前开发状态

系统已经具备可运行的运营端最小主数据链路：管理员开通第二位人员并分配已有角色 → 新人员登录与会话恢复 → 按部门／TEAM／SELF 权限读取客户 → 新建、查看和编辑客户草稿 → 维护一位准入联系人 → 新建或关联权利主体 → 刷新后从 PostgreSQL 读取持久化结果。关键链路已有浏览器、API、数据库约束、越权、并发、事务回滚和迁移测试。

尚未进入正式实现的主要业务域包括线索、公证、案件、材料、费用、结算、日历和报表。客户模块也尚不包含正式准入、多联系人、合作状态、负责人转派、权利资产和协议闭环。

### Current Slice

**ROLE-TEMPLATE-001｜角色模板复制与 Grant 配置闭环。** 任务已正式领取，方案 A、设计文档和实施计划均已固化，进入测试先行实施。切片新增独立`ROLE_MANAGE`，允许有权管理员在当前部门复制已有模板、配置代码中已存在的 Action 与范围、自动预览受影响人员并编辑现有模板；不引入自定义策略、审批流或跨部门全局角色。

### Next Slice

**多联系人及客户关系维护。**

角色模板闭环完成后，按路线图第08项把现有一位嵌入式准入联系人扩展为独立的多联系人关系，支持新增、修改、设为主要联系人、结束关系和历史留存；联系人不会自动成为登录账号，主体关系的扩展范围仍需在该切片设计时确认。

## 影响开发顺序的架构与数据模型问题

- Team前置已收口：`DepartmentMembership`、`RoleAssignment`和`Customer`的非空`teamId`现在通过组合外键引用同部门Team；停用保留历史且禁止新增／恢复绑定。当前Slice无需再以裸UUID或人工改库表达团队。
- 管理授权前置已收口：服务端已有人员／Team／角色六项Action和逐Grant授予上限；首位管理员身份、角色名称及前端菜单均不构成授权。当前Slice新增独立`ROLE_MANAGE`并完成角色模板Grant编辑。
- `CustomerProfileStatus` 目前只有 `DRAFT`。正式准入需要前向迁移、准入 Command 和历史状态审计，因此必须排在文件能力与准入规则之后，不能通过直接改字段提前完成。
- 权限范围内核目前只在客户／权利主体域有运行证据；未来每个线索、案件、文件、费用、报表 Slice 都要增加自己的动作与数据库范围测试，不能把客户域通过泛化为全系统通过。

前两项不再阻塞Current Slice；第三项是每个未来业务Slice各自必须满足的持续约束。

- 当前没有文件、线索、公证、案件、费用或结算表。后续应按本路线图逐 Slice 建模和迁移，不能先建一套大而全的空数据库模型。

上述问题不阻碍当前 Slice；前两项已经收口，并作为其实施阶段必须继续遵守的数据和授权契约。

- **权限管理**：人员、Team和已有角色分配已形成闭环，但角色模板复制与Grant编辑尚未实现。
- **客户管理**：草稿链路已闭环，但正式准入、搜索／状态筛选、合作状态、负责人转派和完整联系人仍未完成。
- **联系人管理**：仅有 Customer 聚合内的一位准入联系人，不是多联系人模块。
- **权利主体管理**：仅支持新建、查看和关联；编辑、删除、解除关联和默认主体均未实现。
- **材料／文件**：规则与技术缝隙已经设计，但没有对象存储适配、材料表、上传 API 或正式页面。
- **案件、线索、公证、费用、结算、日历和报表**：Demo 与 Spec 很丰富，但正式运行时代码和数据库模型均不存在，应视为已设计或未开始，而不是部分 CRUD。
- **四端与外部集成**：只有边界决定，没有独立入口、身份映射或集成协议实现。

## 维护规则

1. 开始业务 Slice 时，在顶部只设置一个 `Current Slice`；完成或暂停后同步状态、证据和唯一 `Next Slice`。
2. 只有 UI、API、后端、数据库、权限和关键测试全链路齐备，并在测试／验收环境由真实 UI 完成业务链路后，才改为 `✅`。
3. 代码完成但缺数据库 E2E、权限负向或部署验收时保持 `🟡`；只有设计时保持 `🔵`；局部外部依赖只把对应行标为 `🔴`。
4. 路线图不复制 Spec 字段和状态机。业务范围变化先更新 Spec／Decision，再调整本表顺序和完成标准。
5. 每次状态变化必须链接实现、迁移、测试或验证记录；不能用 Demo、Mock、页面截图或文档自述作为完成证据。
6. 新增未来能力前先确认它来自现有 Spec、Decision 或用户批准；不得为了填满路线图扩大产品范围。
