# AI 开发与上下文恢复规范

## 目标与事实来源

通过唯一状态入口、按变更更新文档和文件漂移检查，让换会话、上下文压缩或中断后的 AI 能核对进度。自动检查证明文件版本一致，无法证明文字语义正确，也不会自动证明测试通过。

| 信息                                       | 唯一负责来源                                                                     | 更新时机                                 |
| ------------------------------------------ | -------------------------------------------------------------------------------- | ---------------------------------------- |
| 当前阶段、在做什么、剩余工作、最近验证依据 | [project-status.md](project-status.md)                                           | 开工、有效检查点、交付或暂停前           |
| 技术选择、模块边界、待决架构               | [architecture.md](architecture.md)                                               | 选型或边界改变时                         |
| 开发和接口规范                             | [conventions.md](conventions.md)                                                 | 约定改变时                               |
| 运行环境与选定版本                         | [environment.md](environment.md)、[environment-lock.json](environment-lock.json) | 环境/选型改变时                          |
| 实际依赖、脚本、schema                     | package.json、pnpm-lock.yaml、源码与配置                                         | 实现变化时；其他文档引用，不复制完整清单 |
| 实测结果                                   | 带日期、范围和版本的验收报告                                                     | 有新验证证据时；保留历史适用范围         |
| 已核对文件的版本                           | context-snapshot.json                                                            | 文档与实现核对后显式记录                 |
| 临时进程、容器是否运行                     | 当次命令输出                                                                     | 使用前现场检查，不能沿用旧报告           |

用户确认的需求决定“应该做什么”，源码和实际验证说明“已经做成什么”。二者不一致时记录差异并修复，不能用实现反过来宣布需求已批准。聊天中的新增业务决定先写入对应需求文档，再实现。

## 每次开始或恢复上下文

1. 读取根 AGENTS.md、project-status.md 和本规范；再按任务读取基线、开发规范及相关源码。
2. 在同一 PowerShell 中加载项目运行入口，核对版本，执行 `pnpm context:check`。
3. 检查失败时，按列出的新增/修改/删除文件恢复中断现场。保留用户修改，核对真实实现及相关验证；不得直接刷新快照消除错误。
4. 状态文档写明当前任务的目标、允许范围、已完成工作、剩余步骤和阻断项。不存在的授权、未运行的检查写“未确认/未运行”。
5. 如果无活动任务，依照用户新指令工作；不能因为第三步完成就自行启动下一阶段业务开发。

## 工作中的检查点

- 一个可独立核对的阶段完成后更新当前任务；预计长时间下载/测试前记录正在等待的操作及恢复方式。
- 暂停或被用户要求切换任务时，记录最后成功动作、失败证据、尚未执行的步骤；保持任务为“进行中/待验证/阻断”，不能写成已完成。
- 突发中断可能发生在写文档之前。新会话必须依靠旧快照与当前文件差异识别现场，不能假定中断前已同步。
- 状态记录只保留影响恢复的事实和下一步，详细历史放在对应计划或带日期的报告中。密码、令牌、数据库连接串和业务材料不进入状态文件或快照。

## 同一次交付的同步门槛

1. 核对原需求、改动文件和行为；执行与风险相关的检查。
2. 同步受影响的需求、架构、规范、环境或运行说明。更新 project-status.md 中的结果、已知限制及证据；历史报告仍保持其原始验证范围，不冒充最新结果。
3. 先格式化文件，再执行 `pnpm context:record`。有受跟踪文件变化但状态文档内容未更新时，记录命令会拒绝；它不会修改状态或生成“测试通过”的结论。
4. 执行 `pnpm verify`。这会检查上下文快照、类型、Lint、格式、测试和构建；涉及跨端行为时另按 README 启动测试库并执行 `pnpm test:e2e`。
5. 如果检查失败，记录失败与修复；完成修复后重新执行相关检查。最后更新实际结果、重新记录快照，再运行 `pnpm context:check` 和 `pnpm format:check`。只有文档变更时可复用同一代码版本的检查证据，说明复用范围。
6. 最终交付必须说明改动、真实验证、剩余事项。源码状态为未验证时仍可保存检查点，但不能宣称交付完成。

文档属于交付的一部分。未来接入 Git/CI 后，将代码、文档和快照纳入同一提交与必需检查；当前尚无远程 CI，不能声称服务器会强制执行。

## Demo 反向整理与正式业务开发

1. 用户提供或指定待分析的 Demo 版本后，先提取页面、实体、字段、状态流转、角色与权限、校验、金额口径和对接点。
2. 将“Demo 中观察到的行为”“用户/部门已确认需求”“推断及未决问题”分开标记。Demo 是需求证据，不是数据库设计或权限规则的直接授权。
3. 形成需求到页面、接口、业务模块、数据模型和验收用例的映射。到这一步再按已确认需求创建业务模块和迁移。
4. 业务页面使用现有 app/router、api 和模块边界；健康页为工程入口，可移到独立路由。通用层不嵌入案号、诉讼阶段、费用种类或角色规则。
5. 若审核需求与基线产生真实冲突，记录影响和替代方案，只暂停依赖决定的部分；不能同时建立第二套前后端、ORM 或业务状态体系来回避决定。

## 检查能力的边界

`context:check` 比较项目中受跟踪文本文件及 Demo 文本资产的新增、修改和删除，并核对当前文档采用的无标题行内相对文件链接。链接检查不支持引用式链接、带标题链接或复杂 Markdown 语法，也不验证锚点；文档采用简单行内链接，复杂链接另行人工核对。排除依赖、构建/生成结果、运行报告、秘密环境文件和本地临时目录。它不解析自然语言是否诚实、不测试业务、不监控后台进程。

快照是“已人工核对这批文件”的标记，不是语义保证。仅改日期、删除文件清单、放宽排除范围或刷新快照来掩盖差异，均不满足同步要求。新增文件类型或生成目录时同步审查检查脚本的跟踪范围。
