# AI 开发与上下文恢复规范

## 目标与事实来源

通过唯一状态入口、按变更更新文档和文件漂移检查，让换会话、上下文压缩或中断后的 AI 能核对进度。自动检查证明文件版本一致，无法证明文字语义正确，也不会自动证明测试通过。

| 信息                                       | 唯一负责来源                                                                     | 更新时机                                 |
| ------------------------------------------ | -------------------------------------------------------------------------------- | ---------------------------------------- |
| 当前阶段、在做什么、剩余工作、最近验证依据 | [project-status.md](project-status.md)                                           | 开工、收口、暂停或阻断前                 |
| 技术选择、模块边界、待决架构               | [architecture.md](architecture.md)                                               | 选型或边界改变时                         |
| 开发和接口规范                             | [conventions.md](conventions.md)                                                 | 约定改变时                               |
| 运行环境与选定版本                         | [environment.md](environment.md)、[environment-lock.json](environment-lock.json) | 环境/选型改变时                          |
| 实际依赖、脚本、schema                     | package.json、pnpm-lock.yaml、源码与配置                                         | 实现变化时；其他文档引用，不复制完整清单 |
| 实测结果                                   | 带日期、范围和版本的验收报告                                                     | 有新验证证据时；保留历史适用范围         |
| 已核对文件的版本                           | context-snapshot.json                                                            | 文档与实现核对后显式记录                 |
| 临时进程、容器是否运行                     | 当次命令输出                                                                     | 使用前现场检查，不能沿用旧报告           |

用户确认的需求决定“应该做什么”，源码和实际验证说明“已经做成什么”。二者不一致时记录差异并修复，不能用实现反过来宣布需求已批准。聊天中的新增业务决定先写入对应需求文档，再实现。

阶段切换必须登记用户确认依据、批准的需求版本和本次实施范围，再同步开发状态；仅接收字段/规则文档、通过检查或修改状态文字不能构成切换依据。阶段与用户授权冲突时先核对来源，仅暂停有冲突的部分，继续不依赖该决定的已授权工作。

## 最短有效执行链

- 每项任务的风险分级、候选证据、重跑条件、数据库验证、独立审查和自动集成只在[风险分级与已验证集成规则](../.cursor/rules/verified-feature-integration.mdc)完整定义；本规范负责上下文恢复和文档交付，不复制门禁正文。
- 用户明确说“按这个范围执行”“按建议修改”等，视为对应范围的执行授权：直接完成修改、相关验证、留痕和交付，不再把同一范围改写成新的方案审批。只有出现新的业务选择、明显扩大范围、生产操作、权限扩张或未获批准的不可逆风险时，才暂停受影响部分。
- 每轮采用“读取必要上下文→检查本轮Spec→执行→按风险验证→最少留痕交付”。简单明确任务不机械叠加头脑风暴、设计审批和计划审批；跨模块或高风险变更才扩大审查。
- 同一事实只在一个权威位置完整定义：Spec负责业务规则，实施计划负责范围与验收，项目状态负责当前进度，验证记录负责实测证据，Git负责版本差异。其他位置引用，不复制整套规则。
- 阻断必须区分业务规则、接口契约和真实环境参数，只暂停实际依赖该条件的工作。测试Adapter可验证内部契约，但不能冒充真实登录、对象存储或外部联调已经通过。
- AI留痕复用实施计划、项目状态、验证记录和Git；最少记录任务／范围、依据、改动、验证、未决项和版本。没有审计价值时不另建操作流水、重复台账或第二套进度表。

## 每次开始或恢复上下文

1. 读取根 AGENTS.md、project-status.md 和本规范；再按任务读取基线、开发规范及相关源码。
   修改前执行 git status 并检查已有 diff，区分本次范围与他人改动；无 Git 时明确记录这一限制并保护现有文件。
2. 在同一 PowerShell 中加载项目运行入口，核对版本，执行 `pnpm context:check`。
3. 检查失败时，按列出的新增/修改/删除文件恢复中断现场。保留用户修改，核对真实实现及相关验证；不得直接刷新快照消除错误。
4. 状态文档写明目标、允许／排除范围、风险等级与依据、必须检查、拟省略检查及理由。不存在的授权、未运行的检查写“未确认/未运行”。
5. 如果无活动任务，依照用户新指令工作；不能因为第三步完成就自行启动下一阶段业务开发。

## 工作中的检查点

- 状态文档原则上只做开工与收口两批更新；中间失败、修复尝试和命令输出进入现有任务执行记录。预计长时间下载／测试或必须暂停时，记录正在等待的操作及恢复方式。
- 暂停或被用户要求切换任务时，记录最后成功动作、失败证据、尚未执行的步骤；保持任务为“进行中/待验证/阻断”，不能写成已完成。
- 突发中断可能发生在写文档之前。新会话必须依靠旧快照与当前文件差异识别现场，不能假定中断前已同步。
- 状态记录只保留影响恢复的事实和下一步，详细历史放在对应计划或带日期的报告中。密码、令牌、数据库连接串和业务材料不进入状态文件或快照。

## 同一次交付的同步门槛

1. 核对原需求、改动文件和行为；按[风险分级与已验证集成规则](../.cursor/rules/verified-feature-integration.mdc)固定候选、执行门禁并记录证据复用或重跑原因。
2. 同步受影响的需求、架构、规范、环境或运行说明。更新 project-status.md 中的结果、已知限制及证据；历史报告仍保持其原始验证范围，不冒充最新结果。
3. 先格式化文件，再执行 `pnpm context:record`。有受跟踪文件变化但状态文档内容未更新时，记录命令会拒绝；它不会修改状态或生成“测试通过”的结论。
4. `pnpm verify`覆盖上下文、Spec、类型、Lint、格式、工具／前后端测试和构建，但不含数据库E2E；是否执行及E2E范围由任务风险决定。同一候选的可信通过证据不因阶段名称变化而重复运行。
5. 检查失败时保留首次失败和处置。修改使相关输入变化后形成新候选，只重跑失效证据覆盖的聚焦与完整门禁；不能把旧候选结果登记给新候选。
6. 收口时一次回填真实结果、范围、审查和剩余项；格式化后记录快照，执行`pnpm context:check`、`pnpm format:check`并核对最终diff。仅追加非执行性收口文档时可复用业务证据，注明候选，不循环运行构建和E2E。
7. 整项任务仅修改说明文档且不改变Spec、权限规则、执行指令、测试清单、配置或可执行检查时，只做内容／链接、格式、快照及Git差异核对；规则文字不能冒充能力实现。
8. 最终交付必须说明改动、真实验证、剩余事项。源码状态为未验证时仍可保存检查点，但不能宣称交付完成。工程检查通过只表示对应版本满足已执行检查，生产发布还须满足 [开发规范](conventions.md)的上线准入要求。

文档属于交付的一部分。GitHub远端已配置，代码、文档和快照纳入对应候选；交付前核对暂存文件，禁止提交真实.env和运行产物。当前未见托管CI强制证据，不能声称服务器会执行本地门禁。历史提交内的状态描述只对当时检查点有效。

## Demo 反向整理与正式业务开发

收到新的字段/规则文档时，先读取 [后续设计清单](deferred-design.md)。登记文档路径、版本或指纹、来源及确认依据，逐项更新已满足/缺失输入和状态。该清单统一维护后续设计工作，本规范不复制其具体待办。

对应需求条目必须链接设计决定、实现文件和验收用例。文档接收不等于获准需求或实现完成；缺外部条件只暂停依赖项，设计、实现、验证证据齐全后才关闭事项。新的文档版本到来时重新检查受影响项。

1. 用户提供或指定待分析的 Demo 版本后，先提取页面、实体、字段、状态流转、角色与权限、校验、金额口径和对接点。
2. 将“Demo 中观察到的行为”“用户/部门已确认需求”“推断及未决问题”分开标记。Demo 是需求证据，不是数据库设计或权限规则的直接授权。
3. 形成需求到页面、接口、业务模块、数据模型和验收用例的映射。到这一步再按已确认需求创建业务模块和迁移。
4. 业务页面使用现有 app/router、api 和模块边界；健康页为工程入口，可移到独立路由。通用层不嵌入案号、诉讼阶段、费用种类或角色规则。
5. 若审核需求与基线产生真实冲突，记录影响和替代方案，只暂停依赖决定的部分；不能同时建立第二套前后端、ORM 或业务状态体系来回避决定。

## 检查能力的边界

`context:check` 比较项目中受跟踪文本文件及 Demo 文本资产的新增、修改和删除，并核对当前文档采用的无标题行内相对文件链接。链接检查不支持引用式链接、带标题链接或复杂 Markdown 语法，也不验证锚点；文档采用简单行内链接，复杂链接另行人工核对。排除依赖、构建/生成结果、运行报告、秘密环境文件和本地临时目录。它不解析自然语言是否诚实、不测试业务、不监控后台进程。

快照是“已人工核对这批文件”的标记，不是语义保证。仅改日期、删除文件清单、放宽排除范围或刷新快照来掩盖差异，均不满足同步要求。新增文件类型或生成目录时同步审查检查脚本的跟踪范围。
