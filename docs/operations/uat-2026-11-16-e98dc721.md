## 接口

`POST /cases/:id/responsible-user/assign`

| 项               | 说明                                                                     |
| ---------------- | ------------------------------------------------------------------------ |
| 权限             | 同部门且具备 `case.department.proxy` + `case.routine.edit`（DEPARTMENT） |
| 与普通移交的区别 | 不要求操作人是当前负责人，可调整他人负责的案件                           |
| 目标校验         | 目标须为该部门在职内部账号                                               |
| 审计             | `case.responsible-user.assigned`，记录前后负责人与原因                   |
| 能力标记         | 案件详情返回 `recordEdits.canAssignResponsible`                          |

## 可逆性

改派能力不依赖是否为负责人，因此改派后操作人仍可立即改回。实测：

```
改派给 UAT准入主管 → 201，owner=UAT准入主管，canAssignResponsible 仍为 true
改派回知产运营   → 201，owner=知产运营
```

## 界面

「移交负责人」折叠区内新增「管理改派」按钮，仅在 `canAssignResponsible` 为真时显示，点击后二次确认：

> 确认将案件改派给「X」？改派后可由你或其他管理员随时改回。

## 授权方式

当前 UAT 没有任何角色被授予部门代理权限，因此入口默认隐藏（`canAssignResponsible=false`）。

授权路径：组织管理 → 角色 → 为目标角色勾选「部门代理」与「案件资料编辑（部门范围）」。

验证时曾临时给「UAT知产运营」角色插入这两条授权，验证完成后已删除，当前状态已复原（`CAP false`、入口隐藏）。

## 跨部门限制

系统数据隔离按部门硬性生效，`authorizeDepartmentProxyAction` 要求 `facts.departmentId === actor.departmentId`。因此本次实现是**部门内管理改派**，不是跨部门。

真正的跨部门改派需要平台级角色（跨部门身份），属于权限模型扩展，未在本次范围内。
