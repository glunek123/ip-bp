## 二、功能验收标准

### 1. 案件主链路

| 节点 | 通过判据（可观察事实） |
| --- | --- |
| 补充被告／匹配律师 | 提交后列表阶段变为"待写诉状"，承办律师显示所选律师；同一案件重复提交只有一次生效 |
| 提交起诉材料 | 未上传起诉状/授权材料/未填金额或原因时**分别**给出针对性提示；合法提交后阶段=诉状待确认、版本 +1、库内金额与原因落库 |
| 确认诉状 | 标的额与诉状版本必选；确认后阶段=诉状待盖章，确认记录含时间、金额、披露要求 |
| 登记诉状邮寄 | 邮寄日期不得晚于上海今日；未来日期时"核对"按钮禁用；核对页显示日期与份数；提交后阶段=待提交立案 |
| 提交立案 | 法院必选、日期不得晚于今日；核对页展示法院/日期/标的额/诉调号/材料份数；提交后阶段=待正式立案 |
| 正式立案受理 | 受理日期、法院案号必填；材料允许后补；提交后阶段=待开庭 |
| 开庭安排 | 开庭日期不得早于立案日；核对后保存；开庭日次日 00:00（北京时间）自动转待判决 |
| 判决登记 | 收到判决日期、判决书（≥1 份）必填；缺项时提交按钮旁明确说明原因；登记后阶段仍为待判决 |
| 二审 | 保存进展与登记结果分离；结果（发回重审/改判/维持原判）决定后续阶段；无变更重复保存必须幂等成功 |
| 执行 | 提交材料→确认→邮寄→立案备案→执行结束，每步 201 且阶段顺序推进；执行结束需"依据说明或附件至少其一" |
| 结算更新 | 付款类型、诉讼退费声明、是否涉及结算均须明确；结案金额未知时不得声明"涉及"；保存后阶段不变 |
| 实际回款／开票 | 客户回款与律师开票可分别登记，摘要即时反映金额 |
| 归档 | 付款结清/诉讼退费/客户回款/律师开票四项核查全部"通过"才可归档；归档后阶段=已归档，仅剩更正类命令 |
| 外部转入 | 可创建任意在办阶段的案件，必须记录阶段真实日期、来源、原因；创建后按该阶段继续办理 |

### 2. 结算中心与证物

| 功能 | 通过判据 |
| --- | --- |
| 结算明细筛选 | 筛选、清空、勾选在切换筛选时保留 |
| 生成账单 | 首次点击仅展开确认条（显示条数、账单日期、合计），二次确认后才创建并占用编号 |
| 证物批量改状态 | 状态与计数同步（如 在库 2→1、已邮寄律师 0→1），备注随保存写入 |

### 3. 外部端

| 端 | 通过判据 |
| --- | --- |
| 客户 | 待审核线索可"确认侵权"（转线索待确认并留审核记录）或"判定不侵权并归档"（原因必填） |
| 律师 | 本人案件列表展示分阶段计数且非空（承办案件存在时）；可对授权范围内的案件执行确认诉状等动作 |
| 公证 | 可登记开箱（照片必填 + 寄件人信息），提交后阶段=开箱待审核并留存记录 |

## 三、异常与边界验收标准（每个写操作适用）

| 场景 | 通过判据 |
| --- | --- |
| 权限不足 | 返回 403，界面提示"无权…"，不产生任何写入与版本变化 |
| 阶段／版本冲突 | 返回 409 且提示可读（"案件当前不能…"/"版本已变化，请重新读取"），保留已填内容并提供重新读取入口 |
| 并发双开 | 两个会话先后提交同一案件，后提交方被拒绝，不产生重复记录 |
| 非法日期 | 晚于业务上限的日期使提交按钮禁用（仅提示，不给服务端埋雷） |
| 金额格式 | 超过 2 位小数被拦截，提示包含正确示例 |
| 必填材料缺失 | 禁用或拦截，且**说明缺哪一项**，不用笼统文案 |
| 结果未知（网络中断/5xx） | 界面进入"结果未确认"并保留原请求键，只能"核对"或"用原请求重试"，不得静默重复提交 |
| 幂等重放 | 同一请求键重复提交只产生一次业务效果 |

## 四、自动化门禁

| 门禁 | 命令 | 通过阈值 |
| --- | --- | --- |
| 架构 | `pnpm architecture:check` | 通过 |
| 类型 | `pnpm typecheck:prepared` | 双端 0 错误 |
| Lint | `pnpm -r exec eslint . --max-warnings 0` | 0 error / 0 warning |
| 单元与集成 | `pnpm -r test` | 全部通过；新增改动必须带对应断言 |
| 静态快检 | `pnpm check:fast:prepared` | 退出码 0 |
| 冒烟（真实浏览器） | `node .local/qa/61-external-actions.mjs` 等 | 三端 0 个 ≥400 响应、0 控制台错误 |
| 完整门禁 | `pnpm verify` | 用于 Level 3／Release 候选，退出码 0 |

## 五、上线放行条件（全部满足才可上线）

1. 上文第二节每个节点至少有一次**本轮真实浏览器**通过的证据（截图或 JSON 记录）。
2. 第三节异常清单在最近一轮回归中逐项复验通过；未复验的项须写明原因并在发布说明中标注。
3. `pnpm verify` 在最终候选树退出码 0；不允许"跳过 lint／typecheck"上线。
4. 数据库迁移在测试实例上正向执行成功，且旧数据行数与校验和不变。
5. 四类角色各自完成一次登录→办理→退出，退出后会话不可继续使用。
6. 已知缺陷清单中不存在"阻断运营主流程"的项；一般缺陷须有明确规避方式并排在下一迭代。
7. 回滚方案就绪：上一版本程序包与备份可用，且演练过一次恢复。
