# 2026-11-24 未指派案件的守卫健康体检（UAT 164ae904）

## 为什么做

本次上线的「补指派」会递增 `cases.version`。案件主表上有一批延迟约束触发器（归档、结案、执行终态），历史迁移数据若缺对应快照，提交时会抛 SQLSTATE 23514，接口返回 500。运营看到的只是「服务内部错误」，无法自己判断哪个案件能补指派。这份体检给出一份可直接执行的清单。

## 方法

脚本 `backend/scripts/check-case-guards.mjs`（已在 `35e8b29c` 上线）：

```bash
cd /srv/ip-bp-uat/current/backend
set -a; . /etc/ip-bp-uat/backend.env; set +a
node scripts/check-case-guards.mjs --limit=3000 --out=/tmp/guards-all.csv
```

逐案在事务内执行 `UPDATE cases SET version = version + 1` → `SET CONSTRAINTS ALL IMMEDIATE` → `ROLLBACK`，**不提交任何数据**，只回答「这个案件现在能不能改版本」。加 `--stage=WAITING_ARCHIVE,ARCHIVED` 可只看某几个阶段。

## 运营口径

1. **诉讼阶段补指派可以放心用**：待受理、待匹配、待写诉状、待立案、待开庭、待确认诉状、待判决这 1208 个案件全部健康。
2. **待归档、执行中、待执行文书、已归档一律不要补指派**：会 500。这四类共 768 个案件需要先修数据（补归档快照 / 对齐执行终态），修数据不是本轮范围。
3. **结算不受此限制**：结算发起不改 `cases.version`。上面 33 个待归档案件里如果已经有承办律师，律师结算可以正常录（已在 `00920261118139` 实测 100.00 成功）。

## 一个需要产品决策的死结

律师结算只在「待归档」阶段允许发起，而待归档的未指派案件 **33 个全部守卫不健康**，意味着：

> 现在没有任何合法路径给「待归档 + 无律师」的案件补律师并录结算：补指派 500，结算又要求先有律师。

可选解法（未实施，等拍板）：

- **A. 修数据**：为这 33 个案件补齐归档所需的源事实，让补指派恢复可用。工作量取决于缺失快照的形态。
- **B. 放宽结算前置**：允许无律师案件先录律师结算金额（线下交付），指派后置。改动小，但要重新定义结算归属校验。
- **C. 运营兜底**：这 33 个案件线下结算，系统内只在指派完成后补录。

## 能不能靠「补数据」修好（2026-11-24 诊断）

用户倾向 A（修数据）。对 33 个待归档未指派案件做了逐案诊断，结论与预期不同：

| 形态 | 数量 | 特征 |
| --- | --- | --- |
| 无结案、无执行、无归档，`version=1` | 32 | 迁移时直接落在待归档；外部入口 `initial_stage='WAITING_ARCHIVE'`，既没有结案版本也没有执行链 |
| 有结案但来源不符 | 1 | `04320261118824`，`version=14`，有结案与两个结案版本，外部入口是 `WAITING_COMPLAINT`，与结案终态算出的版本对不上 |

报错分别落在 `check_case_execution_finish_final`（32 个，`execution external terminal mismatch`）与 `check_case_closure_final`（1 个，`closure terminal mismatch`）。

看函数体可以确认：守卫校验的不是「某一个字段空了」，而是**完整来源链**——外部入口的初始阶段、执行提交／确认／邮寄／立案／终态之间的父子与版本关系、结案版本链与审计事件的一一对应，最后由 `case_closure_terminal_version` 算出唯一合法版本。要让这些案件通过：

- 32 个需要补出从外部入口到执行终态的整条链（提交、确认、邮寄、立案、终态 + 每步版本与审计），本质是**编造一段从未发生的执行流程**；
- 1 个需要重排结案版本链或改写外部入口阶段，等于改写已达成的结案事实。

两条都不属于数据清理，而是重写业务历史。审计表还要求 `actor_kind='HUMAN'` 且 `actor_user_id` 是真实账号，意味着要以某个运营的名义写入从未做过的操作。**不建议用 SQL 自动化做这件事**，也不建议给脚本开放写入权限。

## 可行的三条路（按风险从低到高）

1. **运营在系统内走正式流程（首选）**：如果这些案件在业务上确实结过案，只是迁移时漏了，让运营用「登记结案资料 → 结案 → 归档」的正常入口补一次，由系统自己生成版本链与审计。前提是阶段允许、材料齐全；走不通的案件才落到第 3 条。这条路不伪造任何事实。
2. **放宽结算前置**：允许「待归档 + 无律师」先录律师结算金额。代价是要改 `case_settlement_launches` 的 CHECK（`side='LAWYER'` 现在强制 `lawyer_id IS NOT NULL`）并重新定义无律师时的归属语义，影响面比看起来大。
3. **线下兜底（最省事）**：这 33 个案件线下结算，系统内等指派完成后再补录，或只登记备注。

建议先做一次抽样：抽 3 个案件问业务「是否真的结过案」。如果答案是「结过、只是没录」，走第 1 条；如果是「本来就没结案、是迁移硬塞进待归档」，那这批数据的阶段本身就是错的，需要业务确认应该退回到哪个阶段，而不是补成已结案。
