## 本轮验收发现的新缺陷（未修）

**结算再次保存 → 500（P2002 唯一键冲突）**

- 触发：案件 `00520261110002`（待归档、已有一份「历史结案文书」）第二次保存结算更新，
  同时勾选「结案金额已确认」与「无诉讼退费」。
- 现象：`POST /api/v1/cases/:id/closure-settlement-updates` 返回 500 `INTERNAL_ERROR`，
  请求 ID `49cc5b67…`／`29372678…`。
- 定位：`backend/src/modules/materials/material.service.ts` → `freezeCaseClosureReferences`
  内 `caseClosureDocument.create`，Prisma `P2002` / PG `23505`，
  冲突键为 `case_closure_documents(closure_version_id, material_id)`。
- 推断：同一 `closureVersionId` 下同一 `materialId` 被冻结两次（历史文书与本次选择各冻结一次，
  或冻结函数在同一事务内被调用两次）。按 materialId/内容版本去重两次尝试均未解除，已回退，
  需要在调用侧或改用 `createMany({skipDuplicates:true})` 处理，并补一条"重复冻结"用例。
- 影响：运营改一次结算金额就会失败；B13 已通过（回款 5000 已登记），B14 归档因此无法进入。

## 结算重复保存 500：已定位并修复（`63759594`）

根因不是脚本，是产品：结案资料冻结 `freezeCaseClosureReferences` 在同一事务里被调用两次
（结案一次、结算一次），逐条 `create` 撞了两处唯一键
——`case_closure_documents(closure_version_id, material_id)` 和
`material_references` 上"每案每用途每内容版本唯一"的**部分**唯一索引（不带事件维度）。

修法：冻结语义是"保证该版本包含这些材料"，改为 `createMany + skipDuplicates`，
让唯一键在数据库侧裁决，并发下也安全；同一次调用内再按内容版本去重。
材料套件 339 项全过；复测时错误从材料层（5855 行）前移到结算事务层，说明该缺陷已消除。

### 23514 的进一步定位（未闭环）

- 复现路径唯一：`settlement.declaration='APPLICABLE'`（界面选"涉及结算"）+ 结案金额已确认。
  不带 `settlement` 字段的保存（明确不涉及/待定）可正常 201，说明问题只在评估写入这一支。
- 该案件目前**没有任何 `case_settlement_assessment_versions` 行**（首次评估）。
- 数据库里**没有 deferrable 的 CHECK 约束**，因此 `SET CONSTRAINTS ALL IMMEDIATE` 报 23514
  不像是常规延迟检查；更像是评估写入所用的原始 SQL/触发器在建行时抛错，
  被 Prisma 归到该批次语句上。
- 现有守卫 `SETTLEMENT_AMOUNT_UNKNOWN`（`settlement-assessment-draft.service.ts:112-128`）
  检查 `closureAmountState !== 'KNOWN'` 与 `result.customerAmount/lawyerAmount` 为 null；
  复现时结案金额已确认，说明 `calculateSettlement` 返回了数值，但落库的
  `customer_amount`/`lawyer_amount` 仍为空——需要对比"计算结果的字段名"与
  "insert 时取的字段名"是否错位。
- 下一步（精确）：在 `settlement-assessment-draft.service.ts` 落库前打印
  `{declaration, customerAmount, lawyerAmount, calculationResult}`，跑一次复现，
  即可确认是取错字段还是计算结果本身为空，再决定补哪一侧。

### 结算更新的根因：结案文书跨版本复用与两条数据库约束冲突（设计级，待决策）

用 API 直接驱动后拿到确定结论（与前端无关）：

1. `closeAmountState=PENDING` + 声明"涉及" → **409 `SETTLEMENT_AMOUNT_UNKNOWN`**（可读、正确），
   证明本轮修的守卫生效（此前同组合是 500）。
2. 改为 `closeAmountState=KNOWN` + 双方手工金额 → 仍在 `SET CONSTRAINTS ALL IMMEDIATE` 处 500，
   数据库日志给出真正的报错：
   - `closure audit/reference/receipt mismatch`（引用必须绑定本次结案版本的审计事件）
   - 尝试把已有引用改绑事件 → `immutable closure reference`（引用创建后不可变）

两条约束叠加的结果是：**同一份结案文书不能跨结案版本复用**。而界面每次保存结算都会
携带 `closeContentVersionIds`，后端据此创建新的结案版本并要求新引用，于是必然冲突。

因此这不是"一行代码的 bug"，需要产品决策，三选一：

- **A（推荐）**：结算更新不新建结案版本——结算字段与结案资料分离，只在结案资料确实变化时
  才产生新版本（前端在未改资料时不提交 `closeContentVersionIds`，后端复用当前版本）。
- B：放宽 `material_references` 的部分唯一索引，允许同一文书对应多个事件，改由触发器按
  "版本→事件"校验。
- C：要求运营每次改结算都重新上传结案文书（运营成本高，不接受）。

阻塞影响：**任何已有结案文书的案件，第二次保存结算都会失败**，B14 归档与"改金额"日常动作
全部走不通，是当前唯一的上线阻断项。

### 方案 A 的落地与边界（2026-11-10 下午）

已实现：金额命令 `POST /cases/:id/closure-settlement-amounts` 支持可选 `declaration`，
前端把"只改声明/金额"路由到该命令——它**不新建结案版本**，因此不触碰引用唯一/不可变约束。
结算面板 55 项用例通过（新增：声明+金额走金额命令）。

**边界（仍未解决）**：当运营同时改付款记录、退费、结案日期或结案资料时，仍走整单
`closure-settlement-updates`，会新建结案版本并重新冻结文书 → 仍 500。
用 API 实测过 `closeContentVersionIds: []` 能 201，但新版本**丢失全部结案文书**
（v12 文书数 0，v11 为 1），属于静默数据丢失，不可接受。

结论：方案 A 只覆盖"改声明/金额"这一支；"改付款/退费 + 已有结案文书"仍需放宽
`material_references` 的部分唯一索引（方案 B），或在后端做"文书沿用但不重复冻结"的
专门实现，并补迁移与回填验证。
