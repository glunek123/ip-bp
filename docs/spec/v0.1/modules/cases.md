# CA 案件

案件办理阶段、审理结果、材料、资金和归档是不同维度。SD-23整体采用本页16阶段门槛；SD-39把普通组员的案件读取与办理范围拆开；仍不得仅按数组next生成正式工作流。

依据：[固定事实](../../../demo-reverse/v158/modules/M02-cases.md)、[候选](../../../demo-reverse/v158/modules/M02-cases-candidates.md)、[决定](../../../demo-reverse/v158/DECISIONS.md)和[纠偏](../../../demo-reverse/v158/CORRECTIONS.md)。字段只在[领域模型](../DOMAIN.md)维护；B/T/E编号见[缺口](../GAPS.md)，通用技术设计见[TD-BASE-05／TD-AUTHZ-01／TD-TRACE-UX-01](../TECHNICAL-DESIGN.md)。本页AC描述业务目标，实际切片完成状态与验证证据分别以[路线图](../../../feature-roadmap.md)和[验证记录](../VALIDATION.md)为准。

侧栏的顶层工作流节点按办理顺序呈现，其中`准备起诉文书`承载“待写诉状→诉状待确认→诉状待盖章”，`准备执行文书`承载“待写执行材料→执行材料待确认→执行材料待盖章”。它们与“案件待匹配”“待提交立案”等节点同级，是连续办理过程的入口与进度呈现；不是跳过内部三步的一次性动作，也不把组名写成案件阶段值。

AC-CA-010（条件性、未执行）：按SD-23已批准的正常阶段前置数据分别构造16个当前阶段对象，执行表内动作与一个不合法跨阶段动作。预期正常动作只到所列目标、保存不推进、缺必要项不推进、非法跨阶段拒绝；判决／二审／执行结束和结案资金未知分支在B13/B15完成前不可标为整条流程验收通过。此场景补充既有REQ，不另造一组字段定义。

## REQ-CA-001 正常建案与转入／历史补录

- 状态：确认方向（BD-02、SD-16/22/23/24）＋纠偏约束。来源：C-C01 C-D02 C-D10 BD-02 FIX-07 FIX-14。字段组：CA01/CA13。
- 目标／动作与结果：正常建案从案件待匹配按16阶段门槛逐步办理，不允许普通新建跳阶段。外部转入／中途接办的在办案件，以及历史案件，使用独立的“转入／补录案件”入口；具备SD-23所定权限和数据范围的人员可选择实际所在的任意阶段，从该阶段继续正常流转。真实业务日期、资料来源和转入／补录原因必填；直接录入已归档仍须具备高风险归档补录权限。初始模板沿用主管或其授权运营／归档仅主管，新案不生成模拟明细。
- 异常、边界及待决：转入／补录不要求虚构此前未在本系统办理的阶段或材料；录入已知真实事实，客户与权利主体仍满足SD-22准入，后续动作仍遵守目标阶段起的正常门槛。普通入口仍不得跳阶段。正常门槛例外由具备对应权限的人员直接处理并填写原因，不建立审批单或审批队列；角色改名或调整不改变材料门槛，编号、防重、并发和审计契约进入T01/T02。
- 依赖：T01/T02/T03；正式操作者与数据范围统一受REQ-XM-001约束。编号基线按SD-08，批量、失败和重复控制见REQ-SH-004。
- AC-CA-001：**给定／操作**：客户转入一件实际已在强制执行中的案件；无补录权限的人员尝试选择已归档；有普通补录权限者填写转入业务日期／来源／原因并录入强制执行中，再尝试录入已归档；有高风险归档补录权限者再执行。**预期**：无权限入口拒绝；合格转入成功且无虚构前序材料，可从强制执行中继续办理；普通补录不能直接到已归档，高风险权限可直接完成并留下原因和审计，不产生审批任务。

## REQ-CA-002 编号及当事人承办

- 状态：Demo基线（SD-08）＋确认方向（SD-17）＋纠偏约束；承办细则待审核。来源：C-C01 C-C02 C-C03 C-D01 C-D03 FIX-03 FIX-11。字段组：CA01/CA02/CA03。
- 目标／动作与结果：案件创建时产生本案业务号；案件身份、业务号、诉调号、法院案号和执行案号独立，外部编号实际产生后补录。案件可维护多名真实律师并允许中途更换，时间轴记录更换；单／批量使用同一动作准入；调整法院案号不能破坏案件关联。
- CA-001匹配补充：至少登记一名主办律师姓名；律所和电话未知时可留空，不填假值。新匹配必须填实际匹配日期`matchedOn`，页面默认当天、可改为真实过去日期，不允许未来日期；这是业务日期，不是操作时间。系统完成匹配时间`matchedAt`和审计时间由服务端自动记录，不能由请求指定。旧案没有实际匹配日期时显示“未记录”，不从`matchedAt`推定。日期、律师与阶段推进在同一事务、同一幂等请求中保存。仅升级前已成功的旧匹配回执允许原请求不含日期、同幂等键原样重放，返回`matchedOn: null`且不再次写入；任何新匹配不适用此例外。
- 异常、边界及待决：显示业务号不承担技术主键职责；编码、唯一性和防重由T01设计。同名被告不直接去重；旧律师只读其参与期间案件／材料，更换要求`case.lawyer.replace`及匹配数据范围，初始模板授予主管和本团队小组长；主办／协办仍按B13。
- 依赖：B13/T01/T03；正式操作者与数据范围统一受REQ-XM-001约束。相关批量、失败和重复控制见REQ-SH-004。
- AC-CA-002：**给定／操作**：已有业务号A、法院案号旧值及费用关联；编辑法院案号为新值。**预期**：业务号A、案件身份和费用关联不变；列表和详情均显示新法院案号。

## REQ-CA-003 起诉、邮寄与立案

- 状态：待审核＋纠偏约束。来源：C-C04 C-C07 C-D03 C-D06。字段组：CA04/CA05/CA06/MT01。
- 目标／动作与结果：按阶段登记起诉材料、确认、邮寄、立案及受理信息；客户和运营都可登记本企业／获授权案件的诉状盖章邮寄，保存草稿与确认推进区分。批量上传材料不冒充已确认办理；自动归案必须明确目标，模糊多匹配不能默选首案。当前动作缺件在原表单／详情就地提示并能定位材料，后端提交仍重新校验。
- 异常、边界及待决：阶段材料门槛按SD-23，文件生命周期按SD-25；ZIP逐文件反馈，但阶段推进批次不得因部分成功留下混合状态。数据校验与状态守卫在服务端设计，不只隐藏按钮。
- 依赖：T02/T05/E02；正式操作者与数据范围统一受REQ-XM-001约束。相关批量、失败和重复控制见REQ-SH-004。
- AC-CA-003：**给定／操作**：两案有相同被告名，批量上传仅含被告名的文书；另在缺必要立案材料时推进。**预期**：歧义文件不得直接归首案，应说明待确认；缺获准必要项不能推进；成功文件范围与失败行明确，不假定全批成功。

### CORE-CA-003 确认诉状契约

本动作细化SD-23、SD-25／26／39及[字段与材料契约§7](../../../superpowers/specs/2026-09-21-core-flow-field-material-contract.md#7-core-ca字段与动作契约)，不改变正常流程方向。

- 单案`WAITING_COMPLAINT_CONFIRMATION → WAITING_COMPLAINT_STAMP`，页面显示“诉状待确认→诉状待盖章”。只有当前有效内部账号具备`case.complaint.confirm`并覆盖目标案才能办理；同部门非负责组员仍只读可下载，客户／公证处不能确认。新增Action复用既有授权计算，不拼接读取范围提权。初始Grant从原`case.complaint.submit`同范围复制，保留既有SELF／TEAM／DEPARTMENT边界，并使受影响授权版本失效。
- `POST /api/v1/cases/:id/complaint-confirm`请求包含`expectedVersion`、`idempotencyKey`、`confirmedComplaintContentVersionId`、`amountState`、条件`amount/pendingReason`、`changeNote?`和明确的`confirmDisclose: boolean`。成功返回`id/stage/version/confirmedAt`；幂等键1～128字符，金额与CA-002同一人民币Decimal口径，不接受浮点、负数或用假0代替未知。`KNOWN`须非负金额且无待定说明；`PENDING`须1～500字符说明且无金额。
- 确认一个明确的本案有效`COMPLAINT`内容版本。复用CA-002材料格式、50MB上限和真实文件校验；可选原已提交的有效版本，也可先上传修订诉状后选择。唯一版本自动选择，多版本用文件名和版本信息明示，不能默选首项。待确认时仅有确认权限的人员可上传本案诉状；不因此开放授权书更换或其他阶段写入。原提交冻结引用继续保留、可读且不可删除。
- 以原CA-002提交事实对比所选版本及金额状态／金额／待定说明；选用未在原提交中出现的版本或改变金额事实时，`changeNote`必填（1～500字符）。原诉状提交金额、版本、提交回执及历史不覆盖；本次确认另存不可改删事实、操作者和服务端时间，冻结所选精确版本。
- `confirmDisclose`记录本次是否需要下载诉状／授权书，不等于已下载、对外披露授权或支付事实。首版提供现有真实逐件下载：需要下载时在确认记录中明确提示下载入口，不声称已生成ZIP或已下载。批量确认、按品牌打包及自动生成文书不在本动作范围。
- 当前身份与数据范围、阶段、版本及材料可用性须在后端重新校验；阶段CAS、确认事实、成功审计`case.complaint.confirmed`、材料冻结与成功回执在同一事务完成。相同键同请求在当前授权仍有效时返回原结果，不重复推进／审计；同键不同请求冲突，旧版本和并发竞争稳定拒绝。审计、冻结或回执失败整体回滚。撤权／转派后下一请求失效，重放不得绕过。
- 详情分别展示原提交和本次确认，列表、侧栏“准备起诉文书”计数及筛选包含新增原子阶段，仍只使用一套阶段导航；诉状待盖章只展示已完成事实，不提供未实现的邮寄操作。加载、成功、已知冲突和未知结果明确反馈；未知提交结果保留原幂等请求，先核对或原样重试，不新建请求重复办理。

AC-CA-011：真实账号经正常来源转案、匹配、上传诉状／授权书和提交后，运营确认精确诉状版本，进入诉状待盖章；刷新、重新登录后原提交和确认事实、金额及真实附件仍可读取。同部门非负责人读取和下载成功但确认403，跨部门404，客户／公证处拒绝；换版本／金额无说明、无权限、撤权重放、旧版本、错误阶段、不可用或他案材料均拒绝。同键重放不重复，同键不同内容冲突，并发只一份成功事实；审计／冻结／回执失败无部分推进。迁移从空库及上一支持schema执行，保留旧提交与回执，验证直接数据库负向输入及失败原子性。

## REQ-CA-004 判决、二审与执行

- 状态：待审核。来源：C-C04 C-C05 C-C06 C-D04。字段组：CA07/CA08/CA09/CA13。
- 目标／动作与结果：判决登记与后续分支分别办理；二审保存不等结果确认。发回重审回到办理受理的流程，改判／维持按确认结果进入执行准备。案件允许多名律师并记录更换；客户和运营都可登记执行材料邮寄。执行更新保存不等执行结束；必须定义结束动作后才允许转待归档。
- 异常、边界及待决：是否必经二审抉择、多轮历史、改判金额／退费权限及执行重启B13；不从Demo单组顶层字段推出只允许一轮。
- 依赖：SD-23/B13/B15/T02；正式操作者与数据范围统一受REQ-XM-001约束。相关批量、失败和重复控制见REQ-SH-004，未定策略不视为已批准。
- AC-CA-004：**给定／操作**：登记一审判决但尚未选择后续分支；另对强制执行中案件保存执行文书。**预期**：前者不直接视为已执行，后者不因保存自动进入待归档；发回重审的历史保留验收待B13确认。

## REQ-CA-005 结案归档与实际款项

- 状态：纠偏约束＋待审核。来源：C-C08 C-D08 C-D09 FIX-08 FIX-09。字段组：CA10/CA11/ST02/ST04。
- 目标／动作与结果：结案、归档、收付款与结算分别记录。归档逐案检查真实状态，不依据当前筛选器替整批决定动作；归档不显示已结算。分期改一次性不能静默丢弃已保存付款。
- 异常、边界及待决：结案与终结归档门槛、付款必填、重开删除B15；费用改删另受BD-06；提示说明实际影响，不能用提示替代留存设计。
- 依赖：B15/B20/B21/T02；正式操作者与数据范围统一受REQ-XM-001约束。相关批量、失败和重复控制见REQ-SH-004。
- AC-CA-005：**给定／操作**：案件已归档但没有财务完成结果；另一案已有两条实际付款，切换付款方式。**预期**：第一案不得显示结算已完成；第二案不得静默删除第二笔真实款项，具体调整路径B15待确认。

## REQ-CA-006 合并办理组

- 状态：确认方向（BD-03、SD-18/24/27）＋纠偏约束。来源：C-C09 C-D07 BD-03 FIX-04。字段组：CA12/NT01/FE01/MT01。
- 目标／动作与结果：同一客户的案件可加入一个可解除的合并办理组，不附加同主体、同被告、案由或办理阶段限制。源案、编号、主体、被告、材料、费用和外部引用保持原身份与归属，组内仅聚合查看；成员前后集合自动留痕，聚合按源案身份去重；合并／解除要求对应操作权限和覆盖全部源案的数据范围。
- 异常、边界及待决：不新建替代主案，不选择冲突字段覆盖源案，不复制或删除材料／费用。入组不授予其他源案访问，聚合Query逐案施加当前授权；组内批量动作须在各动作TD-SLICE明确T02模式，合并本身不改变案件阶段或财务状态。
- 依赖：T01/T02/T03/T05/T06；正式操作者与数据范围统一受REQ-XM-001约束。相关批量、失败和重复控制见REQ-SH-004。
- AC-CA-006：**给定／操作**：同一客户的两案具有不同主体、被告和案由；小组长在本团队建立办理组，查看聚合材料／费用后解除。**预期**：两案身份和所有原归属不变，不产生主案或重复支付指令；组内清楚标识来源案；解除后源案仍完整可查。
