## 必须纠正的简化理解

参考会话“审核主链冻结范围”（conversationId `6aaa2114-c4d0-83eb-979b-1d52388a914c`）的缓存预览属于讨论输入，助手建议不是用户批准。其“Fee→Settlement”示意不能作实体生成关系：

```text
客户 ↔ 权利主体                 已确认多对多；不授权跨部门共享
      ↓ 每条线索／案件各选一个
线索 → 多次明确取证批次／公证事项 → 案件
          ├─ 原费用 ─────────────→ 保留身份与来源关联
          └─ 材料／证物／公证书 → 分别记录，不能混成附件名
案件＋适用协议／金额 → 分侧结算发起明细 → 汇总账单 → 财务结果
```

图中公证→案件的**正式基数待定**；费用并非结算的已确认直接计算输入。Demo `settleFigures`按结案金额等回退值及协议计算，客户与律师分别计算，未在该计算函数读取费用列表；发起另写台账和中心明细。见[结算事实M06](../../../demo-reverse/v158/modules/M06-settlement.md)及[源码](../../../../demo/app.js) L5497–5515、5731–5750、5812–5852。将来费用是否扣减结算必须有B19决定，不能因图示新增规则。

公证流程不只是直线：线上开箱、线下调查、出证、线下直诉、不出证退货、归档是不同分支。固定Demo及BD-03曾把合并源案转为公证归档来源；SD-27以更具体的后续决定改为可解除合并办理组，正式目标不再为合并新建替代案或归档壳。出证归档、案件归档、结算发起、财务完成仍是不同事实。

## BR-04补问确认后的切片依赖

1. **客户／主体基础**：SD-22已补精确判重、无证件草稿和历史留存；可先形成客户基础TD-SLICE，明确排除联系人／开票细节、外部账号和真实存储。
2. **取证批次＋公证办理＋转案**：SD-14/15已补物流明确无、人工改号和退款上限；仍依BQ-03～05及BQ-11的混包、直诉、改号权限、退款口径、未转案费用和文件规则。可以后置真实财务接口，不能把费用关联概念整体后置。
3. **案件正常办理＋历史补录＋合并**：SD-23～27已补正常门槛、补录表单、案件矩阵、旧律师和合并办理组。历史补录与合并可分别进入最小TD-SLICE；审理执行、结案资金和专属材料仍阻断完整案件状态机。
4. **费用处理与结算闭环**：SD-26已补金额已知／待定、0元、方向和累计退款；金额基础可进入TD-SLICE。公式、费用类别／收付方、撤销、部分结果和外部协议仍阻断完整结算流程。

以上不是强制等所有24项业务缺口清零。逐切片登记获准REQ、AC、排除项、依赖、批准依据，满足[READINESS](../READINESS.md)再标“可设计”，不自动标“可编码”。
