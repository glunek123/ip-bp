## 使用顺序与权威边界

准备审核主链时，先读[冻结前准备包PREP-1](preparation/README.md)：关系证据、逐阶段门槛、异常路径及未决输入；这是SPEC-002补证，不改变条款批准状态。

1. 阅读本页和[术语](CONTEXT.md)，再读[领域模型](DOMAIN.md)。
2. 按下方模块导航读取目标行为与验收场景；[跨模块规则](CROSS-MODULE.md)约束所有入口。
3. 使用[覆盖映射](COVERAGE.md)追溯候选、BD、FIX、G、U；对证据疑点先查[一致性核查](CONSISTENCY.md)。
4. 查[缺口](GAPS.md)和[就绪清单](READINESS.md)，只将明确确认且依赖闭合的范围交给切片技术设计；共用机制和本次字段准备设计见[技术设计](TECHNICAL-DESIGN.md)。
5. 实际验证与历史交付见[验证报告](VALIDATION.md)，当前任务只看[项目状态](../../project-status.md)。

当前实现状态与开发顺序只见[功能开发路线图](../../feature-roadmap.md)，当前活动任务只见[项目状态](../../project-status.md)。

固定输入：[反向证据指纹](EVIDENCE.md)、[v158事实](../../demo-reverse/v158/AS-IS.md)、[12项用户决定](../../demo-reverse/v158/DECISIONS.md)、[纠偏](../../demo-reverse/v158/CORRECTIONS.md)及[INPUT-001](../../deferred-design.md)。新增决定见[SD-01～37](DECISIONS.md)；BR-03原始回件及指纹也登记在EVIDENCE，后续确认依据登记为INPUT-010～015。目标条款与Demo或原建议不同可能是有意纠偏；不得用源码反向覆盖用户决定。

## 规则和状态约定

- REQ-模块-序号为稳定需求ID；AC-模块-序号为目标验收场景ID。删除或替代需求保留旧ID及替代关系，不重新编号。
- **确认方向**：只在明确BD／SD／INPUT确认范围内生效，细节缺口仍适用；**纠偏约束**：用户已授权确定错误的文档纠偏，不借此批准新功能或未知策略；**待审核**：完整目标建议，未经模块审核不得实现；**范围待定**：是否纳入本期尚待决定。
- 各模块中出现“系统应”描述目标，而不是已实现事实。状态列决定批准程度，不能只截取句子交给开发AI。
- T01～09的共用技术设计、简单性约束及结算字段／文件准备设计已经形成；各业务能力是否已经实现只由功能开发路线图判定，不在本页重复维护。
- 字段的业务含义和归属只在DOMAIN维护；模块描述动作时引用字段组，不再维护第二份字段字典。字段技术名仅映射旧Demo，不是正式DTO／数据库列。
- 无依据的必填、枚举、关系基数、审批链、金额或法律期限不自行补齐。禁止将演示姓名、默认银行、历史种子和按钮隐藏当业务要求。

## 范围

覆盖客户及权利主体、线索、公证、案件、费用、结算、证物及公证书、日历、报表、模板与数据管理、共享真实数据和权限边界。四端、共享库部门强隔离及可配置角色／案件成员授权进入全局要求；各端专属功能和权限代码仍随对应切片确认。

提供业务目标、设计输入、TD-BASE通用设计及客户基础最小切片；保持现有Vue／Nest模块化单体、PostgreSQL／Prisma、REST／OpenAPI等[技术基线](../../architecture.md)。除客户基础切片外不设计业务端点地址或具体请求响应；本版不产出物理表或迁移，不选择真实登录、存储、财务、公证或AI供应商。

## 维护协议

用户新答复登记日期、原意、受影响REQ／AC和替代关系；仅变更相应条款状态，不批准整份文档。规则更改需检查上游来源、下游副作用、验收和交接范围。未来每条获准实施的需求必须回填设计位置、接口、实现文件、测试及验证版本；没有产物时保留“未产生”，不放假链接。
