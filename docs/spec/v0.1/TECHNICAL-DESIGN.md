## 2. 模块、接口与依赖方向

继续使用[技术基线](../../architecture.md)的Vue／Nest模块化单体。每个业务模块对外只暴露两类接口：

- **Command接口**：表达一次明确写入意图，在模块内完成权限、当前状态、输入、关系及并发校验。
- **Query接口**：返回按调用方数据范围约束的类型化结果，不返回Prisma实体，不要求调用方直连本模块表。

Controller只负责HTTP解析、DTO校验和错误映射；业务校验位于所属模块的Command实现内。跨模块写入由主责模块组织，通过其他模块公开接口完成；不跨过接口改写别的模块数据。

概念契约如下，名称用于后续TD-SLICE保持一致，不表示本轮已创建TypeScript类型：

```text
CommandContext = actor + requestId + idempotencyKey? + expectedVersion?
CommandResult<T> = value + version + occurredAt + affectedIds
BatchResult<T> = requestedIds + succeeded + failed + committedMode
QueryContext = actor + dataScope + requestId
```

`actor`是已验证调用者语境，不是前端传入的角色字符串；`affectedIds`只包含实际成功写入对象；`committedMode`明确本次是全部成功或逐项结果，不让页面猜测。

## 3. T01：稳定身份、编号和类型化关联

### 已确定

- 按[开发规范](../../conventions.md)，新业务实体使用UUID字符串作技术主键；技术主键不展示为案号。
- 线索、公证事项、案件等保留各自业务单号，法院案号、执行案号和外部回执号分开存放。
- 模块内关联优先使用明确外键。必须表达多种来源时使用“来源类型＋来源身份”的可辨识关联，禁止单个无类型`caseId`承载公证事项、案件等不同对象。
- 业务单号在所属记录创建事务内分配；重试同一创建意图不能多占号或多建记录。

### 留待TD-SLICE

具体编号前缀、年度段、长度和业务唯一范围在对应切片设计时决定。客户适用信用／证件号码精确重复的唯一范围为同部门和同证件类型；名称重复只产生提醒和继续原因，不建立名称唯一约束。合并办理组只关联源案身份，不分配替代主案编号，也不复制材料或费用。

## 4. T02：写入一致性、并发、防重与批量结果

每个Command按固定顺序处理：

1. 从会话获得`actor`和数据范围，不信任请求体角色。
2. 读取目标及必要关联，验证数据范围、当前阶段和业务前置条件。
3. 比对`expectedVersion`；版本已变更时返回409及稳定错误码，不以后到请求静默覆盖。
4. 在单一PostgreSQL事务内完成本地业务事实、关联、版本和审计索引写入。外部HTTP调用不放进数据库事务。
5. 返回真实完成范围；失败时不生成“已完成”活动或假回执。

有副作用且可被网络重试的Command接受`idempotencyKey`。后端按“已验证调用者＋动作＋密钥”保存请求指纹和结果：相同密钥与相同指纹返回原结果，相同密钥与不同指纹返回409。“明确新建第二批”必须使用新意图密钥，与重试分开。

批量操作先固定明确选中的身份集合，再校验。技术契约支持两种可观察模式：

- `all-or-nothing`：任一项不合法则全批不写；
- `per-item`：逐项独立提交，返回每项结果。

每个业务动作必须在TD-SLICE中选定一种，页面不能自行切换。SD-07只确定“无选不执行”，不被扩大为全局批量原子性结论。

## 5. T03：身份语境、可配置授权和数据范围

定义应用内部`ActorContext`，最少包含稳定账号身份、当前活动部门、团队／组织归属、可验证的外部主体关联和`authorizationRevision`。角色名称、部门和权限不得从请求体直接接受。身份提供方适配与业务授权分层：

- SD-35已固定v0.1先使用管理员开通的实名内部账号，由AUTH-LOCAL-001定义本地密码和会话；未来公司SSO／OIDC以稳定`issuer + subject`映射为同一账号。MFA、恢复和OIDC仍分别后续。
- 授权层按一个不可拆分的`Grant = action + scope`判定。只有同一个有效授权同时允许目标动作并覆盖目标资源时才放行，不能把“本部门查看”和“本人编辑”合并成“本部门编辑”。
- `scope`首期只支持`selfResponsible`、`participant`、`team`、`department`和`explicitDepartments`五种数据范围；不提供自定义表达式或通用策略语言。
- 角色模板只是多个Grant的可编辑集合；主管、小组长和运营是SD-24默认模板。同一人员可以在不同部门获得不同模板，Query在数据库读取时即施加对应范围，不先读全量再在前端或内存过滤。
- 案件负责人、律师和协作人员作为资源成员提供个别授权。普通协作只使用“只读／办理”预设；办理不自动获得合并、终止、归档、导出或证件下载。
- 默认拒绝。授权管理动作也需要Grant和“可授予上限”；禁止自我提权、跨部门越级授予及授予自己不具备委托权的高风险权限。

权限模板或分配保存后提升相关账号的`authorizationRevision`；下一次服务端请求必须重新按新版本判定，旧会话或权限缓存不得继续沿用已撤销授权。角色升降、账号停用等敏感变化应使旧会话失效；每次模板、分配、成员和负责人变更记录前后值、操作者、原因及影响范围。授权决定可返回安全的`reasonSource`供管理页面解释“为何有权”，但不得泄露其他部门数据。

SD-33选择共享库／共享表按部门强隔离。所有部门业务记录必须具备可信部门归属，列表、详情、搜索、导出、统计、文件、后台任务和缓存键均施加范围；客户端提交的部门值仅作为意图，必须由服务端根据有效授权确认。权限只决定谁可尝试动作，业务Module仍独立校验阶段、材料、金额、合并和归档门槛。有权角色直接执行受控动作并提交原因，不设计审批单、审批队列或审批状态机。

## 6. T04：金额、日期、时间和调度

### 金额

- HTTP中金额使用十进制字符串，不使用JSON浮点数作权威值。
- 服务内计算使用`decimal.js`，中间值不提前取整或到分。
- SD-05确定的“每笔最终金额四舍五入到分”在业务金额最终化点使用十进制`ROUND_HALF_UP`，并记录应用前的计算来源。
- PostgreSQL使用Decimal；具体precision/scale在首个金额切片根据合法上限决定，不以未知范围为由盲目设极大精度。

SD-26规定所有业务金额使用`known`／`pending`两种业务状态。`known`时金额必填、允许0且不得为负；`pending`时金额字段不提交，不得默认0。费用方向、退款和冲销使用类型／方向字段，不用负数；0元业务记录可保存，但Command不得生成支付或结算指令。同一原支出的累计退款上限在写入事务中校验。具体费用类别、收付方、公式、已处理更正和非单笔指标仍在对应TD-SLICE决定。

### 日期与调度

- 业务日期使用数据库`date`和`YYYY-MM-DD`；实际操作时点使用`timestamptz`和带时区ISO 8601。
- 展示和业务调度使用`Asia/Shanghai`；不把日期字符串先转UTC子夜再取本地日期。
- 开庭自动推进使用持久化触发条件的可重入扫描，而不依赖页面打开。执行时重新校验当前阶段、开庭日期和已执行标记；重复跑不产生第二次推进。
- 调度异常恢复采用“补扫未满足已执行标记的到期对象”，不伪造原应执行时刻。延期和已推进后更正的业务结果等BQ-08。

## 7. T05：文件、上传草稿与OCR候选

文件能力放在业务模块与私有对象存储实现之间的单一缝隙。业务模块只依赖以下能力：建立上传草稿、完成内容持久化、读取经授权内容、标记删除、恢复、作废／更正关联及获取内容元数据。知产和品维使用隔离私有命名空间，数据库只保存元数据和关联；具体服务商、加密、备份和恢复由E02后续决定，页面不直连存储凭据或永久公开链接。

文件元数据与业务关联分开。上传草稿绑定已验证调用者和预期业务目标；最终提交再次校验目标和权限，避免“在A上传、切换B后写入B”。原文件名、实际内容身份、MIME／扩展名、大小和校验和分别保留；业务可见文件名不充当存储定位符。

SD-09的OCR使用独立候选流：

```text
获准材料 -> OCR任务 -> 结构校验 -> 字段候选 -> 人工选择 -> 普通业务Command再校验并采用
```

OCR输出不直接修改业务字段或阶段；候选保留来源材料、任务和目标字段对应。人工采用时使用普通Command、当前版本和当前权限，因此过期候选不能覆盖新值。允许发送的材料／字段及供应商等待BQ-11、E04。

SD-21/25要求删除后可恢复，SD-28使文件动作也通过可配置授权执行。技术缝隙定义`active`、`deleted`、`superseded`三种可见状态，并保留稳定材料身份、内容身份、原业务关联、操作者、原因和时点。上传人或当前业务负责人删除／恢复未引用文件是初始Grant，具体请求仍需动作和范围同时匹配；`deleted`从删除时起保留90天，恢复原关联而不是复制。被阶段、账单或发票引用的文件不能转`deleted`，只能上传新版本并把旧版标为`superseded`。90天后只有技术管理员可执行最终清除，但不会因此获得正文查看权，且必须写审计；在E02适配器确认前仍不提供物理清除实现。

客户证件按SD-32限定PDF、JPG/JPEG、PNG，单文件不超过20MB、单次最多10个；后端根据真实内容MIME、大小和安全检查判定，拒绝不可检查／预览的加密PDF及Word、Excel、压缩包和可执行文件。换版保存新内容版本并保留原件，不原位覆盖；这些限制不自动套用其他案件材料类型，也不得把证件发送到公共扫描服务。

## 8. T06：权威事实、读取投影与外部处理

- 费用、结算发起、账单明细和实际财务结果按DOMAIN的不同概念保存，不用一个“已完成”字段取代。
- 列表、中心页、客户统计和报表可使用可重建读取投影，但投影不提供业务编辑入口。重建投影不会改写原始事实。
- 投影行保留来源身份和计算版本；页面和导出的同名指标调用同一Query接口，不在前端各算一份。
- 外部发送与业务状态分开，使用持久化的“待处理／尝试／结果”记录承载请求指纹、幂等标识及未知结果。本地业务事务只写待处理事实；外部网络调用在事务外执行。

首期按SD-10只保留本地待处理、人工登记结果及导入导出边界；在E03前不生成伪外部成功、不自动重发未知结果。BQ-09～11仍决定资金状态、公式和指标口径。

## 9. T07：导入、迁移与失败恢复

业务导入或版本化迁移能力如果被批准，固定分为四阶段：

1. 只读解析并建立包版本、声明范围和内容指纹；
2. 在不改数据的候选区完成结构、关联、权限和业务校验；
3. 展示将创建、更新、跳过和拒绝的精确对象范围；
4. 按已批准的原子范围应用，记录结果和失败原因。

候选数据不会先清理现有数据。“失败保持原状”指已声明的应用事务范围，不冒充已完成数据库灾备恢。共享或生产环境迁移仍须遵循开发规范的授权、备份、风险和恢复门槛。

## 10. T08：旧键、别名与动态属性隔离

旧Demo键只能存在于明确的导入／兼容适配器，适配器输出DOMAIN中的标准字段语义。正式业务模型不保留宽泛全局索引签名，不用`any`或未知字符串键接续业务逻辑。

每个切片开始时，将其涉及的旧键逐项分为：标准字段映射、仅导入保留、显示派生或明确排除。未分类键不进入正式DTO／Prisma模型；新发现语义先回写DOMAIN/GAPS，不由实现暗自定义。

## 13. TD-PREP-ST-FIELDS-01：结算与律师费发票字段边界

## 14. BR-006简单业务切片约束

以下形状作为后续TD-SLICE的上限约束，防止为了通用性增加用户不需要的复杂度：

- 客户创建只出现一次重复提示；同部门适用信用／证件号码精确命中直接引导打开已有客户，名称命中提供“返回／填写原因继续”两个选择，不设计合并向导。
- 历史补录使用一张表单选择目标阶段并填写真实日期、来源和原因；补到已归档时要求高风险归档补录权限，初始只授予主管模板，不产生审批任务。
- 受控动作使用同一确认模式：展示对象和影响、要求原因、直接执行并记录审计；不建设审批中心。
- 合并办理组只维护组名／成员／操作者／时间，支持解除；页面聚合读取源案，不复制字段、材料、费用或外部编号。
- 金额控件只提供“已知／待定”；已知输入非负金额，待定隐藏金额输入。0元保存后显示“无需发起”，不出现不可用的支付按钮。
- 文件只提供上传新版本、删除、恢复三类普通动作；被引用文件显示“上传新版本”，不向普通用户暴露物理清除。

这些约束不代替每个切片的错误码、并发、防重和越权测试设计，也不新增队列、工作流引擎、Redis、微服务或独立审批服务。

## 15. TD-SLICE-CU-BASE-01：客户基础

### 15.1 依据、范围与排除项

用户于2026-09-16确认按上一轮答复执行：先把客户列表、新建／编辑、判重、草稿保存、资料准入校验和详情设计到可直接判断编码准入，并保持简单易用。本切片落实[REQ-CU-001／AC-CU-001](modules/customers.md)、SD-11/12/22/28～34及REQ-XM-001/005/006的数据范围、灵活授权与回溯原则；字段语义仍引用[DOMAIN的CU01／CU02](DOMAIN.md)，不另建字段表。

本切片只包含运营端客户主档：

- 列表、名称／信用或证件号码检索、资料状态筛选和分页；
- 新建、编辑、保存草稿、保存并准入、查看详情；
- 同部门适用信用／证件号码精确重复阻断、名称重复一次提示并要求继续原因；
- 客户正式身份证明材料的引用校验、至少一位准入联系人、后端授权和业务审计。

明确排除权利主体、完整联系人管理、权利资产、协议、开票、客户统计、合作暂停／终止动作、删除、导入导出、OCR、案件入口、完整文件中心和审批流。准入只内嵌一位联系人姓名和一种联系方式，不提供联系人列表／主要联系人规则；已存在的合作状态可在详情只读展示，但本切片不提供变更动作。

### 15.2 方案比较与选择

| 方案                           | 形状                                                               | 优点                                            | 代价／结论                                     |
| ------------------------------ | ------------------------------------------------------------------ | ----------------------------------------------- | ---------------------------------------------- |
| A 单一客户Module               | 一个Module同时隐藏判重、草稿、准入、并发和审计，页面只表达保存意图 | Interface小、规则集中、最容易保持页面与后端一致 | **采用**；文件和身份只通过既有缝隙接入         |
| B 客户档案与准入拆成两个Module | 档案保存后再由独立准入模块处理                                     | 以后可扩展复杂审批                              | 当前没有审批需求，增加状态同步和页面步骤，拒绝 |
| C 通用CRUD加页面校验           | Controller／页面直接写客户并各自判断重复和材料                     | 初看文件少                                      | 并发时失效、规则散落、前端隐藏不能授权，拒绝   |

采用方案A。删除该Module会使判重、准入、版本冲突、材料校验和审计复杂度重新散落到Controller、页面及后续主链调用方，因此该Module具有足够Depth。

### 15.3 领域状态与逻辑对象

“客户资料状态”和“合作状态”是两个独立概念：

- `draft`（草稿）：至少有客户名称，可以继续补资料；不能被线索、公证或案件的正式选择Query返回。
- `admitted`（已准入）：主体类型对应的信用／证件信息、正式身份证明及最低联系人信息均通过当前准入规则；可供后续正式业务选择。准入后编辑不得破坏这些不变量，也不自动退回草稿。
- 合作中／暂停／终止继续属于合作状态。暂停／终止限制新增业务，但不替代资料准入状态；对应变更动作不在本切片。

本切片只设计以下逻辑对象，不提前固定Prisma表名：

| 逻辑对象                    | 责任与不变量                                                                               |
| --------------------------- | ------------------------------------------------------------------------------------------ |
| Customer                    | 稳定身份、部门归属、CU01字段、资料状态、只读合作状态、版本和真实时间点；名称变化不改变身份 |
| CustomerIdentityDocumentRef | 同时保存稳定`materialId`和准入实际使用的不可变`contentVersionId`；不复制文件内容或存储地址 |
| CustomerAdmissionContact    | 本切片准入所需联系人姓名及一种联系方式；不自动创建账号，不替代后续完整联系人管理           |
| Shared AuditEvent           | 复用TD-TRACE-UX统一审计事件记录客户动作；客户Module只追加／投影，不建立第二套客户审计事实  |

`normalizedName`和`normalizedIdentityNumber`是判重派生值，不是用户展示字段。第一版只做不改变业务含义的归一化：Unicode NFKC、去除首尾空白、合并连续空白；号码中的拉丁字母再转大写。不得擅自删除标点、企业类型后缀或内部字符，也不使用相似度算法。格式校验按主体和证件类型分别定义，不能把所有客户强制为18位统一社会信用代码。

精确号码唯一性限定在同一部门和适用证件类型内。共享库使用“部门＋证件类型＋归一化号码”的条件唯一约束；不开展跨部门查询、提示或自动合并，同一现实客户可在两个部门分别建档。

### 15.4 页面与操作

使用四个可直接导航的页面，不使用多步骤向导或通用动态表单：

| 页面                  | 最小内容                                                                                   | 交互结果                                                             |
| --------------------- | ------------------------------------------------------------------------------------------ | -------------------------------------------------------------------- |
| `/customers`          | 名称／信用或证件号码搜索、资料状态筛选、20条分页；名称、号码、资料状态、合作状态、更新时间 | 默认按`updatedAt desc, id asc`稳定排序；加载、空、失败、取消分开显示 |
| `/customers/new`      | CU01表单、准入联系人和身份证明材料引用                                                     | “保存草稿”允许资料不齐；“保存并准入”执行完整准入校验                 |
| `/customers/:id/edit` | 同一表单、版本和已有材料引用                                                               | 保存时提交`expectedVersion`，冲突后重新加载，不静默覆盖              |
| `/customers/:id`      | 客户身份、资料状态、合作状态、当前身份证明和更新时间                                       | 草稿显示明确提示；仅有权限时显示编辑入口                             |

首次提交时若仅名称命中，页面在表单内展示命中摘要和“返回修改／填写原因继续”两个选择；填写原因后再次提交，同一轮不弹出第二个确认框。同部门适用信用／证件号码命中时不允许继续创建，展示“打开已有客户”。并发冲突时页面重新执行判重Query，不能把409当作普通字段错误吞掉。

### 15.5 Customer Module Interface

Module外部只暴露一个写Interface和三个读Interface；Controller、页面和后续主链调用方不自行复制判重或准入规则：

```text
saveCustomer(
  CommandContext,
  customerId? + expectedVersion? + intent(draft|admit)
  + customerType + name + identityType? + identityNumber?
  + issuingCountryOrRegion? + category? + region?
  + admissionContact? + identityDocumentIds[] + duplicateNameReason?
) -> CustomerSummary + version

listCustomers(QueryContext, query? + profileStatus? + page + pageSize)
  -> items + total + page + pageSize + capabilities(createDraft)
getCustomer(QueryContext, customerId) -> CustomerDetail + sharedAuditHistory
findCustomerDuplicates(QueryContext, name + identityType? + identityNumber? + excludeCustomerId?)
  -> exactIdentityNumberMatch? + sameNameMatches[]
```

`saveCustomer`在Module内部区分创建和编辑，并根据`intent`执行草稿或准入规则；调用方不需要学习两套写入顺序。文件Module的读取Interface和身份适配Adapter是其依赖，不并入Customer Module的公开Interface。

### 15.6 HTTP与OpenAPI映射

| 方法与路径                         | Module Interface         | 关键输入／结果                                                             |
| ---------------------------------- | ------------------------ | -------------------------------------------------------------------------- |
| `GET /api/v1/customers`            | `listCustomers`          | `query`、`profileStatus`、`page`、`pageSize`；返回分页结构与服务端动作能力 |
| `GET /api/v1/customers/duplicates` | `findCustomerDuplicates` | `name`必填，代码和排除身份可选；只返回当前数据范围内最小摘要               |
| `POST /api/v1/customers`           | `saveCustomer`           | 新建；`intent`为`draft`或`admit`；接受`Idempotency-Key`                    |
| `GET /api/v1/customers/:id`        | `getCustomer`            | 越范围与不存在均返回404；范围确认后投影可见的共享审计历史                  |
| `PATCH /api/v1/customers/:id`      | `saveCustomer`           | 编辑；`expectedVersion`必填，省略字段表示不修改                            |

DTO拒绝未知字段；部门、角色、操作者、资料状态、合作状态、版本和审计字段均不得由前端伪造。写响应返回当前版本和详情链接，不返回Prisma实体。`findCustomerDuplicates`只为交互提示，`saveCustomer`仍须在事务内重新校验。

### 15.7 写入顺序、并发与防重

`saveCustomer`遵守T02并进一步固定为：

1. 从可信`ActorContext`校验完整Grant和部门范围；创建时部门来自服务端活动部门，不来自请求体。
2. 归一化名称／证件号码；编辑时锁定目标部门并核对`expectedVersion`。
3. 在同部门查询同证件类型的精确号码和名称。号码命中立即返回冲突；名称命中且无继续原因则返回冲突；有原因时记录审计事件。
4. `intent=admit`时，按客户类型校验最低主体字段、准入联系人、文件访问权和全部准入字段；逐份校验选定`contentVersionId`属于目标`materialId`、当前可用且类别匹配，并把该精确版本冻结为本次准入依据。普通任意附件不得自动算正式证件。
5. 单一PostgreSQL事务内写客户、材料关联、版本和审计索引。创建依靠唯一约束兜住并发，数据库冲突映射为稳定业务错误。
6. 相同创建`Idempotency-Key`和相同请求指纹返回原结果；同键不同指纹返回409。PATCH不自动重试，版本冲突交给用户确认新数据。

草稿创建也执行已填写证件号码的部门内唯一校验，避免先建重复草稿再准入。已准入客户编辑时若清空必需号码、移除全部有效身份证明／准入联系人或把关联文件变为无效，整个写入拒绝，原数据保持不变。

### 15.8 权限、材料和审计

Customer Module使用动作名`customer.read`、`customer.create-draft`、`customer.edit-routine`、`customer.correct-identity`和`customer.admit`调用授权策略。默认模板为运营管理本人、小组长管理／准入本团队、主管管理／准入本部门；关键身份更正默认仅主管，但模板可由有权管理员调整。Query在数据库读取时施加范围；详情404不区分“不存在”和“存在但越范围”。前端路由守卫及按钮隐藏只改善体验，不承担授权。

| 初始模板 | 建草稿 | 日常编辑 | 正式准入 | 关键身份更正 | 默认读取范围 |
| -------- | ------ | -------- | -------- | ------------ | ------------ |
| 运营     | 允许   | 本人负责 | 不允许   | 不允许       | 本人负责     |
| 小组长   | 允许   | 本团队   | 本团队   | 不允许       | 本团队       |
| 主管     | 允许   | 本部门   | 本部门   | 本部门       | 本部门       |

新建时默认创建人为负责人；转派后按新负责人重新计算范围，不保留永久创建人访问权。系统管理员默认无客户业务Grant，律师只通过案件授权读取必要客户摘要和材料，不因此获得客户库权限。

身份证明通过T05文件缝隙引用。Customer Module接收稳定`materialId`与明确`contentVersionId`，验证该内容版本属于目标材料、状态可用、格式／大小和目标类型符合准入规则、调用者有权访问且绑定当前客户上传草稿。准入记录冻结实际采用的内容版本；之后上传V2不会把历史准入依据从V1静默替换。被流程引用的版本不得由普通用户物理清除；材料可上传新版本并按规则作废旧版，物理存储位置、下载凭据和正文不进入客户数据或日志。

审计至少产生`customer.draft-created`、`customer.updated`、`customer.admitted`和`customer.duplicate-name-overridden`。同名继续原因是业务审计内容；普通编辑不要求统一填写原因。本切片不新建审计中心页面，先保留后端可追踪事实。

### 15.9 稳定错误

| HTTP | code                            | 页面处理                                                 |
| ---- | ------------------------------- | -------------------------------------------------------- |
| 400  | `VALIDATION_ERROR`              | 标记无效DTO字段，不推断业务状态                          |
| 403  | `CUSTOMER_ACTION_FORBIDDEN`     | 停止操作；不得靠隐藏按钮代替后端检查                     |
| 404  | `CUSTOMER_NOT_FOUND`            | 返回列表或提示记录不可访问                               |
| 409  | `CUSTOMER_IDENTITY_DUPLICATE`   | 重新查询本部门命中摘要并提供打开已有客户入口             |
| 409  | `CUSTOMER_NAME_REASON_REQUIRED` | 显示一次同名提示和继续原因输入                           |
| 409  | `CUSTOMER_ADMISSION_INCOMPLETE` | 保留表单，列出缺少的准入字段／材料类别                   |
| 409  | `CUSTOMER_DOCUMENT_INVALID`     | 标记失效、越范围或类别不符的材料，不把上传成功当准入成功 |

## 16. TD-AUTHZ-01：可配置角色与案件成员授权

### 16.1 模块边界与接口

采用一个后端Access Control Module集中解释角色模板、角色分配、Grant、组织归属和资源成员；业务Module仍拥有自己的阶段、材料和状态守卫。Controller、页面和业务服务不得自行用角色名称拼授权。

```text
authorize(ActorContext, action, ResourceFacts) -> Allow | Deny + reasonSource?
buildQueryScope(ActorContext, action, resourceType) -> database predicate
explainAccess(ActorContext, action, resourceId) -> safe grant sources

saveRoleTemplate(CommandContext, template + grants + expectedVersion)
assignRole(CommandContext, user + department + template + validity?)
setCaseMembership(CommandContext, case + user + preset(read|handle) + validity?)
transferResponsibility(CommandContext, resourceIds[] + newResponsible + reason)
```

`action`来自随代码版本发布的固定权限目录；设置页只能选择已有项。`buildQueryScope`必须返回可用于数据库查询的约束，不能先读全量再过滤。模板和分配写入使用乐观版本及审计；批量转派返回逐项结果，不因一个越权对象扩大整批范围。

### 16.2 两个管理入口

- “系统设置→人员与权限”：当前切片直接维护人员账号、当前部门成员、Team和已有角色分配；日常启停、调队、重置密码与撤权／恢复自动审计，不要求人工填写原因或重复验证管理员密码。模板复制／修改、Grant编辑和影响预览另开切片。
- “案件详情→成员与权限”：调整负责人、律师、只读／办理协作成员。这里不能编辑角色模板，也不能把“办理”扩成合并、终止、归档、导出或证件下载。

### 16.3 授权顺序与不变量

1. 认证层解析稳定账号并确认未停用、会话与`authorizationRevision`有效。
2. 依据服务端活动部门读取组织归属、角色分配和目标资源事实；拒绝客户端伪造部门、负责人或成员。
3. 查找单个同时满足`action`和`scope`的Grant，或适用的资源成员预设；不存在即拒绝，不合并扩大范围。
4. 业务Module继续验证阶段、材料、金额和其他业务门槛；权限通过不等于业务动作必然成功。
5. 成功动作与授权来源、业务结果分别审计；授权变更提升版本并使下一请求按新配置判定。

被撤销案件成员如果仍有部门角色授权，访问仍可成立，`explainAccess`只返回“部门角色”等安全来源，不返回其他部门对象。被更换律师按SD-25只读参与期内容；账号停用优先于全部角色和成员授权。系统管理员只承担技术管理动作，默认不获得客户或案件内容权限。

### 16.4 安全验收

| 场景                    | 预期                                                               |
| ----------------------- | ------------------------------------------------------------------ |
| 两项Grant动作／范围不同 | 不拼接为更宽权限；越权写入403，列表和详情不泄露目标                |
| 同一人员两个部门角色    | 只在明确活动部门和对应角色范围内访问，切换不能复用另一部门查询缓存 |
| 修改角色模板／撤销成员  | 保存后的下一请求按新权限判定；旧页面继续保存／下载被拒绝           |
| 自我提权／超上限授予    | 拒绝并审计，不因管理页面可见而放行                                 |
| 负责人批量转派          | 每个对象分别校验范围，历史负责人和操作记录保留                     |
| 成员撤销但角色仍授权    | 仍可访问并能解释有效来源；不得错误显示“无权限”或暴露其他授权详情   |
| 账号停用                | 旧会话失效，角色和成员均不能恢复访问                               |
| 文件查看／下载／导出    | 三类动作分别验证，不因可查看案件自动取得证件下载或批量导出         |

该范围涉及认证、租户隔离和敏感证件，按Q2门禁必须在实现前接受独立安全设计复核，在合并前以真实PostgreSQL执行跨部门、撤权、缓存和并发越权测试。本轮没有产生实现或可执行测试。

### 16.5 Team完整性与Grant Boundary最小收口

- `Team`只表达部门直属团队，包含稳定ID、不可变部门、名称、ACTIVE／INACTIVE和时间戳；不增加编码、层级、虚拟组织或物理删除。数据库触发器拒绝改变Team部门，`DepartmentMembership`、`RoleAssignment`、`Customer`通过`(teamId, departmentId)`组合外键引用同部门Team。
- 停用Team保留成员、角色和客户历史引用；现有客户可按原权限继续维护。新成员绑定、新角色绑定、恢复旧绑定和新客户绑定必须使用ACTIVE Team，防止产生新的停用引用。
- 管理动作固定为`user.read`、`user.manage`、`team.read`、`team.manage`、`role.read`、`role.assign`。它们与客户动作一样只能经服务端Grant放行，不承认首位管理员、角色名称、用户名、固定ID或前端可见性为授权来源。
- 角色分配的授予上限同时校验操作者的`role.assign`是否覆盖目标成员，以及待授角色每个Grant是否被操作者同Action的当前有效范围覆盖。DEPARTMENT只覆盖同部门；TEAM只覆盖同一目标Team的TEAM范围；SELF只属于原主体，不能向他人转授；TEAM也不能推导目标成员未来SELF数据。没有业务不变量证明包含关系时默认拒绝。
- Team新建／启停要求DEPARTMENT `team.manage`；SELF不适用于Team主数据。TEAM Grant仅在操作者当前成员Team为ACTIVE且分配Team一致时有效；任何活动且绑定Team的角色分配都必须先处理，成员才能调队。
- 管理变更在可串行化事务内重读操作者账号、成员、授权修订和Grant，并按固定顺序锁定部门授权序列及账号、成员、角色、Grant、Team和分配行；客户新建在写事务内共享锁定Team并重检ACTIVE。角色分配成功与审计、目标账号授权修订递增同事务提交，失败整体回滚。
- `PermissionAction`枚举扩展与Team建模分为两个有顺序依赖、各自显式事务化的前向迁移，因为PostgreSQL新增枚举值需先提交后才能用于Grant回填。第二迁移锁定引用表，先建立兼容Team与确定性映射，再建立组合外键；原`NULL`不回填。只有满足既有引导账号结构特征且角色未被其他账号共享的唯一关系获得六项管理Grant，不按角色名称批量升级。

本收口原先不提供管理HTTP或页面；PERSONNEL-ACCESS-001现已在不改变schema和权限目录的前提下补齐`OrganizationService`事务边界、`/api/v1/organization`管理接口及`/settings/people-access`工作区。创建账号、凭据、当前部门成员、初始角色与成功审计共享一个可串行化事务；账号或成员停用、密码重置和角色变化递增授权修订并撤销适用会话。角色模板编辑、跨部门全局账号管理以及Lead、Case、File、Fee、Settlement或Report仍不在本切片。

## 17. TD-TRACE-UX-01：低负担回溯与原页面易用性

### 17.1 选择与边界

采用“**业务事实与审计事件同事务写入，原详情页读取历史投影**”的最小方案。它复用模块化单体、PostgreSQL、Access Control Module和File Adapter，不采用事件溯源，不新增审计微服务、通用工作流、审批中心、万能配置平台、独立工作台或第二套财务／任务台账。

写入时，业务表仍是当前状态的权威来源；同一事务追加不可由普通业务人员编辑的审计事件。读取时，Query按现有资源权限把相关事件投影为原详情页可折叠的“历史记录”。审计写入失败则业务事务整体失败，避免“业务成功但没有历史”；读取投影暂时失败不回写业务事实。

### 17.2 自动审计与三类时间

统一审计事件最少包含：事件身份、对象类型与身份、动作代码、操作者、系统记录时间`recordedAt`、适用的业务发生时间`occurredAt`、更正时间`correctedAt`、前后版本、关键字段差异、材料内容版本身份、请求／幂等身份及授权来源摘要。敏感证件正文、完整个人信息和文件内容不复制进审计；差异只保留必要字段、脱敏值或稳定引用。

- `occurredAt`表达业务实际发生时间，可由获准动作填写；普通实时操作可由服务端以当前时刻确定。
- `recordedAt`始终由服务端产生，不接受客户端覆盖。
- `correctedAt`在更正成功时追加记录；原`occurredAt`、原值和原事件保留，不原位抹去。
- 只有既有规则要求原因的历史补录、关键更正、转派、撤销、合并等动作继续要求原因；普通编辑不新增原因弹窗。
- 普通业务账号无审计修改／删除动作。读取历史与读取目标资源使用同一数据范围，不能借历史接口看到当前无权查看的材料、人员或其他部门对象。

概念接口如下，名称供后续切片保持一致，不表示本轮已创建代码：

```text
appendAuditEvent(transaction, actor, action, before, after, exactMaterialVersionIds)
getResourceHistory(QueryContext, resourceType, resourceId, cursor) -> permission-scoped events
getActionReadiness(QueryContext, resourceType, resourceId, action?) -> missing + conflicts + sourceRules
getPrefillCandidates(QueryContext, source, targetAction) -> uniqueExplicitValues
```

`appendAuditEvent`只能由业务Command在事务内调用，Controller和页面不能直接伪造事件。`getActionReadiness`只解释已确认门槛，不建立新的状态机；最终提交仍由业务Command重新校验。

### 17.3 材料身份、内容版本与清理

材料使用稳定逻辑身份`Material`与不可变内容版本`ContentVersion`分层；“当前版本指针”只服务当前查看，业务历史引用直接保存`contentVersionId`。上传V2后，此前阶段动作、账单、发票、权利依据或授权仍打开V1。每个版本自动保存上传人、上传时间、原文件名、真实MIME、大小和完整性校验值；裁剪、标注、格式转换等派生件保存`derivedFromVersionId`，不覆盖原件。

清理Command必须同时满足：可恢复期限已届满、没有业务精确版本引用、没有争议／调查等保留标记、操作者拥有技术清理权限，并在清理前后审计。90天届满本身不等于可清理；业务管理员不因有删除权获得技术清理权或正文查看权。校验值用于发现内容变化，不被描述为来源真实性证明。

文件预览与下载只暴露应用层`FileAccessGateway`。客户端不获得永久对象存储地址；每次兑换一次性、短时应用凭证时，网关依据目标材料、动作、范围和当前`authorizationRevision`重新授权，再代理读取内容。权限撤销后，未兑换凭证和新请求均失败；已经下载到个人设备的副本不能由系统追回。

### 17.4 权限覆盖与异步导出

`buildQueryScope`统一用于列表、详情、搜索、统计、材料预览／下载、导出、合并组聚合和后台任务。搜索命中数、统计总数、摘要、联想词和缓存键均在授权范围内计算，禁止先读全量再隐藏行。不同Grant不能拼接扩大动作范围，合并办理组也不继承或传播源案权限。

异步导出分两次授权：任务执行前按当前权限固定可导出资源集合；用户领取结果前再次核验导出动作、数据范围和`authorizationRevision`。任一时点权限已撤销则拒绝执行或领取，导出产物按短期私有材料管理。旧律师的时间边界同时限制业务事件和材料版本：只读其参与期间有权范围内的版本，不自动看到离场后新增内容。

### 17.5 原页面就地办理

- **自动带入**：仅从唯一、明确且当前有权读取的客户、主体、权利、案件或负责人关系带入；不猜客户、主体、金额、期限，不覆盖用户已修改的字段，也不新增强制“确认带入”弹窗。
- **上传**：保留原单文件入口，同时允许可选多文件拖放；每个文件独立显示进度、结果、预览和重试，沿用当前业务对象及现有材料分类。单文件失败不要求全部重传。
- **校验与缺件**：基于相同业务守卫在原表单字段旁或详情缺件区显示，只检查当前动作已确认的门槛，能定位到原输入位置。提交失败保留表单值；后端仍是最终权威，不要求预填未来阶段资料。
- **冲突与重试**：正常保存保持一次点击、不新增确认；相同幂等请求返回原结果，版本冲突才显示具体差异并阻止静默覆盖。
- **检索**：在原列表增强案件号、客户名称、平台／店铺和有权材料名称检索；个人保存筛选是可选偏好，激活时显示清晰条件并支持一键清除，不能让用户误以为数据消失。
- **下一步与提醒**：只从当前阶段、已确认门槛、来源日期和未完成任务派生，在原案件详情或日历／待办入口展示。相同来源去重；转派时未完成事项随责任人更新。案件阶段、材料齐备、任务和财务状态继续分开，不猜截止日期，不成为第二套流程。

### 17.6 权利、合并、费用与报表补强

- 客户、权利主体、具体权利、维权授权和案件／行动使用稳定引用串联，业务记录冻结实际使用的权利及授权材料版本。到期或委托方不匹配在原页面提示；是否阻断只按已批准规则，不因客户已准入自动推导授权有效，也不另建权利资产平台。
- 合并办理组只记录成员前后集合并从源案聚合；按稳定身份去重、逐案校验授权，解除后原案事实不变。进入组不产生查看全部源案的权限。
- 退款／冲销引用原支出并在同一事务内锁定或以版本条件校验累计退款；网络重试不重复记账。保留“已知／待定”、0元和现有公式边界，不建立第二套财务台账。
- 报表保持原入口、列和已批准指标；发布／归档结果记录生成时间、筛选期间、指标定义版本、导出人和精确文件版本，与当前实时重算分开。导出执行和领取都使用当前数据权限，不建设数据仓库或历史重算平台。

## 19. TD-SLICE-CU-RH-01：客户与权利主体最小关联

### 19.1 依据、范围与排除项

### 19.2 方案比较与选择

| 方案                                 | 形状                                                        | 优点                                                        | 代价／结论                                                   |
| ------------------------------------ | ----------------------------------------------------------- | ----------------------------------------------------------- | ------------------------------------------------------------ |
| A 客户锚定的独立主体记录与关联Module | 独立稳定主体记录＋客户—主体关联；所有本轮读写从有权客户进入 | 保留多对多和稳定身份，可在小Interface内集中隔离、并发及审计 | **采用**；共享主体编辑另开切片                               |

### 19.7 事务、并发、审计与稳定错误

两个写Command都先锁定／条件更新目标客户版本，再在一个PostgreSQL事务内完成主体或关联、客户版本递增和共享审计。创建主体同时追加`rights-holder.created`和`customer.rights-holder-linked`两个不同事实；关联已有主体只追加后者。审计只保存稳定身份、操作者、时点和必要动作信息，不复制名称、信用代码、地址或法定代表人等正文。

同一`Idempotency-Key`与相同请求指纹返回原结果，同键不同指纹返回`IDEMPOTENCY_KEY_REUSED`。两个请求并发关联同一客户—主体时，组合唯一约束保证只产生一个关联；非重试的第二次显式关联返回`RIGHTS_HOLDER_ALREADY_LINKED`。客户版本已变化返回`CUSTOMER_VERSION_CONFLICT`，不静默覆盖。主体创建、关联、客户版本或任一审计写入失败时全部回滚。

| ---- | ------------------------------ | -------------------------------------------------------------- |
| 400  | `VALIDATION_ERROR`             | 保留表单并标记无效字段；名称必填，其余CU03字段可空             |
| 403  | `CUSTOMER_ACTION_FORBIDDEN`    | 当前客户可读但无日常编辑Grant时停止写入                        |
| 404  | `CUSTOMER_NOT_FOUND`           | 目标客户不存在或越范围，返回客户列表                           |
| 404  | `RIGHTS_HOLDER_NOT_FOUND`      | 主体不存在、不可见、跨部门或未与当前详情客户关联，均不枚举原因 |
| 409  | `RIGHTS_HOLDER_ALREADY_LINKED` | 刷新当前客户主体列表，不重复创建关联                           |
| 409  | `CUSTOMER_VERSION_CONFLICT`    | 重新加载客户详情后由用户重新选择是否提交                       |

本切片仅包含受控命令创建首个账号、用户名／密码登录、会话恢复、退出、CSRF／登录限速及前端登录页；不开放注册，不实现日常建号／禁用／重置、权限管理页面、MFA、找回密码、OIDC或生产部署。完整模型、接口、安全边界和Q2验收见[系统自有账号认证设计](../../superpowers/specs/2026-09-17-local-account-auth-design.md)。该切片现已完成schema、迁移、接口、页面、数据库型Playwright、隔离复审和内部集成；范围外能力仍须另开切片。
