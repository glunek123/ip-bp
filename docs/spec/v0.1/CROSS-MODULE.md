# 跨模块目标与责任边界

字段定义只见[领域模型](DOMAIN.md)，新增决定见[SD](DECISIONS.md)，原BD见[固定决定](../../demo-reverse/v158/DECISIONS.md)。通用技术设计、权限及回溯易用性基础见[TD-BASE-05／TD-AUTHZ-01／TD-TRACE-UX-01](TECHNICAL-DESIGN.md)。系统自有账号、客户域最小Grant／部门隔离和客户—权利主体关系已有API、代码、迁移及正式测试；下列AC只有明确引用这些证据的子范围已执行，其余仍是目标场景。

## REQ-XM-001 身份、四端和数据范围

- 状态：确认方向（INPUT-001、SD-03/04/13/24/25/28/31/33/39）；客户域授权与系统自有账号子集已内部集成，案件域及外部端仍待开发。公证处、律师、客户是外部业务身份；运营体系的主管／小组长／运营是可编辑初始角色模板。
- 同一系统服务知产和品维，部门业务数据不互通；存在运营、律师、公证处、企业客户端四类入口，不从Demo导航推导四套已实现应用。
- 案件初始模板按SD-39拆分：普通运营读取和逐件下载附件限本部门，普通写动作限本人当前负责案件；小组长、主管及其他动作仍按明确Grant和SD-24动作矩阵。实际请求按当前有效的“操作权限＋数据范围＋资源成员”计算，不直接比较职位名称，也不得把部门读取与本人写入拼接提权。被更换律师只读其参与期间案件／材料；客户、公证处及账单／发票端范围继续按SD-13，导出仍由独立权限控制。
- 用户已经确认的隔离方向约束读写和统计设计；前端隐藏不能作为授权控制。权限错误不得泄漏其他部门的关联对象、材料或统计。
- 依赖：T03/E01/E03/DD-10；SD-33已选择共享库／共享表按部门强隔离。多对多和合并办理组不授予跨部门访问，文件查看、下载和导出分别授权。
- AC-XM-001：给定两个部门、部门甲两个团队以及默认模板人员；普通运营可读取部门甲全部案件和获准附件，但只能办理本人负责案件，不能读取部门乙案件；小组长、主管的办理范围继续按其有效Grant判断。给同一人员明确增加部门乙角色后才可按该角色访问部门乙。系统自有账号认证和客户域越权测试已实现，案件域尚未实现。

## REQ-XM-005 可配置角色、数据范围与资源成员

- 状态：确认方向（SD-28/29/31/33）；[TD-AUTHZ-01](TECHNICAL-DESIGN.md)已设计，客户首批最小Grant／部门隔离和系统自有账号认证已通过内部数据库、浏览器及隔离Q2验证；人员／角色管理、未来OIDC／MFA和其他业务域授权仍未完成。字段组：AC01～06。
- 角色模板可编辑／复制，人员可按部门分配不同角色；每项授权同时绑定操作权限和数据范围。案件负责人、律师和协作人员使用资源成员授权，普通协作只提供“只读／办理”预设，办理不默认包含合并、终止或归档。
- 授权引擎只在单个有效授权同时覆盖目标操作与对象范围时放行；不能把“本部门查看”和“本人编辑”拼成“本部门编辑”。未明确授权默认拒绝，权限管理者不能授予超过自身可授予范围的权限或自我提权。
- 角色、分配、负责人和案件成员变更从下一次后端请求起生效，必要时提升授权版本并使旧会话失效；历史操作者和成员记录不改写。移除成员后如仍由其他角色获权，访问解释应显示其有效来源。
- 权限配置仅选择代码已实现的动作和范围，不能绕过状态、材料、合并、归档、金额等业务守卫，也不建设通用策略语言或工作流引擎。
- AC-XM-005：给用户甲授予“查看本部门”和“编辑本人负责”两项，再尝试编辑同部门他人案件；随后为单案加入“办理”成员、撤销成员并变更角色模板。预期不能拼接成部门编辑；单案授权保存后下一请求生效，撤销后下一请求失效；若仍由其他角色可访问，解释返回该来源；全部变更有前后值、操作者和原因。

## REQ-XM-002 客户与权利主体关系

- 状态：确认方向（SD-01/11/22）。字段CU01/CU03/LD01/CA01。
- 客户和权利主体分别识别，可建立多对多关联且可为同一主体；每条线索和案件选择一个客户与一个权利主体。同部门适用信用／证件号码精确相同阻断客户重复创建；仅名称相同提示并要求继续原因；不自动判重权利主体。
- 所选主体须属于所选客户的有效关联；无证件客户草稿不能进入正式线索／取证／案件。关系结束后存量继续至案件全结，随后按[历史关系留存](CONTEXT.md)保留只读关系事实，不因删除关联静默换掉历史主体；这不要求敏感证件正文或个人信息永久保存。
- 依赖：B05/T01/T03；SD-33已定客户档案和精确判重按部门独立。
- AC-XM-002：在同一获准范围内，客户甲关联主体P/Q，客户乙关联主体P；分别为甲/P、乙/P创建线索。预期共用主体关系可表达，每条仅一个客户和主体，甲/Q不被误改；尝试一案选两主体应不符合已确认基数。

## REQ-XM-003 主链移交和来源保留

- 状态：确认方向（BD-01/03/12、SD-02），其他转换条件待审核。字段LD06/NT01/CA12/FE01/MT01。
- 明确新取证批次可使同一线索关联多个公证事项；原线索保留只读。来源线索、各批次、公证转案与合并归档的关系分开，不按店铺或展示串猜配。
- 合并办理组按SD-27只聚合源案；不新建替代主案或归档壳，不移动材料／费用。BD-03原“合并原案公证归档”方向由本次更具体决定替代；公证转案费用仍保留同笔来源，不复制成新的财务指令。
- 重复点击／网络重试与明确创建新批次是不同意图，T02设计防重复机制；BQ-03决定批次撤销、更正和可变内容；合并组可解除，材料生命周期按SD-25。
- AC-XM-003：线索L第一次移交产生公证N1后只读，再明确新建第二取证批次N2。预期N1/N2均能追溯L，L未被覆盖或删除，不能把同一次请求重试冒充用户授权新批次；防重具体方案未设计。

## REQ-XM-004 批量写入必须明确选择

- 状态：确认方向（SD-07/08）；适用于批量推送、立案、归档、费用发起、合单等业务写入；字段为所选业务身份集合，不新增业务表。
- 未选择对象时不执行，提示先选取；操作前展示实际选中范围，不能无勾选隐式处理全库或当前筛选结果。用户主动全选属于明确选择，但须说明全选范围。
- 混合状态、并发变更、部分成功和重复请求由T02按统一业务校验与可观察结果设计；本决定不改变只读导出的范围约定。
- AC-XM-004：筛选显示2条而全库5条，无勾选执行批量推送／立案／归档／费用发起／合单。预期全部不写数据并提示选择；明确选中其中1条后预览只包含该条，不能隐含另4条。

## REQ-XM-006 低负担回溯与就地办理

- 状态：设计约束已确认（INPUT-013、SD-34）；[TD-TRACE-UX-01](TECHNICAL-DESIGN.md)已设计，Q2安全复核、实现及运行验证未产生。
- 现有新建、普通修改、阶段变化、转派、律师变更、合并／解除、删除／恢复和退款等动作在同一事务中自动形成业务历史事件，记录操作者、系统时间、业务对象、关键前后变化及实际使用的材料版本。普通编辑不新增原因弹窗；审计记录不可由普通业务操作改删，并按目标资源的数据范围读取。
- 业务发生时间、系统录入时间和后续更正时间分别保留；材料历史引用指向具体内容版本，上传新版不覆盖旧依据。上传自动保留上传人、时间、原文件名、校验值和原件／派生关系；未知来源不补造。
- 历史、缺件、冲突、下一步和提醒在原列表、表单、详情或日历中就地展示。系统只从唯一明确关系带入已知信息，不猜客户、主体、金额或期限，也不覆盖已经人工修改的字段；阶段、任务、材料齐备程度和资金状态继续分别表达。
- 列表、详情、搜索、统计、文件预览／下载、导出、合并组聚合及后台任务使用同一授权语境，结果数量、摘要和缓存不得泄漏越权资源。权限撤销后，新请求、导出执行／领取和未兑换下载凭证均重新校验；已经下载到个人设备的副本不能由系统追回。
- 正常新建、文件上传、阶段办理和费用录入的新增必填字段、必经页面和强制确认均为0；可选多文件上传、保存筛选、单文件重试和历史折叠区不得妨碍原单文件及单步操作。
- AC-XM-006：给案件阶段动作引用材料V1后上传V2，并以历史业务日期补录、更正一次；随后撤销参与律师权限，尝试搜索、预览、下载、领取导出及访问合并组。预期历史仍打开V1并分别显示业务／录入／更正时间；撤权后的所有新入口均按当前有效授权拒绝且不泄漏数量；正常办理未新增必填字段、页面或确认。再重试同一提交及并发退款，预期不重复创建业务事实且累计退款不超过原支出；备份恢复验收须保持业务记录、材料版本和审计关联一致。
