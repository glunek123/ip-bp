# CORE-LD-007 不侵权归档撤回纠错设计

状态：SD-40 所述“运营申请、原客户企业确认”已由用户确认；本设计只把该边界落成可实现、可验收的最小契约。依据为 REQ-LD-003、SD-38／40、[核心业务字段与材料契约](2026-09-21-core-flow-field-material-contract.md)以及 CORE-LD-003／004 的真实身份、审核决定和回执实现。

## 目标与排除

运营人员对仍处于 `ARCHIVED`、当前有效结论为 `NO_INFRINGEMENT` 的线索说明原因并申请撤回。申请成功只写入待确认事实，线索继续归档、原决定继续有效。原客户企业的当前有效获权账号确认后，线索才原子回到 `WAITING_REVIEW`；客户可再次作出正常侵权或不侵权决定。原决定、归档事实、申请、确认和每轮回执均保留。确认人不必是原审核的个人账号。

不实现客户自行发起、运营单方生效、驳回／取消申请、批量撤回、其他归档类型的重开、普通编辑、取证／公证／案件撤回或通用工作流。一次原决定只允许一份待确认申请；本切片没有驳回／取消动作，因此不能以换键反复申请同一决定。

## 方案选择

1. **线索当前决定指针＋不可变历史（采用）**：`Lead.activeReviewDecisionId` 仅是当前投影指针；既有 `LeadReviewDecision` 转为一对多且始终不可变。前向迁移回填旧决定指针、移除一对一唯一键，并用组合外键证明指针所指决定属于同一线索、客户和部门。撤回确认清空指针，下一次客户审核写新决定并设置指针。两份不可变撤回事实分别记录申请和确认，既有旧审核回执保持原样。
2. **改写旧决定的 `revoked` 标志（不采用）**：破坏既有不可变决定契约，历史和回执难以核对。
3. **仅按最新时间推导当前决定（不采用）**：跨轮次查询、附件范围和将来的其他归档类型会依赖时间排序猜测，无法用外键锚定当前事实。

## 数据与迁移

- `LeadReviewDecision.leadId` 改为非唯一，保留 `(id, leadId, customerId, departmentId)` 组合身份约束以及旧回执到决定的组合外键；新增每线索／轮次版本唯一性。旧 `LeadReviewDecision`、`ClientLeadReviewReceipt`、归档原因与时间原样保留，旧线索的当前决定指针在迁移中按唯一旧决定回填。
- `LeadWithdrawalApplication` 保存原决定 ID、线索／客户／部门、申请人、1～5000 Unicode 码点的规范化原因、服务端申请时间、版本前后、幂等键、指纹和首次响应快照。`(originalDecisionId, leadId, customerId, departmentId)` 必须以组合外键引用同一审核决定；原决定 ID 唯一；内部申请人必须为当前部门成员，申请事实不可更新／删除。申请成功另写内部成功审计。申请使 `Lead.version + 1`，不改变 `ARCHIVED`、当前决定或归档时间。
- `LeadWithdrawalConfirmation` 保存申请 ID、原决定 ID、线索／客户／部门、确认客户账号和当时有效的企业绑定、服务端确认时间、版本前后、幂等键、指纹及首次响应快照。`(applicationId, originalDecisionId, leadId, customerId, departmentId)` 必须以组合外键引用同一申请，绑定也须以 `(bindingId, actorUserId, customerId, departmentId)` 组合外键锚定该企业。每申请至多一份确认；确认事实不可更新／删除。该不可变事实本身是外部客户确认审计，不强行写入只接受内部部门成员的通用 `AuditEvent`。
- 申请和确认使用各自动作域内的 `(departmentId, actorUserId, idempotencyKey)` 唯一键；约束、触发器及前向迁移必须兼容空库和上一支持 schema。不得修改已执行迁移、删除旧决定／回执或重写其响应快照。

## Command、权限与错误

运营入口 `POST /api/v1/leads/:id/withdrawal-applications`：`{reason, expectedVersion}` 和 `Idempotency-Key`。新增内部 `lead.withdraw.apply` Action，只能由当前 Grant 覆盖目标线索的内部成员申请；管理员模板按现有受控升级方式获得该 Action，其他角色须显式授权。服务端锁定线索，核验部门／范围、当前 `ARCHIVED`、有效不侵权决定、尚无申请及版本，在 Serializable 事务中增加版本、写不可变申请、成功审计和幂等快照。旧键同请求先重验当前操作者授权后返回旧结果；异参冲突。申请成功不改变客户审核结论。

客户入口 `POST /api/v1/client/leads/:id/withdrawal-confirmations`：`{applicationId, expectedVersion}` 和 `Idempotency-Key`。`client.lead.withdraw.confirm` 是固定客户能力，不可分配给内部角色。事务内先重读当前 CLIENT 账号、有效绑定与 ADMITTED 客户，锁定同企业已推送线索，核验申请仍未确认且指向当前有效不侵权决定、状态仍归档及版本；随后清空当前决定指针、把状态设为 `WAITING_REVIEW`、增加版本、写不可变确认及幂等快照。客户不能选择或修改申请原因，也不能确认其他企业申请。旧键重放仍须当前身份／绑定有效，不重复推进或审计。

客户普通 `POST /client/leads/:id/reviews` 保持原请求、指纹、响应和旧回执兼容；只对当前 `WAITING_REVIEW` 且无有效决定的线索写新一轮决定、设当前指针并增加版本。旧审核键可返回其原始成功快照，但不能改变当前轮次。不同键竞争仅一次提交；旧版本、错误状态、无权限、跨企业与故障回滚沿用现有稳定错误码／不泄漏存在性的边界。

## 读取、附件和页面

- 双端列表及详情用当前决定指针解释业务状态，不以“曾经存在不侵权决定”使已撤回的线索仍显示为归档。详情另提供该线索全部审核决定、申请和确认历史，按各事实的版本转换顺序、同版本时按 ID 稳定排序；客户端只返回本企业可见字段，运营仍受 `lead.read` 范围限制。截图权限继续锚定当前企业、推送事实和精确材料版本，不因历史决定扩大范围。
- 运营详情只有服务端下发 `withdrawApply` 能力时显示“申请撤回归档”；表单在操作前说明原因用途和“申请后仍归档，须原客户企业确认”。必填有红色标识，提交中禁用，成功显示申请人与时间；网络结果不明时保留同一原因与键重试。
- 客户“待我处理”列表包括本企业待审核线索和有待确认撤回申请的归档线索，后者明确标为“待确认撤回”；待确认申请不再重复进入“已处理”列表，已归档原结论在详情中仍可查看。客户详情显示申请原因、申请人和时间，确认前说明“确认后回到待审核，原结论和归档记录保留”；只由服务端 `confirmWithdrawal` 能力开启确认按钮。确认后重新读取并可再次审核；历史记录在刷新后仍可回看。
