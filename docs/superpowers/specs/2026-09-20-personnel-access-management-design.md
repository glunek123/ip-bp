# 人员账号、部门成员与角色分配闭环设计

日期：2026-09-20

任务：PERSONNEL-ACCESS-001

状态：设计已确认，等待书面规格复核后进入实施计划与编码。

## 1. 目标与依据

本 Slice 交付路线图第 07 项：有权管理员通过正式页面创建实名内部账号，为其建立当前部门的活动成员关系，按需绑定活动 Team，并分配一个已有活动角色；新人员随后使用真实用户名和密码登录，只能访问角色实际授予的范围。此后同一页面支持账号和成员启停、管理员重置密码、成员调队、角色分配的新增／撤销／恢复，以及最小 Team 创建／启停。

设计继续遵守 REQ-SY-004、SD-28／31／33／35／36、AUTH-LOCAL-001 和 Team 管理授权架构。认证、组织关系和授权仍是不同责任，但一次业务命令需要改变多个对象时必须共享事务。前端只呈现服务端判定的能力，不承担最终授权。

## 2. 范围与排除项

本 Slice 包含：

- 当前部门内的人员列表、详情和管理上下文查询。
- 创建一个全新的本地实名账号、`LocalCredential`、当前部门成员关系和一个初始角色分配。
- 账号启停、当前部门成员启停、成员 Team 调整。
- 管理员为他人重置密码，并撤销目标账号的既有会话。
- 已有角色模板的查询，以及角色分配、撤销、恢复和合法改绑。
- Team 查询、创建和启停。
- 成功及拒绝路径的服务端授权、事务、并发保护、安全日志和业务审计。
- 正式 Vue 页面、真实 PostgreSQL 和浏览器验收。

本 Slice 不包含：

- 角色模板复制、Grant 编辑、权限代码创建或通用策略表达式。
- 自助注册、邀请链接、找回密码、强制首次改密、MFA、OIDC 或企业微信。
- 为已有账号新增第二个部门成员关系、公司级跨部门账号管理或跨部门授予。
- 用户自助改密、自助停用、自助调岗或任何自我提权入口。
- Team 层级、编码、物理删除、矩阵组织或客户负责人转派。
- 生产账号、生产迁移、发布或真实人员数据处理。

## 3. 纵向交付顺序

实施保持一个业务 Slice，但按可独立验收的纵向能力推进：

1. **开通闭环**：管理上下文查询，创建账号／成员／初始角色的原子命令，正式人员页面，以及新人员真实登录和范围验证。
2. **日常管理**：账号与成员启停、重置密码、调队、角色撤销／恢复和 Team 管理。
3. **安全收口**：跨部门、越级授予、自我操作、并发、回滚、会话失效、审计、迁移回归和浏览器验收。

每一步先写能在旧实现失败的测试，再写最小实现。阶段性提交不改变最终 Level 3 候选必须整体通过完整门禁的要求。

## 4. 后端模块与事务边界

`OrganizationService` 继续作为组织及授权管理的深模块，不新建平行的账号／权限体系。它增加查询和人员生命周期命令，并把现有角色分配核心拆成可接收 `Prisma.TransactionClient` 的事务内实现。公开命令仍自行开启 Serializable 事务；创建人员命令则在同一事务中顺序完成：

1. 在事务外规范化用户名、校验展示名和密码，并完成密码哈希，避免在持锁期间执行高成本 scrypt。
2. 进入 Serializable 事务并取得当前部门序列锁。
3. 锁定并重新校验操作者账号、当前部门成员关系、授权修订和实际 Grant。
4. 校验操作者具备部门级 `user.manage`，且不能以任何名称、首位账号或固定 ID 绕过授权。
5. 校验 Team 为当前部门的活动 Team；无 Team 时初始角色不得包含 TEAM Scope。
6. 锁定并读取目标角色及 Grant，使用现有 Grant Boundary 逐项确认操作者能够覆盖待授予角色。
7. 创建 `UserAccount`、`LocalCredential`、活动 `DepartmentMembership`、初始 `RoleAssignment` 和审计事件。
8. 任一步失败时整体回滚，不留下无凭据账号、无角色成员或孤立审计。

现有 `assignRole()`、`changeMembershipTeam()` 和 Team 命令共享相同的事务内锁顺序与授权加载，不允许 Controller 直接写 Prisma 绕过边界。预计复用现有 schema，不新增迁移；若实施中发现现有约束无法表达已确认不变量，必须先回到设计评审，不以临时字段或开放索引签名绕过。

## 5. 查询范围与页面能力

管理查询返回当前操作者能够看到和操作的最小投影，不把整库对象先读入再由前端过滤：

- `user.read / DEPARTMENT` 可查看当前部门全部成员；`TEAM` 只可查看同一活动 Team；`SELF` 只返回本人只读摘要。
- 账号创建、账号启停、成员启停、密码重置和调队要求 `user.manage / DEPARTMENT`。当前 Slice 不赋予 TEAM 或 SELF 范围这些生命周期动作。
- `team.read / DEPARTMENT` 返回当前部门全部 Team；`TEAM` 只返回操作者所属的活动 Team；`SELF` 对 Team 主数据默认拒绝。
- Team 创建和启停继续要求 `team.manage / DEPARTMENT`。
- 角色模板查询必须具备 `role.read`，并只返回当前操作者通过实际 Grant Boundary 有可能授予的活动模板及必要 Grant 摘要；最终写入仍重新执行 `role.assign` 目标范围和逐 Grant 覆盖检查。
- `role.assign / DEPARTMENT` 可作用于当前部门其他成员；`TEAM` 只作用于同一活动 Team 的其他成员；SELF 不允许向他人授予，也不存在自分配入口。

前端使用管理上下文中的服务端能力控制入口和按钮，但隐藏按钮不代替后端拒绝。没有任何管理读取能力时，不显示“人员与权限”导航；直接访问路由仍由 API 返回 403，并显示无权提示而不是伪装成空数据。

## 6. HTTP 契约

正式路由统一位于 `/api/v1/organization`，使用现有会话、同源与 CSRF 机制：

| HTTP                                                               | 行为                                                    |
| ------------------------------------------------------------------ | ------------------------------------------------------- |
| `GET /organization/management-context`                             | 返回当前部门内受权人员、可见 Team、可授予角色及页面能力 |
| `POST /organization/users`                                         | 原子创建新账号、当前部门成员和一个初始角色              |
| `PATCH /organization/users/:userId/status`                         | 启用或停用单部门账号                                    |
| `POST /organization/users/:userId/password-reset`                  | 有权管理员直接为他人设置新密码                          |
| `PATCH /organization/users/:userId/membership`                     | 启停当前部门成员或调整 Team                             |
| `POST /organization/users/:userId/role-assignments`                | 新增、恢复或合法改绑已有角色                            |
| `PATCH /organization/users/:userId/role-assignments/:assignmentId` | 撤销指定活动角色分配                                    |
| `POST /organization/teams`                                         | 创建当前部门 Team                                       |
| `PATCH /organization/teams/:teamId/status`                         | 启用或停用 Team                                         |

创建请求包含展示名、用户名、初始密码、可选 `teamId` 和一个 `roleTemplateId`。密码永不回显。日常启停、调队、撤权、恢复和密码重置不要求人工填写原因；服务端自动记录操作者、动作和前后状态，避免把审计负担转给业务人员。

所有响应仅包含页面所需字段，不返回密码哈希、会话摘要、外部身份内部值、其他部门成员关系或目标账号在其他部门的角色。

## 7. 账号、成员、角色与会话规则

- 新账号始终创建为活动账号和当前部门活动成员；用户名沿用全局唯一、NFKC 小写和 3～64 个 ASCII 字符规则，密码沿用 12～128 个 Unicode 码点与当前 scrypt 版本。
- 本 Slice 的账号停用和管理员密码重置只允许目标账号恰有当前部门这一项活动成员关系。多部门目标返回 `GLOBAL_ACCOUNT_MANAGEMENT_REQUIRED`，避免部门管理员影响其他部门；公司级账号管理员留待后续独立设计。
- 禁止操作者对自己执行账号停用／启用、管理员重置密码、成员启停／调队和角色分配／撤销／恢复。
- 账号停用撤销目标账号全部未撤销会话并递增 `authorizationRevision`；重新启用不会恢复旧会话。
- 成员停用撤销目标账号在当前部门的全部未撤销会话，并递增 `authorizationRevision`。恢复成员关系后必须重新登录。
- 密码重置依赖当前有效登录会话和部门级 `user.manage`，不重复要求管理员输入自己的当前密码。成功后写入新哈希、更新 `passwordChangedAt`、撤销目标账号全部会话，并递增授权修订。
- 角色新增、恢复、改绑和撤销均锁定目标成员、角色、Team 与既有分配，成功后递增目标账号授权修订。恢复不能绕过当前 Grant Boundary。
- 成员仍有任意活动且绑定 Team 的角色分配时，调队继续返回 `ACTIVE_TEAM_ROLE_ASSIGNMENT_EXISTS`；页面引导管理员先撤销这些分配，不自动迁移或静默扩大范围。
- Team 停用不删除或改写历史引用，但禁止新绑定和恢复绑定；现有授权计算继续忽略无效 Team 绑定。

## 8. 并发、错误与审计

部门序列锁和固定行锁顺序继续保护管理命令。事务开始后重新加载操作者授权，避免并发撤权、停用或调队后仍完成旧请求。用户名唯一冲突、角色状态变化、Team 状态变化和重复角色操作使用稳定错误码；未知、跨部门或无权目标统一 403，不泄漏目标是否存在。

需要明确呈现的业务冲突包括：

- `USERNAME_ALREADY_EXISTS`
- `ACTIVE_TEAM_ROLE_ASSIGNMENT_EXISTS`
- `ROLE_ASSIGNMENT_ALREADY_ACTIVE`
- `ROLE_ASSIGNMENT_NOT_ACTIVE`
- `ROLE_ASSIGNMENT_TEAM_REQUIRED`
- `GLOBAL_ACCOUNT_MANAGEMENT_REQUIRED`
- `REAUTHENTICATION_FAILED`

成功写入与业务对象保持同一事务审计。自我提权、越级授予和跨部门尝试还必须留下拒绝型 `AuditEvent`：事件归属操作者当前部门，以操作者当前成员关系作为审计资源，只记录操作种类和稳定拒绝码，不记录目标对象原始 ID 或可推断的跨部门细节。拒绝审计在业务写事务之外持久化，审计失败绝不能使原操作放行，并必须另记不含秘密的安全错误。其他拒绝路径同样使用不含密码、Cookie、令牌、完整异常或跨部门对象细节的安全日志。成功审计 `details` 自动记录前后状态、目标用户 ID、角色模板 ID 和 Team ID，但绝不记录明文密码或密码哈希。

## 9. 前端交互

新增 `/settings/people-access` 页面和最小正式导航。页面保持单一工作区，不增加审批中心或多级向导：

- 人员列表显示展示名、用户名、账号状态、当前成员状态、Team 和活动角色。
- “创建人员”表单一次收集账号、初始密码、Team 和初始角色；根据角色 Grant 提示 Team 是否必需。
- 人员详情就地提供账号／成员状态、密码重置、Team 调整和角色分配操作。状态切换和 Team 调整直接保存；密码重置只填写目标人员的新密码，不增加原因、重复认证或审批步骤。
- 遇到活动 Team 角色阻止调队时，页面列出需先撤销的分配并保留管理员已选择的新 Team，不自动连锁撤权。
- Team 区域只提供查询、创建和启停；停用前显示不会删除历史引用。
- 401 使用现有全局登录失效处理；403 显示无权；409 保留表单输入并给出可操作冲突提示；网络失败不误报为授权问题。

## 10. 测试与完成标准

本任务按 Level 3 执行。测试先行覆盖：

1. 服务单元和 Controller 契约：创建成功、非法字段、重复用户名、自我操作、跨部门、TEAM／SELF 边界、逐 Grant 越级检查、不可授模板过滤、停用 Team、调队阻断、撤销／恢复旁路和稳定错误码。
2. 认证专项：密码重置、账号／成员停用、授权修订和旧会话不可恢复。
3. 事务及数据库：账号／凭据／成员／角色／审计任一步失败全部回滚；并发创建、停用、撤权、调队和恢复不能绕过锁与唯一约束。
4. 前端单元：页面能力、表单校验、冲突保留、调队引导、密码输入不持久化和 API 错误映射。
5. 真实浏览器／PostgreSQL主路径：管理员创建人员并授予角色 → 新人员登录并只看到正确客户范围 → 管理员撤权／调队／成员停用／账号停用 → 下一请求失效且重新启用不恢复旧会话。
6. 负向浏览器／数据库路径：跨部门已知 UUID、越级角色、自我提权、多部门全局账号操作和事务注入失败均被拒绝且不留下半成品。

最终稳定候选运行聚焦测试、完整 `pnpm verify`、覆盖身份／授权／真实写入路径的数据库 E2E，以及 Level 3 Review。Review 必须给出 `ACCEPTED` 且未关闭 finding 为 0 才能标记内部集成就绪；本地通过不表示已推送、发布或处理生产数据。

## 11. 验收主路径与后续

主验收链路为：现有管理员登录 → 打开“系统设置／人员与权限” → 创建第二位人员并选择活动 Team 与已有角色 → 退出管理员 → 新人员登录 → 验证 SELF／TEAM／DEPARTMENT 实际客户范围 → 管理员执行角色、成员或账号变化 → 新人员下一请求失效 → 重新登录后只获得当前有效授权。

本 Slice 完成后，角色模板复制和 Grant 编辑仍是下一独立权限 Slice；MFA、找回密码、OIDC、公司级跨部门账号管理和客户负责人转派继续分别推进，不因本实现自动获批。
