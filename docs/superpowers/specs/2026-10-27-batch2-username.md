# 第二批：用户名兼容邮箱和自定义形式

## 范围与规则

内部人员、企业客户、公证处和律师账号仍共用 `LocalCredential.username`，使用同一登录入口。用户名可以是邮箱形式，也可以是普通自定义文字；邮箱形式不触发邮件发送或验证。密码、限流、会话以及各类账号的原有创建权限保持不变。

创建和登录继续沿用现行 `trim → Unicode NFKC → lowercase`。在裁剪前先拒绝原始输入中的控制字符、常见零宽字符和双向格式控制字符；规范化后复验，并限制为 3–64 个 Unicode 码点。普通首尾空格仍可裁剪；内部空格、`@`、`+` 和中文可使用。前端仅作即时反馈，后端服务层是最终输入边界。数据库继续使用规范化值的精确唯一索引，并以新增迁移替换原 ASCII 格式 CHECK；数据库约束不执行规范化。不改动旧迁移、不回填或合并历史账号。不同原始输入规范化为同一值时，仍由唯一约束判为重复账号。

历史 ASCII 用户名符合新约束，原规范化规则也未改变。数据库 `char_length` 与服务层的 Unicode 码点长度口径一致。DTO 的 256 个 UTF-16 单元上限只是传输保护；服务层按规范化后的 64 码点限制，避免 NFKC 展开或补充平面字符被 DTO 提前误拒。

## 验收边界

聚焦程序测试应覆盖邮箱、普通自定义、全角与大小写规范化、规范化碰撞、重复账号错误映射、原始输入首尾换行或制表符及内部控制字符拒绝、旧用户名登录。迁移需要主任务在已授权的隔离 PostgreSQL 中逐项验证：旧 ASCII 账号及 unique 索引保留；邮箱、`+`、全角规范化结果与中文值可写；直接绕过 DTO 写入过短、超长、控制字符、零宽和双向控制字符时 CHECK 拒绝；相同规范化值重复写入时 unique 拒绝。真实 HTTP 创建后登录也留待主任务统一验收。本候选不执行数据库迁移，也不声称真实登录链路已通过。
