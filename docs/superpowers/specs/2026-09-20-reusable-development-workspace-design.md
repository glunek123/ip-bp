# 可复用开发工作区设计

## 1. 目标与边界

单人串行开发默认复用当前合适的开发工作区，每个任务仍使用独立任务分支。worktree 只解决确有需要的目录隔离，不再与任务、风险等级或会话生命周期机械绑定。

本轮只调整工作区选择、恢复和收尾规则，不改变风险分级、候选冻结、验证证据、数据库隔离、推送授权或发布规则；不新增工作区登记表、管理脚本、依赖或常驻治理流程。

## 2. 工作区选择

按以下顺序选择最短安全路径：

1. 同一任务继续开发、修复或补测时，复用原工作区。属于该任务的未提交修改是恢复现场，不以“必须干净”为由自动暂存、重置或删除。
2. 单人串行开始新任务时，优先复用当前开发目录或已有可复用开发 worktree。复用前确认上一任务已集成、目录干净、没有进行中的 merge／rebase、没有其他写入者或占用进程；从已核实的本地 `main` 创建新的任务分支。`origin/main` 落后时不得覆盖已验证的本地集成结果。
3. 只有并行任务、现有目录承载其他未完成现场、需要同时维护不兼容版本，或测试／运行环境确实需要额外目录隔离时，才创建临时 worktree。

工作区复用不改变“一处工作区只允许一个写入者”。worktree 不是数据库、端口、进程或安全沙箱；这些资源继续使用现有测试环境保护和互斥规则。

## 3. 环境准备与候选验证

复用目录时先核对项目运行时、锁文件和生成输入。只有依赖链接缺失、锁文件／运行时变化或生成产物失配时才重新安装或准备；不因任务编号变化机械重装依赖。

开发期允许在任务现场运行定向检查。正式候选仍必须是干净、固定的 Git tree，并满足所属 Level 的验证和 Review 要求。工作区寿命与证据有效期相互独立，复用目录不会使旧候选证据自动适用于新 tree。

## 4. 集成与分类收尾

候选按既有规则集成并核实远端后，根据工作区用途收尾：

- **可复用开发工作区**：保留目录、依赖和可复用生成环境；确认没有任务现场后，安全退出已合并任务分支。主工作区可回到本地 `main`，附加 worktree 可停在已核实 `main` 提交的 detached 状态，或直接切换到下一任务的新分支；已合并本地任务分支在不再被工作区占用后安全删除。
- **临时隔离 worktree**：确认提交已进入 `main`、远端已核实、目录干净且无进程占用后，删除该 worktree，安全删除已合并本地任务分支并 prune。
- **脏或归属不明的工作区**：先判断是否仍需集成；需要清理时先形成可恢复保全并记录恢复方式，禁止强删。
- **宿主工具管理的工作区**：遵循宿主生命周期，不把手工删除或跨任务改造作为项目完成条件。

## 5. 文档职责

`.cursor/rules/verified-feature-integration.mdc` 是工作区选择与收尾的唯一执行规则。`AGENTS.md` 只保留触发入口，`docs/ai-coding.md` 只说明同一任务恢复和按变化准备环境。README、环境报告、历史状态、历史验证和既有实施计划继续保留事实职责，不复制新的日常操作规则。

## 6. 验收

- 当前规则不再同时出现“按需创建”和“任务结束无条件删除”的冲突。
- 同一任务恢复、单人串行新任务、并行／不兼容任务三种路径都有唯一选择结果。
- 可复用与临时 worktree 的收尾不同，脏现场始终先保全。
- 风险门禁、正式候选洁净度、证据绑定、数据库隔离和授权边界保持不变。
- 不新增脚本、依赖、状态表或每任务必填文档。
