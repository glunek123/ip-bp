# 精简现有开发流程与最小护栏设计

日期：2026-09-20

状态：方案已确认；本文只记录本次流程调整的依据和验收范围。日常执行继续以
[`verified-feature-integration.mdc`](../../../.cursor/rules/verified-feature-integration.mdc)
为唯一规则入口，不把本文维护成第二份操作手册。

## 1. 目标与非目标

目标是让普通任务走最短路径，只在真实风险出现时增加控制，并复用仍然有效的验证证据。新增治理开销在代表性 Level 2 任务上实测应尽量为零、最多约一分钟；该预算只约束新增静态治理，不削减原本必要的业务测试。

本轮只交付三项结果：

1. 精简现有执行规则，删除重复确认和机械步骤；
2. 核对并理顺现有门禁的真实检查集合，删除昂贵重复调用；
3. 修复状态双写，并补上三个最小架构护栏。

本轮不建设通用事务框架、统一 Repository 层、依赖分析平台、测试调度平台、治理报表或第二套规则文档，也不顺带重构业务实现。

## 2. 两条执行路径

### 普通路径

Level 1 和复用既有权限、隔离、事务及审计机制的普通 Level 2 均使用：

```text
读取适用规则和必要上下文
→ 明确验收条件
→ 实现并运行定向测试
→ 执行所属等级的交付检查
→ 只同步真正变化的文档
→ 交付
```

Level 1 与 Level 2 的主要区别是验证范围，不是文档数量。普通任务不默认写独立设计、实施计划或开工状态，不默认创建 worktree、独立 Review 或完整 `verify`。已有设计足够明确时直接实施。

### 高风险路径

改变认证、授权计算、部门隔离、共享事务／审计基础设施、财务核心不变量，实施破坏性迁移或产生难恢复影响时，在普通路径上增加：

```text
必要时确认关键设计
→ 实现和定向风险验证
→ 前置 Review 并关闭阻断问题
→ 稳定最终候选
→ 完成该候选所需的完整门禁
→ 按授权集成
```

风险由“改变了什么规则、影响范围和失败恢复难度”决定，不因使用既有权限能力、涉及多个文件、增加普通迁移或经过多个模块就机械升级。新增敏感操作即使没有修改共享内核，也必须覆盖其真实权限、隔离和失败风险。

worktree 只在需要隔离时使用；已经处于合适隔离环境时不再创建第二层。Review 可以针对 finding 运行聚焦测试，但不默认重跑完整门禁。

## 3. 去除重复确认和重复上下文

同一设计只确认一次。用户已确认范围且落盘内容没有增加、删除或改变关键决定时，写设计、计划、测试、范围内文档和本地提交属于执行动作，不再逐项询问。只有产品分叉、既有规则冲突、关键安全边界变化、不可逆数据影响、生产／真实外部操作或明显扩展范围时暂停。

新任务先读取当前规则、`project-status.md`、路线图中的当前 Slice、对应 Spec、源码和直接测试。架构、完整技术设计、历史验证及其他模块资料只按触发条件读取；规则、分支和任务范围未变化时不重复加载，发生变化时重新核对现场。

## 4. 现有门禁的真实包含关系

本设计以当前脚本为准，不根据命令名称猜测覆盖范围：

- `verify:slice:customer` 和 `verify:slice:right-holder` 已分别包含一次 Prisma 准备、定向单元／契约测试、`check:fast:prepared`、Slice 格式检查、prepared 后端构建及对应数据库 E2E。
- `verify:slice:auth` 包含同类认证聚焦集合，但只是 Level 3 的聚焦证据，不替代最终完整门禁。
- `pnpm verify` 包含严格上下文、Spec、Prisma、类型、Lint、格式、工具／前后端单元测试和构建，不包含数据库 E2E。
- `pnpm test:e2e:full` 当前通过无过滤的 Playwright 入口收集 `tests/e2e`，配置只有一个 Chromium project；它与 `pnpm verify`职责不同，不因名称含有 `full` 就互相替代。

开发期间可以重复运行最小相关测试获取快速反馈。候选 tree 已稳定且即将运行正式 Slice 入口时，不再紧接着机械执行该入口已经包含的定向测试和 `check:fast`。Level 3 最终候选仍分别完成 `pnpm verify` 和风险要求的数据库 E2E；若完整 E2E 已覆盖相同配置下的专项范围，最终阶段不再依次重复专项 E2E。

实施时使用 Playwright `--list` 和现有脚本测试核对完整入口、专项入口、project、过滤及零匹配行为。该核对用于固定配置和回归测试，不成为每个业务任务的人工步骤。

“最终集中验证”表示尽量在不会继续大改的候选上运行，不是限制执行次数。最终验证失败并修复后形成新候选，必须重新判断并完成受影响门禁；旧证据只能在 tree、检查集合、环境和相关输入仍匹配时复用。

业务规则、执行规则、测试配置和技术说明应在最终候选冻结前同步。验证结果随后引用实际被测 tree；不能修改影响结论的文件后仍把旧结果描述成新候选证据。

## 5. 三个最小架构护栏

第一版只处理已经明确的三类问题：

1. 禁止业务模块跨目录导入另一个业务模块的内部实现；
2. 禁止业务 Controller 直接访问 `DatabaseService`、Prisma Client 或事务客户端，健康检查等技术入口使用显式窄例外；
3. 新增 Prisma Model 必须声明唯一主责模块。

能由现有 ESLint 的静态导入规则准确表达的约束直接复用 ESLint，不另写重复扫描器。ESLint 无法可靠识别的 Model 所有权或明显跨模块写入，只补一个窄范围、带正反例测试的检查；检查必须说明支持的语法范围，不能把未识别写法宣称为已证明安全。

例外集中登记主责、理由、依据和删除条件，不允许在业务源码中随意忽略。第一次真实跨模块写入出现时，由该 Slice 明确主责、事务参与方式、锁顺序、失败边界和聚焦数据库 E2E；出现第二个真实重复后再决定是否抽象公共事务接口。

## 6. 状态唯一事实源

- Spec、DOMAIN、CROSS-MODULE 和 Decision 保存业务规则、语义、批准状态和验收条件；
- `feature-roadmap.md` 保存所有 Slice 的全局实现状态、依赖顺序和唯一 Current／Next；
- `project-status.md` 只保存当前任务指针、恢复所需最小事实、当前限制和下一动作；
- `VALIDATION.md` 保存历史验证，不充当当前状态；
- README 只导航，并指向上述唯一来源。

普通短任务不机械更新 `project-status.md`。业务能力状态变化才更新路线图；当前长任务或阶段切换才更新项目状态；业务规则变化才更新 Spec／Decision；验证完成才记录对应候选证据。

实现必须修改现有规则并删除冲突旧条款，不能只新增本文。本文完成实施说明职责后保持稳定，不参与日常状态更新。

## 7. Slice 拆分与安全

拆分用于缩小反馈批次，不降低风险等级。人员权限可以拆成“开通闭环”和“日常管理闭环”，但每个闭环必须同时包含自己的权限、部门隔离、自我操作、回滚、并发、审计和会话失效验证；不得把安全作为最后一个候选补做。

是否拆分根据独立用户结果、风险和可验证主路径判断，不使用文件数或代码行数机械判定，也不拆成数据库、后端、前端三个水平阶段。

## 8. 落地与验收

实施顺序固定为：

1. 修正规则和状态职责，清除已经确认的状态漂移；
2. 为现有门禁包含关系补回归测试并删除重复调用；
3. 用现有 ESLint 优先实现导入和 Controller 限制，仅为 Model 所有权补必要的窄检查；
4. 用一个代表性普通 Level 2 任务做前后对照，不建立长期治理报表。

验收需要证明：

- 普通任务不再重复确认设计、计划、worktree 或常规测试；
- 稳定候选不会在 Slice 门禁前机械重复其完整检查集合；
- `verify` 与数据库 E2E 的职责被准确保留，不因去重而漏检；
- Spec、Roadmap 和 Project Status 不再维护同一实现状态；
- 三个最小护栏分别有允许和拒绝用例；
- 代表性 Level 2 的新增治理耗时经实际测量不超过一分钟；
- 未增加通用事务框架、架构平台、测试调度平台或新的日常操作手册。
