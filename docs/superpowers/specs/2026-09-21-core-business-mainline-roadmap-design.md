# 核心业务主线优先与纵向切片重排设计

日期：2026-09-21

任务：CORE-ROADMAP-001

状态：方案 A“核心主线优先”已确认；本文固定详细切片边界，等待实施计划前复核。

## 1. 目标

开发重心从“先完善联系人、权限、文件平台和客户外围能力”调整为知产案件管理系统的核心业务价值链：

> 客户／权利主体 → 线索 → 取证批次／公证事项 → 案件 → 立案 → 审理／执行／归档

后续仍采用纵向切片：每个切片同时交付正式页面、HTTP API、后端业务规则、PostgreSQL、最小权限、审计和关键浏览器验收。权限、材料、客户准入等基础能力只在当前业务动作确有需要时补最小闭环，不再先建设大而全的平台。

本设计只重排开发优先级和定义前四个核心切片，不把 Demo 直接升级为正式规则，也不宣称任何核心业务代码已经实现。

## 2. 事实依据与纠偏边界

主链不是重新发明，来源如下：

| 范围   | 已有依据                                | 本设计采用方式                                                   |
| ------ | --------------------------------------- | ---------------------------------------------------------------- |
| 线索   | `M01-leads.md`、REQ-LD-001～004         | 保留待推送→待审核→待确认、归档支路以及来源线索只读留存           |
| 公证   | `M03-notary.md`、REQ-NT-001～005        | 首期只实现线上正常路径；物流“明确无”、来源关联和转案纠偏继续有效 |
| 案件   | `M02-cases.md`、REQ-CA-001～009、SD-23  | 正常案件从待匹配逐阶段推进；首期只做到待开庭，后段另切           |
| 跨模块 | REQ-XM-002／003／006、SD-01／02／22／34 | 使用稳定客户、主体和来源身份；自动审计；不按店铺名或展示串猜关系 |
| 权限   | REQ-XM-001／005、TD-AUTHZ-01            | 复用现有 Grant 与 SELF／TEAM／DEPARTMENT，不硬编码角色名称       |

以下 Demo 行为明确不继承：删除已移交线索、用字符串拼接代替关系、虚构法院案号、仅保存文件名冒充上传成功、任意跳阶段、按按钮可见性授权、批量未选择时默认处理全部、按店铺或队列猜测来源。

## 3. 方案选择

已确认采用方案 A：围绕完整业务主线连续交付小纵向切片。

- 不采用“先完成多联系人、资产、协议、通用文件中心再做业务”的平台优先路线，因为它继续推迟核心价值。
- 不采用“直接做案件页面、以后再补线索和公证”的案件优先路线，因为它会产生第二套建案来源和返工。
- 不把整条线索到归档塞入一次巨型开发；按跨模块业务交接点拆成四个可独立验收的小切片。

## 4. 核心切片顺序

### 4.1 CORE-LD-001｜线索录入、审核与移交公证

这是唯一 Current Slice。

业务结果：有权内部人员为已满足准入条件的客户和关联主体建立线索，经过推送、侵权审核和取证确认后，明确创建一个取证批次／公证事项；来源线索转为只读并可反查，失败或重试不产生重复事项。

本切片包含：

- 客户主线准入的最小缺口：正式身份字段、一位准入联系人、至少一份真实证件材料、准入动作和状态审计。
- 线索主档、商品明细、估算、列表／详情／新建／编辑和四个既有阶段。
- 推送、侵权／不侵权、确认取证／不取证和归档动作。
- 明确选择本次商品、已有材料、公证处、取证方式和目的后创建取证批次。
- `Lead → NotaryMatter`稳定来源关系、幂等意图、版本冲突和同事务审计。
- 当前运营端的低负担办理；外部客户审核暂以“内部人员代录线下反馈”表达，审计记录真实操作者和渠道，不伪装成客户账号。

最小字段沿用 DOMAIN LD01～06：客户、权利主体、负责运营、案件类型、侵权类型、来源、平台／线下对象、发现时间、店铺及标识、披露标记、备注、商品 URL／名称／销量／单价／评论数和估算额。截图材料可选；商品草稿可暂缺，推送和移交按动作门槛重新校验。

明确排除：CSV、批量推送、外部客户端、OCR、线下取证办理、公证后续阶段、费用中心、联系人扩展、资产和协议。

### 4.2 CORE-NT-001｜公证线上办理与出证转案

这是唯一 Next Slice。

业务结果：从有稳定来源的公证事项进入线上正常路径，完成物流、开箱材料、侵权审核、出证确认并原子生成案件；案件保留客户、主体、来源线索、取证批次、公证事项和已有费用来源，不虚构法院案号。

首期路径：待取证 → 待取件开箱 → 开箱待审核 → 开箱待确认 → 待出证 → 已归档并生成案件待匹配。

包含物流公司和单号的真实值／明确无、开箱材料、审核结论、公证处、公证书编号与日期、披露信息以及金额“已知／待定”。公证费、样品费、调查费和披露费只保存稳定来源事实，不在本切片发起支付。

明确排除：线下调查／直接提诉、不出证退货、ZIP 批量开箱、OCR 自动匹配、批量归档、证物实物台账、公证处外部账号和系统对接。

### 4.3 CORE-CA-001｜案件待匹配至正式立案

业务结果：公证转入的案件从待匹配按正常门槛办理到待开庭，形成可见的案件主档、当事人、律师承办、起诉材料、邮寄、法院提交、正式受理和完整时间轴。

首期路径：案件待匹配 → 待写诉状 → 诉状待确认 → 诉状待盖章 → 待提交立案 → 转正式立案 → 待开庭。

本切片实现被告、律师承办关系、起诉材料精确版本、标的额、邮寄日期、法院、提交日期、法院案号、正式受理日期和开庭安排；保存与推进分离，缺件就地提示，服务端仍执行状态和材料守卫。

明确排除：历史补录、批量诉状／批量立案、多人律师复杂协作、保全、合并办理组、缴费发起、外部律师端和客户端。

### 4.4 CORE-CA-002｜审理、执行、结案与归档

业务结果：在 B13／B15 所需细则收口后，从待开庭继续完成判决选择、必要二审、执行准备、执行立案、执行结束、结案与归档。

该切片不得因为当前案件数组存在 `next` 就提前实现未知分支。费用、结算和真实收付款仍保持不同事实；归档不等于结算完成。

## 5. 支撑能力如何随主线落地

### 5.1 客户准入

不放宽 SD-22／30：无正式身份证明的客户仍只能保持草稿，不能进入正式取证或案件。CORE-LD-001只补主线所需的最小准入，不扩展多联系人、合作状态、负责人转派、资产或协议。

准入使用现有客户身份字段、一位联系人和有效客户—主体关联；正式证件通过 Material／ContentVersion 精确引用。客户从 DRAFT 进入 ADMITTED 必须由单一 Command 完成校验、状态更新和审计。

### 5.2 文件能力

不先建设通用文件中心。CORE-LD-001实现既有 T05 缝隙的最小子集：上传草稿、不可变内容版本、授权读取、引用后不可删除、未引用删除／恢复以及校验元数据。

开发和测试使用可替换的私有本地存储 Adapter，保存真实文件字节并通过应用授权读取；它只证明内部契约和浏览器主链，不冒充 SD-32 所需的生产私有对象存储、加密、备份或恢复验收。生产 E02 继续保持阻塞。

### 5.3 权限

现有授权引擎、角色模板和数据范围足够，不再开新的权限平台切片。各业务切片只增加代码中固定的最小 Action：

- CORE-LD-001：`CUSTOMER_ADMIT`、`LEAD_READ`、`LEAD_MANAGE`、`LEAD_REVIEW`。
- CORE-NT-001：`NOTARY_READ`、`NOTARY_MANAGE`。
- CORE-CA-001：`CASE_READ`、`CASE_MANAGE`、`CASE_ASSIGN`。

初始模板可把主管配置为本部门、小组长配置为本团队、运营配置为本人范围；实际授权仍只看有效 Grant，不比较职位名称。业务服务在权限通过后继续校验客户准入、阶段、来源、材料和并发版本。

## 6. 模块与数据边界

- `customers`拥有客户准入状态和准入依据；`materials`拥有稳定材料、不可变内容版本及存储 Adapter。
- `leads`拥有线索、商品、状态和决定历史；只通过客户模块读取可开展业务的客户／主体投影。
- `notary`拥有取证批次、公证事项及办理状态；创建时冻结来源线索和本批所选载荷，不复制成无关联字符串。
- `cases`拥有案件主档、当事人、承办关系、阶段和活动；公证转案调用案件模块公开 Command。
- 跨模块写入在同一 PostgreSQL 事务内完成；业务事实和 AuditEvent 同成同败。

列表、详情和联想均从服务端授权范围构造查询，不先读全量再过滤。每个可变聚合使用 `version`；创建批次、转案和阶段推进接受幂等键，重复请求返回原结果，不生成新业务事实。

## 7. 页面与操作负担

正式页面沿用 Demo 已确认的信息架构：侧栏“线索库／公证阶段／我的案件”，列表上方阶段筛选，详情页就地显示当前状态、下一动作、缺件和折叠历史。

- 一个页面只有一个主要推进动作；保存草稿和推进明确分开。
- 能从客户、主体和来源关系带出的信息自动带入，但不覆盖用户已修改值。
- 普通动作不增加原因弹窗、审批页或多级确认；只有既有异常动作要求原因。
- 提交失败保留表单值并定位字段；409提示刷新但不清空输入。
- 第一阶段只有运营端，不建设客户、公证处或律师的独立入口；线下反馈代录必须显示真实操作者与渠道。

## 8. 错误和异常边界

每个 Command 至少区分：无权、目标不可见、当前状态不允许、客户未准入、主体关系无效、材料缺失或版本失效、并发版本冲突、重复意图以及跨模块事务失败。

非法推进不修改业务状态；跨模块创建失败不留下“已移交／已转案”假成功。取消弹窗不写业务事实。归档对象不能通过普通编辑重新进入流程；重开、更正和撤销留给获准的独立动作。

## 9. 验收与风险等级

CORE-LD-001预计为 Level 2：新增普通业务模块、前向迁移和业务 Action，但复用而不修改共享权限计算、部门隔离、审计与事务基础设施。若实施中必须改变这些共享机制，立即升级 Level 3。

完成标准必须包含：

1. 聚焦单元／Controller／组件测试覆盖状态动作、字段和错误保留。
2. 空库全迁移、上一支持 Schema 升级、数据库约束和事务回滚测试。
3. 真实 PostgreSQL 浏览器链：登录 → 补齐并准入客户 → 新建线索 → 推送 → 记录侵权审核 → 确认取证并创建公证事项 → 刷新后来源关系和只读线索仍正确。
4. SELF／TEAM／DEPARTMENT 范围、跨部门拒绝、撤权下一请求生效和非法状态负向测试。
5. 重复提交、并发版本冲突和跨模块失败不产生重复事项或假成功。
6. `pnpm check:fast`、受影响格式、`pnpm spec:check`及为该切片建立的正式 Level 2 门禁。

## 10. 后置能力

多联系人、主体关系完整维护、客户负责人和合作状态、完整生产存储、CSV／批量、OCR、线下公证与退货、公证处／律师／客户端、资产协议、费用支付、结算、报表和合并办理组仍保留在能力总账中，但不得再次排到核心主链前面。

生产部署、真实私有对象存储、备份恢复、外部系统协议和生产数据迁移不属于这四个内部 MVP 切片的完成声明。
