# 核心业务主线优先与状态动作切片设计

日期：2026-09-21

任务：CORE-ROADMAP-001

状态：核心主线方向、“里程碑＋状态动作小切片”粒度及字段／附件／存储契约已获用户确认；`CORE-LD-001`实施计划已生成。

## 1. 目标

开发重心从“先完善联系人、权限、文件平台和客户外围能力”调整为知产案件管理系统的核心业务价值链：

> 运营发现并录入线索 → 企业客户审核 → 运营确认取证 → 公证办理 → 生成案件 → 立案 → 审理／执行／归档

后续仍采用纵向切片，但不再把整个线索、公证或案件模块称为一个Slice。四个大段只作为里程碑；真正的Slice以“一类真实角色完成一个业务动作，并产生一个用户可见的状态变化”为边界，同时交付该动作所需的正式页面、HTTP API、后端规则、PostgreSQL、最小权限、审计和关键浏览器验收。

权限、材料、客户资料准入和外部入口只在当前动作确有需要时补最小闭环，不先建设大而全的平台。

本设计重排优先级和细化切片，不把Demo直接升级为正式规则，也不宣称任何核心业务代码已经实现。

各Slice的精确字段、受控选项、必填条件、附件类型／数量／格式、数据库与私有二进制存储边界、材料版本引用及未决动作阻塞，以[核心业务字段、附件与存储契约](2026-09-21-core-flow-field-material-contract.md)为唯一编码级补充。实施计划必须逐行引用该契约，不得再从Demo临时推断字段或以文件名代替真实附件。

## 2. 事实依据与纠偏边界

主链不是重新发明，来源如下：

| 范围   | 已有依据                                | 本设计采用方式                                                   |
| ------ | --------------------------------------- | ---------------------------------------------------------------- |
| 线索   | `M01-leads.md`、REQ-LD-001～004         | 保留待推送→待审核→待确认、归档支路以及来源线索只读留存           |
| 公证   | `M03-notary.md`、REQ-NT-001～005        | 首期只实现线上正常路径；物流“明确无”、来源关联和转案纠偏继续有效 |
| 案件   | `M02-cases.md`、REQ-CA-001～009、SD-23  | 正常案件从待匹配逐阶段推进；首期只做到待开庭，后段另切           |
| 跨模块 | REQ-XM-002／003／006、SD-01／02／22／34 | 使用稳定客户、主体和来源身份；自动审计；不按店铺名或展示串猜关系 |
| 权限   | REQ-XM-001／005、TD-AUTHZ-01            | 复用现有 Grant 与 SELF／TEAM／DEPARTMENT，不硬编码角色名称       |

以下 Demo 行为明确不继承：删除已移交线索、用字符串拼接代替关系、虚构法院案号、仅保存文件名冒充上传成功、任意跳阶段、按按钮可见性授权、批量未选择时默认处理全部、按店铺或队列猜测来源。

必须区分两个概念：

- **客户资料准入**：客户身份、证件、联系人和客户—主体关系满足正式业务门槛。这是数据条件，不是线索阶段。
- **客户审核线索**：运营把待推送线索提交给企业客户端后，获授权客户判断侵权／不侵权。这是线索状态动作。

运营始终是线索的创建者。企业客户不会创建运营线索；客户端只接收已推送给本企业的线索并完成获准动作。上一版“运营代录线下反馈、外部客户端整体后置”的范围被本设计替代。

## 3. 粒度方案

已比较三种拆法：

1. **状态动作切片（采用）**：一个Slice只完成一个角色动作和一次主要状态转换，最早形成真实可见成果。
2. **角色端切片（不采用）**：先完整建设客户端、公证处端或律师端，再接业务；会重新把平台建设放到主线之前。
3. **模块切片（不采用）**：一次做完整线索、公证或案件模块；范围过大，难以及早验收和纠偏。

分支动作可以分别交付。例如“客户确认侵权”和“客户判定不侵权归档”从同一当前状态出发，但分别形成独立验收切片。支撑能力不得单独膨胀为平台；首次需要真实客户端时，只交付企业账号映射、本企业待办、详情和当前审核动作。

## 5. 支撑能力随动作落地

### 5.1 客户资料与真实客户端

客户资料准入不作为线索状态节点。SD-22／30仍有效：无正式身份证明的客户保持草稿，不能进入正式取证或案件；正式准入需要匹配主体类型的证件、一位联系人和至少一种联系方式。

现有运行时代码尚无已准入客户，因此`CORE-LD-001`包含一个不单列为业务阶段的支撑子集：补齐最小真实证件材料、执行准入Command并留下审计。正式线索只能选择已准入客户及其有效关联主体；这不会改变“运营是线索创建者、客户在推送后审核线索”的流程顺序。

`CORE-LD-002`必须提供最小真实客户端，而不是运营端换皮或代录：企业账号与一个明确客户企业绑定，只读取本企业获推送线索，后端按企业范围过滤，并使用与运营端相同的业务Command执行审核。完整客户首页、资产、协议、报表和自助账号管理不在该Slice。

### 5.2 文件能力

不先建设通用文件中心。首次需要真实材料的Slice实现最小子集：上传草稿、不可变内容版本、授权读取、引用后不可删除、未引用删除／恢复和校验元数据。

开发和测试使用可替换的私有本地存储Adapter，保存真实文件字节并通过应用授权读取；它只证明内部契约和浏览器主链，不冒充SD-32所需的生产私有对象存储、加密、备份或恢复验收。生产E02继续保持阻塞。

具体Material／ContentVersion／MaterialReference模型、上传补偿、授权下载、各业务动作冻结的内容版本以及每类文件的格式和数量上限，统一见[字段、附件与存储契约](2026-09-21-core-flow-field-material-contract.md)。本文不再留给实施AI自行选择本地路径、公开URL或覆盖旧文件等实现方式。

### 5.3 权限

现有授权引擎、角色模板和数据范围足够，不开新的权限平台切片。固定业务Action随首次动作增加，例如：

- 运营线索：`LEAD_READ`、`LEAD_CREATE`、`LEAD_EDIT`、`LEAD_PUSH`、`LEAD_EVIDENCE_DECIDE`。
- 企业客户：`CLIENT_LEAD_READ`、`CLIENT_LEAD_REVIEW`，范围固定锚定获授权企业，不复用运营SELF／TEAM扩大读取。
- 公证：`NOTARY_READ`及与各推进动作对应的最小Action。
- 案件：`CASE_READ`、`CASE_ASSIGN`及与各阶段动作对应的最小Action。

权限配置只能选择代码已经实现的动作；业务服务在授权通过后继续校验企业归属、客户准入、当前阶段、来源、材料和并发版本。

## 6. 模块与数据边界

- `customers`拥有客户资料状态、企业账号映射和准入依据；`materials`拥有稳定材料、不可变内容版本及存储Adapter。
- `leads`拥有线索、商品、状态、推送和审核决定历史；运营创建，客户端只经公开Command审核。
- `notary`拥有取证批次、公证事项及办理状态；创建时冻结本批所选载荷并保留来源线索关系。
- `cases`拥有案件、当事人、承办关系、阶段和活动；公证转案调用案件模块公开Command。
- 跨模块写入在同一PostgreSQL事务内完成；业务事实和AuditEvent同成同败。

列表、详情和联想均从服务端授权范围构造查询，不先读全量再过滤。每个可变聚合使用`version`；创建、移交、转案和阶段推进接受幂等键，重复请求返回原结果，不生成新业务事实。

## 7. 页面与操作负担

正式页面沿用Demo已确认的信息架构：运营端侧栏“线索库／公证阶段／我的案件”，列表上方阶段筛选，详情页显示当前状态、下一动作、缺件和折叠历史。客户端只展示本企业当前需要处理或查看的记录。

- 一个页面只有一个主要推进动作；保存草稿和推进明确分开。
- 能从客户、主体和来源关系带出的信息自动带入，但不覆盖用户已修改值。
- 普通动作不增加原因弹窗、审批页或多级确认；只有不侵权、不取证、归档等既有异常动作要求原因。
- 提交失败保留表单值并定位字段；409提示刷新但不清空输入。
- 首次出现某类外部角色时只提供完成当前动作所需的最小入口，后续Slice再扩展其待办。

## 8. 错误和异常边界

每个Command至少区分：无权、目标不可见、企业不匹配、当前状态不允许、客户未准入、主体关系无效、材料缺失或版本失效、并发版本冲突、重复意图以及跨模块事务失败。

非法推进不修改业务状态；跨模块创建失败不留下“已移交／已转案”假成功。取消弹窗不写业务事实。归档对象不能通过普通编辑重新进入流程；重开、更正和撤销留给获准的独立动作。

## 9. Current Slice验收与风险

`CORE-LD-001`预计为Level 2：新增线索最小模型、运营端页面、前向迁移和业务Action，但复用而不修改共享权限计算、部门隔离、认证、审计与事务基础设施。若实施中必须改变这些共享机制，立即升级Level 3。

`CORE-LD-001`完成标准：

1. 运营端出现线索列表、四阶段计数、空状态、新建、详情和允许范围内的编辑入口。
2. 有权人员先按既有规则补齐并准入客户；运营再选择当前范围内已准入客户及其关联主体，录入必要线索和至少一项商品，保存为待推送；刷新后从PostgreSQL读回。
3. 未授权客户／主体、跨部门对象、非法金额、空商品和失效版本被服务端拒绝，用户输入不被清空。
4. SELF／TEAM／DEPARTMENT查询和详情范围正确；撤权下一请求生效。
5. 同一幂等意图不重复创建线索，并发旧版本编辑返回冲突；成功写入与审计同成同败。
6. 聚焦单元／Controller／组件／数据库测试、真实PostgreSQL浏览器链和所属Level 2门禁通过。

该Slice不包含推送、客户端审核、取证确认或公证表。它只交付第一个可运行成果；这些动作分别由后续小切片负责，不能用预置状态或Mock冒充完成。

## 10. OCR、爬虫和导入的扩展边界

未来OCR录入、线索爬虫和案件导入需要稳定接入点，但本轮不预建供应商接口、回调、任务队列、批次表或通用导入平台。

- 运营表单、OCR确认和爬虫导入最终调用同一套领域Command；任何适配器都不得直接写正式业务表或直接改变状态。
- 创建Command支持幂等意图，并为业务记录保留独立的创建渠道和可选外部来源标识；渠道字段不与“线上／线下侵权来源”混用。
- OCR和爬虫结果先进入候选／暂存区，经过类型校验、重复检查和人工确认后才调用正式Command。候选失败不污染正式线索或案件。
- 未来案件导入使用历史案件导入／补录Command，携带真实业务日期、资料来源和补录原因；不得借导入绕过正常案件阶段。
- 具体任务模型、批次失败模式、爬虫协议、OCR供应商和回调契约在对应功能立项时设计；当前只保证核心模块接口不依赖HTTP表单形状，便于新增适配器而不改状态机。

## 11. 后置能力

多联系人、主体关系完整维护、客户负责人和合作状态、完整生产存储、CSV／批量、OCR、爬虫、线下公证、复杂退货、公证处／律师／客户端完整门户、资产协议、费用支付、结算、报表和合并办理组仍保留在能力总账中，但不得再次排到当前核心动作之前。

生产部署、真实私有对象存储、备份恢复、外部系统协议和生产数据迁移不属于这些内部MVP切片的完成声明。
