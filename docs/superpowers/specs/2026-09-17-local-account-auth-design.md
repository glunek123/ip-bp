# 系统自有账号认证设计

日期：2026-09-17

任务：AUTH-LOCAL-001

状态：已获方案确认，待实施计划

## 1. 依据与目标

用户于2026-09-17引用会话“执行联系人切片”，确认正式身份认证不依赖第三方登录，首期采用系统自有账号，并进一步确认第一切片先交付“一次性命令创建首个管理员＋正式登录／会话／退出”，人员与权限管理页面紧接着另开切片。

本切片的目标是让当前运营端不再因缺少身份而把业务接口的`401`显示成“连接失败”：管理员先在受控终端创建首个本地账号，用户通过同源登录页建立服务端会话，后端把会话解析为现有`ActorContext`，再继续使用已经实现的部门、角色、Grant和数据范围校验。

这是E01“正式身份认证实现”的第一种正式Adapter，不是测试Mock。未来增加OIDC／企业微信时保留同一`IdentityAdapter`和`UserAccount`业务身份，业务Module不改写。

## 2. 范围与排除项

本切片包含：

- 全局唯一用户名和密码凭据；不以姓名、手机号或邮箱作为稳定身份。
- 一次性初始化命令，创建首个本地账号、部门成员关系及可操作当前客户功能的初始角色分配。
- 用户名／密码登录、当前会话查询和退出。
- PostgreSQL持久化的不透明会话、会话到期、显式撤销和账号停用后的下一请求失效。
- 同源`HttpOnly` Cookie、写请求CSRF校验和数据库支持的登录失败限速。
- 前端登录页、启动时恢复会话、未认证路由跳转、退出，以及把401与网络故障分开显示。
- 继续支持`NODE_ENV=test`专用Bearer测试身份，不把它开放到开发或生产环境。

本切片明确排除：

- 开放注册、自助邀请、共享账号和匿名业务访问。
- 人员与权限管理页面、日常建号、禁用、重置密码、角色模板维护和跨部门授予；这些属于下一切片。
- 找回密码、邮件／短信验证码、MFA、长期“记住我”和第三方OIDC／企业微信登录。
- 生产部署、生产账号创建、真实数据迁移和真实秘密交付。

## 3. 方案选择

采用“数据库不透明会话＋同源Cookie”。登录成功后生成高熵随机令牌，浏览器只保存`HttpOnly` Cookie，数据库只保存令牌的SHA-256摘要。相比JWT，该方案无需刷新令牌、黑名单或浏览器本地存储，账号停用和退出可以从下一次请求起生效；当前Vue／Nest模块化单体没有必须使用无状态令牌的跨域消费者。

不采用仅开发Mock作为正式路径。Mock仍用于自动化测试，但不能解决真实密码、会话撤销和账号生命周期。也不在本切片实现完整人员管理后台，以免把认证、授权管理和组织管理三个Q2范围一次耦合。

## 4. 模型与不变量

现有`UserAccount`继续代表稳定业务操作者并保留历史审计引用。新增对象只承担认证责任：

| 对象              | 责任与不变量                                                                                          |
| ----------------- | ----------------------------------------------------------------------------------------------------- |
| `LocalCredential` | 一对一关联`UserAccount`；保存规范化用户名、版本化密码哈希和密码修改时间；用户名全局唯一、大小写不敏感 |
| `AuthSession`     | 保存令牌摘要、用户、当前部门、CSRF摘要、绝对到期时间、撤销时间和最后使用时间；不保存明文令牌或CSRF值  |
| `AuthThrottle`    | 按用户名摘要和来源摘要分别累计失败窗口及阻断时点；不保存提交的用户名原文、密码或完整来源地址          |

密码由Node内置`scrypt`生成版本化编码，随机盐至少16字节，派生结果64字节；比较使用恒定时间函数。首期密码长度为12至128个Unicode码点，不自动裁剪或改写密码。用户名先裁剪，再转为Unicode NFKC和小写，必须是3至64个ASCII字母、数字、点、下划线或连字符；展示名与用户名分开。

会话使用至少32字节随机令牌，绝对有效期12小时，不滑动续期。Cookie使用`HttpOnly`、`SameSite=Lax`和`Path=/`；生产环境必须启用`Secure`，开发环境仅允许本机HTTP关闭`Secure`。后端每次解析会话时重新读取账号激活状态、部门成员状态和最新`authorizationRevision`，因此停用账号／成员立即401，角色或范围变化由现有授权层在下一请求重新计算。

## 5. 初始化命令

根脚本提供交互式`pnpm auth:bootstrap-local`。命令只连接明确校验过的目标数据库，拒绝接受命令行密码参数或把密码写入日志；密码从隐藏交互输入读取，自动化场景只允许标准输入。命令要求操作者明确输入部门名称、用户名和展示名。

命令仅在不存在任何本地凭据时成功，事务内创建或复用同名部门、创建`UserAccount`、`LocalCredential`、激活的`DepartmentMembership`、当前客户权限的初始主管角色模板／Grant及角色分配。若数据库已有本地凭据、同名账号、冲突部门结构或部分初始化数据，则整体拒绝，不猜测合并，不生成第二个“首个管理员”。密码和会话令牌不进入审计正文。

这里的首个账号是系统初始化操作者；当前客户业务权限来自显式角色分配，不因“系统管理员”名称绕过Grant。下一切片启用人员管理后，账号创建、停用、重置和授权仍必须经过独立权限代码与审计。

## 6. HTTP与页面契约

| HTTP                       | 行为                                                                                         |
| -------------------------- | -------------------------------------------------------------------------------------------- |
| `POST /api/v1/auth/login`  | 接收用户名、密码和可选部门ID；成功设置会话Cookie并返回当前账号、可用部门、当前部门和CSRF令牌 |
| `GET /api/v1/auth/session` | 恢复当前会话；返回账号、当前部门、可用部门和CSRF令牌；无效／过期／停用统一401                |
| `POST /api/v1/auth/logout` | 要求有效Cookie和CSRF头；撤销当前会话并清除Cookie；重复退出仍清除Cookie且不泄漏会话状态       |

单个激活部门成员关系自动选中。存在多个激活部门且登录未指定部门时，返回`DEPARTMENT_REQUIRED`及仅包含可选择部门ID／名称的列表；用户选择后重新提交密码，不预先建立会话。指定无权部门与错误密码使用同一通用认证失败文案，避免枚举成员关系。

前端增加`/login`，只包含用户名、密码和必要时的部门选择。应用启动先调用`GET /auth/session`；有效会话进入原目标路由，无会话跳转登录页并保留站内返回地址。HTTP层将401发布为认证失效事件，页面跳转登录；只有状态0的请求才显示“无法连接服务”。登录成功后客户列表继续调用原API，不增加测试Authorization头。

所有Cookie认证的`POST`／`PUT`／`PATCH`／`DELETE`请求必须携带当前会话返回的`X-CSRF-Token`。登录接口不要求CSRF，但执行同源`Origin`／`Sec-Fetch-Site`检查；Bearer测试身份仅在`NODE_ENV=test`使用并继续走现有E2E路径。

## 7. 失败、安全与审计

- 用户不存在、密码错误、账号停用、成员停用和指定部门无效，对登录方统一返回`AUTHENTICATION_FAILED`，不暴露哪一项不匹配。
- 同一规范化用户名或同一来源在15分钟内连续5次失败后阻断15分钟；成功登录清除对应用户名失败桶，不清除来源桶中的其他账号风险。
- 被限速返回`LOGIN_RATE_LIMITED`和可用于界面倒计时的秒数，不返回账号是否存在。
- 会话不存在、摘要不匹配、到期、已撤销或账号／成员停用统一返回现有`UNAUTHORIZED`。
- CSRF缺失或错误返回403 `CSRF_INVALID`，业务Command不执行。
- 登录成功、失败限速触发、退出和初始化结果记录安全事件；不记录密码、明文令牌、CSRF值、完整Cookie或数据库连接串。
- 初始化、凭据、会话和限速迁移使用前向迁移；旧测试身份和现有客户／审计记录不得重写。
