# v6 运营系统优化基线

用户于2026-10-26指定以下需求为本轮开发基线，并明确替代原稿第二十一节第1条“仅整理、不实施”的限制：现在开始实施已确认且无歧义的需求，独立任务并行；多模态识别不在本轮。实际账号增权、数据库迁移执行、历史数据重编号及部署仍单独按目标和范围授权。

## 同轮补充确认：编号

1. 既有客户按创建时间先后补客户ID；旧线索和旧案件也改用新编号。实际历史重编号执行尚未授权。
2. 同一线索出现第二案时，首案保留无后缀原号，第二案为原号-02，其后顺序增加后缀。
3. 客户ID和单客户日序号超过999后都自然扩位到4位及以上，不截断、不回绕、不沿用999上限。
4. 保留UUID关联，不靠解析展示编号推导业务关系。并发唯一、重试幂等和上海时区边界继续适用。对原文其他真实业务歧义，仅暂停对应依赖并询问用户。

## 编号工程契约

- `Customer.id` 及所有外键继续是 UUID；新增展示字段 `businessId`。所有客户共用从 1 开始的持久序列，显示时至少补足三位，超过 999 自然扩位。历史客户按 `created_at ASC, id ASC` 定序，含已删除但仍保留的客户。客户详情、列表和创建响应展示 `businessId`；迁移前旧响应可缺少此字段，生产切换后的真实客户必须非空。
- 人工线索、CSV 线索和外录案件在同一事务里从 `(customer_id, 上海业务日)` 共享计数取号；格式为 `businessId + YYYYMMDD + 至少三位日序号`。使用创建时的上海日，计数超过 999 自然扩位。客户未完成编号初始化时拒绝创建，不能回退旧格式或临时编号。重试先查原幂等回执；同键重放不再取号。
- 正常公证出证建案通过 `Case.sourceLeadId` 读取线索编号，首案直接沿用；同线索第二案开始依次加 `-02`、`-03`，不改首案，也不消耗客户日序号。建案前核对全局客户序列已完成切换且关联客户ID非空，旧线索号不能绕过初始化门槛。用来源线索 UUID 锁与数据库唯一约束串行分配后缀；`Case.sourceNotaryMatterId`、证书和客户等既有关系继续校验。外录案件 `sourceLeadId = null`，只使用共享日序号。
- 切换草稿分为可审阅的 DDL／前向写入代码、历史预检、停写后的原子回填及开启新版本四步。DDL 中全局客户序列以 -1 表示未初始化；停写回填核对全部客户、线索和案件后，最后将序列种子设为客户总数，才允许新客户取号。Prisma 客户ID字段保持可空以匹配增量迁移；数据库约束触发器在序列可用后拒绝客户ID为空的新行或更新行。给已软删草稿补ID时，只在停写锁内确认旧删除保护触发器的身份及启用状态，事务性暂时停用这一条触发器，执行仅改 `business_id` 的更新，随即恢复；任何失败须回滚触发器状态。历史回填须先编号全部客户，再按客户和上海创建日对线索与外录案件按 `(created_at, 类型稳定次序, id)` 分配共享日序；正常案件沿显式来源线索 UUID，以 `(created_at,id)` 排序确定首案及后缀。来源缺失、关联不一致、旧号碰撞或无法确定归属时停止该记录，不凭商品、公证批次或展示号猜配。数据库实际执行、历史重编号与部署另需明确授权。
- 旧号保留为按实体类型及 UUID 唯一关联的 alias／映射，审计与已签发的幂等回执保持不可变。重放先以 UUID、动作及请求指纹校验旧回执，再经 alias 核验旧号归属，对调用方返回当前展示号；不得把旧号与当前号的字符串相等当成身份校验。法院案号、公证事项自身编号不变。

## 同轮补充确认：商品截图与费用

用户确认商品截图可在创建商品时一起填写，也可在商品行后补；允许待推送及推送后的在办阶段补传，已归档只读。每张截图关联稳定商品ID和精确材料版本，商品编辑不重造已有商品身份。当前关联变化不反写已引用的公证、案件材料。历史归属不明的原截图继续保留“待关联”，不按位置、名称或链接自动猜配。

已支付费用允许先作废，退款后补核对。原支付金额和凭证保留；作废不等于退款，退款未核实时明确显示“待核对”，不能自动调整为已退款或结清。

后续补充：已发起但未确认支付的费用也允许先作废，支付情况保持待核对。本轮支持部分及多次真实退款核对，每笔保留实际日期、金额及原费用关联。原系统费用面额／状态缺少真实实付明细时，以人工核实的实付金额和日期作为退款基准，不从面额推算实付；未核实保持未知，明确核实未付才为0。每笔退款留不可变记录、精确证明版本（如有）和操作审计，累计不得超过已核实实付；不覆盖原发起、原支付和原凭证。

## 同轮补充确认：案件CSV疑似重复

用户确认跨文件以“客户ID＋法院＋法院案号”相同提示疑似重复，运营核对后可明确确认继续，不自动合并案件或把法院案号设为全局唯一。仅对已知且合法的客户／法院／非空案号查当前部门可读案件，空值不作为重复依据。预览保留同文件其他有效行的疑似重复行号，即使该行未选中；提交在同一事务内重查并核对运营实际确认的完整候选集合，有新增或变化须重新预览、重新确认。同文件同一行已成功导入仍硬性防重，不得用疑似重复确认绕过；确认集合纳入批次幂等指纹。CSV重复核对须当前部门案件读取授权，不对无权账号泄露案件存在性和编号。

## 需求原文

一、总体目标

1. 一屏尽可能展示更多有效信息，但清楚、不混乱；操作简单、路径短。
2. 排版参考 Demo，以本次明确要求为准。三列、横向紧凑布局等新要求优先于 Demo 原有形式。
3. 减少大块空白、过大行距和内边距、重复标题、冗余说明及多层边框。
4. 不靠极小字体、隐藏必要信息或增加多层跳转达成“一屏”。常用内容尽量首屏可见，大量明细允许合理延伸。
5. 公共样式统一复用，避免每个模块各自一套尺寸。界面优化不改变数据真实性和权限边界。
   二、侧边导航调整
6. “日历”“数据报表”移入侧边栏的“工具栏”分组；结算中心、证物管理、客户管理保留在工具栏，设置保留在系统分组。
7. 原“案件”拆为同级的“我的案件”“全部部门案件”。工作台下依次为：线索库、公证阶段、我的案件、全部部门案件。
8. 不保留共同的“案件”父菜单，“我的案件”下面不能再出现“全部部门案件”。
9. “我的案件”显示本人负责案件；“全部部门案件”显示本人所属部门全部案件，不代表跨部门查看全公司案件。
10. 页面标题、面包屑、路由、导航选中状态、列表和计数保持一致。整理原页面内重复的“我负责/本部门全部”切换，避免进入“我的案件”后又切出部门全部数据。
11. 如保留阶段子菜单，其列表和计数随所在入口范围变化。可复用同一套列表组件，不必复制业务代码。
12. 去掉所有导航文字前的装饰图标和占位。同级菜单统一字号、字重、行高、内边距、文字起点和选中样式；数字计数右对齐。
13. 展开/收起箭头是操作控件，保留并统一，不与装饰图标一起删除。
    三、所有模块详情页紧凑布局
14. 常规字段优先三列“字段名＋字段值”展示；商品明细、多条记录、时间轴等不适合三列的内容，在下方使用紧凑表格或卡片。
15. 保留必要分组，减少重复标题、空白卡片及过大留白。
16. 图片、证件、协议等以名称、状态或缩略图作为入口，点击直接预览，不默认展开大图。
17. 多联系人、多权利主体和历史记录使用紧凑列表或摘要＋明细入口，不将无限内容硬塞首屏，也不增加不必要的操作路径。
18. 创建时间、更新时间、版本等辅助信息放在紧凑信息区，不独占大卡片。
19. 窄屏合理降列或换行，不挤压、遮挡、错位。已合适的布局直接复用。
    四、全局操作栏与固定按钮尺寸
20. 覆盖所有列表页、详情页、卡片、列表行和弹窗，不仅修改截图中的页面。
21. 同一作用范围的操作集中在同一行，统一紧凑高度、字号、间距和内边距；同类按钮使用固定宽度或统一尺寸档位，不能随页面忽大忽小。
22. 页面级操作放顶部操作栏；查询、清空放筛选区同一行；单条记录操作在对应行；卡片操作在标题行。不同作用范围不能混淆。
23. 常用操作一眼可见，不散落各处，不全部藏入“更多”。桌面端优先一行排齐；窄屏按统一规则换行，不重叠或裁切。
24. 主要、次要、危险操作视觉层级清楚，不缩小到难以点击。
25. 推进按钮优先使用清晰的2字或4字，例如“推送客户、移交公证、申请撤回、确认匹配”。长解释放在必要的简短提示或确认内容中。
26. 不为缩字改变语义：“申请撤回”不能变成已生效的“撤回”，“进入待出证”不能变成“完成出证”。保留校验、分支选择、权限、幂等和必要确认。
    五、精简说明卡片与名称
27. 移除“流程推进：下一步由运营核对线索后推送……”这类仅解释常规操作、没有独立业务信息的整块说明卡片。其他页面同类冗余内容同步检查。
28. 错误原因、缺少必填材料、权限限制、风险提醒和必要确认不能删除，应在相关操作附近紧凑展示。
29. 所有面向用户的“案件办理组”统一改为“案件系列”，包括菜单、按钮、标题、面包屑及说明。
30. 改名不改变分组业务、数据库关联或权限，内部技术命名非必要不重构。
    六、客户基本信息整合

现有七栏：客户资料、联系人与权利人、准入与身份、企业账号、合作协议、开票资料、办理历史。

1. 移除开票资料模块，其余内容合并成紧凑基本信息页面，避免七个二级页签反复切换。
2. 普通字段三列展示；联系人、权利主体、账号、历史采用紧凑列表或摘要，清晰分组。
3. 图片、证件、协议点击查看，编辑入口明确；编辑仅修改对应信息，不触发流程推进。
4. 顶层“权利资产”“结算记录”不在删除范围。布局合并不得泄露原本无权读取的资料。
5. Demo现有客户档案是两列，本次三列属于新要求，不机械照搬两列。
   七、移除客户开票资料模块
6. 删除客户页开票资料展示、录入、编辑入口，核查创建、保存、准入流程，不让已移除字段继续阻塞办理。
7. 本轮不清空历史数据、不直接删数据库列，不删除费用、结算、账单或其他发票功能。
8. 先检查依赖，解除不必要的页面和校验依赖。仍有真实业务依赖时报告影响，不填假值绕过。
9. 客户开票资料移除，不等于删除结算中心开票状态及真实财务记录。
   八、客户准入与企业账号权限
10. 所有普通运营可准入本部门全部客户，包括其他同事负责的客户，支持请假代办；不扩大到其他部门。
11. 企业账号创建权限留给运营主管，不下放给普通运营。
12. 服务端落实 customer.admit 动作与数据范围，不仅显示/隐藏按钮。准入所需的客户读取及证明材料操作应在授权范围内完整可办，不连带扩大其他编辑、删除权限。
13. 保留资料、证件、联系人等合法准入条件，移除开票资料依赖除外。
14. 当前企业账号创建共用内部人员管理权限，需要最小化拆分，不能顺带授予广泛的内部人员管理权限。
15. 企业账号读取、启停等动作不自动随创建权限扩大；保留客户已准入等前置条件，不擅自改变管理员职责。
16. 案件继续“本部门可读、本人可办”；金额查看、案件导出、报表导出分别授权。
    九、客户ID与线索、案件编号

已确认：

1. 新增业务展示字段“客户ID”，从001自动递增，两部门共用一套序列，不同客户不能重号；保留UUID主键及外键。
2. 新编号格式：客户ID＋创建日期YYYYMMDD＋该客户当天三位序号。例如00120261026005，不带原LD-/CA-前缀。
3. 线索创建时生成，人工创建和CSV导入均覆盖；日期为线索创建日期，不在转案时改成转案日期。
4. 一条线索正常转一个案件，案件原样沿用线索编号，不重新取号、不加后缀。法院案号独立，不受影响。
5. 同一线索转多个案件时，才使用“原线索编号-01、-02……”区分。
6. 外录案件按客户及外录创建日期，从该客户当天同一序列取号，不虚构线索。例如线索005→外录006→新线索007。
7. 最后三位是当天新分配序号，不严格等于线索数量。正常转案和多案后缀不再次消耗序列。
8. 服务端保证并发唯一、重试幂等；不能靠前端数量生成编号，不能用解析编号代替数据库关联。日期核对现行上海时区规则，不悄悄改变边界。
   仍待确认：

- 已有客户补号顺序，旧线索、旧案件是否保留旧号。
- 第二个案件出现时，第一个不带后缀案件是否改成-01。
- 客户ID或单客户日序号超过999如何处理，以及扩位格式。

4. 统一行高、列对齐及间距，保障编号、状态、店铺、商品入口、常用操作可见，提高每屏线索数量。
   十一、截图归入对应商品

    十四、证物管理专项布局

    十五、案件列表横向排版与批量操作

现状核对：案件列表第一格堆叠编号、办理按钮、负责人及来源说明；尚无勾选数量工具栏和批量归档；已有的是按当前筛选结果导出。案件系列与证物批量操作不能算案件批量办理。

1. 编号、负责人、操作及辅助说明重新分配为清晰的横向列或横向区域，不全部纵向堆在第一格。
2. 使用统一紧凑字号、行高和列间距；按钮固定尺寸档位、横向对齐，避免一行被操作内容撑高。
3. 明确增加三类批量能力：批量导入、批量导出、批量归档。本轮不新增批量推进流程或批量分配负责人。
4. 页面工具栏集中展示入口；列表提供勾选和选中数量，批量操作对象清楚。未选择时适当禁用并提示，不让用户找不到可做什么。
5. 批量导出明确区分“选中案件”和“当前筛选结果”，保留读取、金额和导出权限约束，不混淆范围。
6. 批量归档逐案检查权限、当前状态和版本；清楚反馈成功、失败及原因，失败项可定位，不能部分失败却提示全部成功。
7. 明确分页、筛选变化时的选择范围，执行前展示对象和数量，避免误操作未选案件。
   十六、案件CSV批量导入

现状核对：尚未发现案件文件批量导入实现，已有单案外录；线索CSV创建待推送线索，不能代替案件导入。

1. 本轮支持CSV批量录入外部已有案件，允许填写案件当前所处阶段，不要求补造线索、公证前序。
2. 基于现有单案外录能力核对字段和合法阶段要求，保留真实客户、权利主体、来源及相应业务资料，不能虚构已经完成的前置节点。
3. 提供明确模板、导入预览、逐行字段校验、错误定位及结果反馈，防止重复导入；具体字段和处理边界有歧义先问。

5. 使用已确认的外录编号规则，与该客户当天新线索共用序列，不生成虚构来源线索。
6. 文件格式本轮为CSV，不顺带扩成PDF识别或多模态模型项目。
   十七、任意阶段提前归档

已确认：案件无论当前处于哪个阶段，都允许提前结束办理并归档，单案和批量均适用。

1. 这是业务规则变更，不只是恢复按钮。现行仅待归档且有结案资料才能归档的限制，应增加合法的提前归档路径，不能伪造结案资料来通过旧校验。
2. 案件各阶段列表及详情提供清楚、一致的归档入口；已归档案件不重复归档，缺少权限不得放行。
3. 保留原阶段、历史、材料、案件关联及财务记录，记录操作人、归档时间和原因，区分提前结束与正常流程完成。
4. 归档停止诉讼办理和相关后台自动推进，检查与开庭等自动任务并发时的状态边界，不能归档后又被自动推进回办理中。
5. 仍遵守“本部门可读、本人可办”和具体归档权限，不因任何阶段可归档而允许办理他人案件。
6. 不自动将未完成诉讼步骤标成已完成，不自动生成结案金额，不把归档当成已收款、已付款或债务结清。
7. 归档记录继续可查询，保留追溯证据；恢复办理等未明确的新能力不自动加入本轮。
   十八、归档后的费用、结算与取消费用

已确认：提前归档只停止诉讼流程，不抹掉债权债务；允许继续办理未完成的费用和结算。

1. 按原财务动作权限继续办理，不能因归档扩大财务权限。
2. 调整当前因案件已归档而拒绝新发起结算的限制；仍保留适用的金额、资料和业务校验，不把“可继续财务办理”变成无条件发起。
3. 已有费用、账单及收付款关联保留，案件归档不自动清零或结清。
4. 取消费用应有明确入口，不继续污染有效费用和结算结果，不能仅从页面隐藏。
5. 尚未入账单、未实际收付款的取消费用：允许逻辑删除，保留操作记录，从有效费用、可选结算项及对应计算中排除。
6. 已关联账单或已有收付款的费用：通过作废或冲正处理，保留原记录和关联，不直接抹掉；历史账单、真实资金记录与调整结果必须可追溯。
7. 取消、删除、作废、冲正时检查当前状态、关联和权限，防止并发操作造成重复计费或账目不一致。具体实现优先复用现有能力，不扩大成无关财务重构。
8. 上述规则同样适用于提前归档后的费用处理，不要求为了处理财务而把案件重新推进诉讼流程。
