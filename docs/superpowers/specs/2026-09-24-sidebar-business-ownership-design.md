# 线索库与公证阶段侧边栏业务归属修复设计

日期：2026-09-24  
状态：已实现并完成隔离测试，待与主线切片集成

## 目标与依据

运营端侧边栏按业务对象分开显示“线索库”和“公证阶段”。用户提供的 Demo 截图确定布局和名称；Demo 的数量与未实现节点不进入正式系统。正式业务以 [LD 线索 Spec](../../spec/v0.1/modules/leads.md)、[NT 公证 Spec](../../spec/v0.1/modules/notary.md)和 [SD-02／SD-37](../../spec/v0.1/DECISIONS.md)为准。

当前 `NotaryMatter` 已是独立实体，拥有 `PENDING_EVIDENCE`、`WAITING_UNBOX`、`UNBOX_REVIEW` 三个已实现阶段；正式系统只有事项详情而没有事项列表。`AppShell` 将 `/notary-matters/:id` 误归线索导航；线索侧栏展示 `TRANSFERRED_TO_NOTARY`，使来源线索与公证事项混在同一个工作队列。一个来源线索可以对应多个公证事项，不能以线索数代替事项数。

## 导航归属

| 一级区域          | 已实现入口                                       | 对象和计数                     |
| ----------------- | ------------------------------------------------ | ------------------------------ |
| 工作台 → 线索库   | 全部、待推送、线索待审核、线索待确认、线索已归档 | 线索；全部为四种线索库状态之和 |
| 工作台 → 公证阶段 | 全部、待取证、待取件开箱、开箱待审核             | 公证事项；每个批次算一件       |
| 工具栏            | 客户管理                                         | 沿用现有客户页面               |
| 系统 → 设置       | 公证处、人员与权限                               | 沿用现有授权与路由             |

“我的案件”、结算中心、证物管理、日历、报表及公证后续节点等尚无正式可用列表的入口保持隐藏；对应切片交付时再添加。导航项与徽标必须来自有权范围的真实 API，不复制 Demo 的种子数字。桌面和移动端使用同一导航结构，两个工作台组可展开，当前路由所属组自动展开；父项点击进入该对象的“全部”列表。`/notary-matters/:id` 的激活态和面包屑归“公证阶段”，来源线索详情仍归“线索库”。

## 线索库列表口径

新增 `GET /api/v1/leads?view=LIBRARY`，仅用于线索库工作队列。其 `items`、`total` 和 `counts` 在同一 `lead.read` 数据范围内排除 `TRANSFERRED_TO_NOTARY`；四个侧栏状态的数量之和等于“全部”数量。`status` 仍可筛选四个线索库状态；`view=LIBRARY&status=TRANSFERRED_TO_NOTARY` 返回 400。未传 `view` 的既有 API 行为保持兼容，供已有调用方查询所有线索状态。

移交后来源线索继续持久化、只读，并保留直接详情 URL 和公证详情里的来源链接；它不再出现在“线索库 → 全部”。不改 `LeadStatus` 枚举、移交事务、材料引用或历史审计。线索库的“已归档”仍只表示线索自身的两种归档结果，不借用公证归档。

## 公证事项列表契约

新增 `GET /api/v1/notary-matters?page=1&pageSize=20&stage=PENDING_EVIDENCE`；`stage` 可省略，参数限当前正式 `NotaryMatterStage`，未知值返回 400。响应为 `{items,total,page,pageSize,counts}`，`counts` 是同一可见范围内按阶段统计的事项数量，含零值；`total` 随筛选变化。每项只返回列表需要的 `id/businessNo/stage/createdAt`、来源线索 `id/businessNo` 和公证处 `id/name`。排序为 `createdAt DESC, id ASC`。

读取范围与既有 `GET /notary-matters/:id` 完全一致：内部账号、当前部门及 `lead.read` 对来源线索的 SELF／TEAM／DEPARTMENT 范围。服务端对列表、总数、各阶段计数使用同一个谓词；无权限返回 403，不能通过徽标推断其他部门或其他人的事项。一个来源线索对应两个事项时，线索详情保留一个来源身份，公证列表和计数显示两件。查询为只读，不增加迁移或新的授权 Action。

前端在统一 API 层校验响应后显示公证列表。列表支持阶段切换、分页、详情、来源线索返回，以及加载、空态、失败重试。移交成功仍导航至事项详情；从那里可以进入公证阶段列表。完成取证或开箱后刷新事项与侧栏计数，不依赖线索状态推断公证阶段。

## 与并行切片的边界

本修复在独立 worktree 基于 `main@459b78e` 开发，不修改正在进行的 `CORE-NT-003` 工作目录。NT-003 若新增阶段，合并时将其已落地阶段加入公证列表的允许值、标签与侧栏选项，并在集成候选上重新验证；不得提前显示尚未交付的 Demo 节点。路线图唯一 Current／Next 仍由核心业务切片维护，本修复只在对应 Spec 和验证记录中记载归属调整。

## 验收

1. 运营移交一条线索后，线索库“全部”和四个状态计数减少相应一条；原线索详情可从事项详情追溯。两个取证批次在公证列表和计数中显示两件。
2. 待取证 → 待取件开箱 → 开箱待审核时，公证列表筛选、徽标和详情一致；未知阶段与非法分页明确拒绝。
3. 无权、跨部门和其他 SELF／TEAM 范围的事项既不出现在列表，也不计入任何徽标；页面不得把请求错误显示为空列表。
4. 线索与公证导航的高亮、面包屑和移动端展开行为正确；未实现的案件及公证节点没有死入口。
5. 聚焦服务／Controller／前端测试和真实 PostgreSQL／浏览器用例通过；与 NT-003 集成形成新 tree 后重新核对阶段选项和回归。
