# 活 Spec、AI 留痕与开发前审计设计

日期：2026-09-16；任务：GOV-LIVE-SPEC-001；批准依据：用户确认按本设计范围执行。

## 目标

在不新增重复管理平台的前提下，让业务 Spec 能随已批准需求持续演进，让每个 AI 开发任务都能恢复上下文、追溯依据和核对真实结果；在首批任务拆分前修正已发现的 Spec 逻辑问题，并清理明确可再生成的本地运行产物。

本设计不授权首批业务代码实现。完成本设计、现有 Spec 修正、机械检查和清理后，才为“授权登录→客户草稿→编辑与判重→证件上传→正式准入→按权限查询与历史留痕”生成实施计划。

## 方案比较与选择

| 方案                   | 做法                                                                                  | 优点                                          | 代价与结论                                              |
| ---------------------- | ------------------------------------------------------------------------------------- | --------------------------------------------- | ------------------------------------------------------- |
| A 复用现有文档与 Git   | Spec 维护目标规则；实施计划记录任务；项目状态记录当前现场；验证报告与提交记录保存证据 | 无重复录入，AI 恢复路径清楚，符合现有项目规范 | **采用**                                                |
| B 新增统一 AI 工作日志 | 每次操作另写一份连续日志                                                              | 表面集中                                      | 与项目状态、计划、验证和 Git 重复，容易相互不一致，拒绝 |
| C 建任务／审计平台     | 用数据库或外部系统记录任务和模型活动                                                  | 可扩展统计                                    | 当前阶段过重，也不能替代 Spec、测试和 Git，拒绝         |

采用方案 A。AI 留痕是现有事实来源之间的稳定关联，不是要求模型把聊天或终端全文复制进仓库。

## 活 Spec 规则

### 权威来源

- 当前目标行为由 `docs/spec/v0.1/` 下的 REQ、AC、SD、DOMAIN 和技术设计共同表达。
- `DECISIONS.md` 保存已批准决定和替代关系；后续决定不能静默改写早期决定的历史含义。
- `READINESS.md` 只回答范围是否可拆任务、可编码或可联调，不复制业务字段和流程正文。
- `COVERAGE.md` 维护决定、需求、设计、实现和测试之间的追踪关系。
- `project-status.md` 只保留当前现场、最近有效证据和下一步，不承担永久流水账。
- Git 提交和带日期验证记录保存已经发生的变更证据。

### 变更顺序

业务规则在开发中改变时，按以下顺序处理：

1. 登记批准来源、原意和影响范围；未经确认的想法保持为缺口，不改成已批准规则。
2. 更新或新增 SD，并在原 REQ／AC／DOMAIN 中就地修改；不复制一套新版本 Spec。
3. 检查受影响的接口、数据约束、权限、历史兼容、测试和实施任务。
4. 更新 READINESS、COVERAGE 和实施计划中的任务状态。
5. 再修改实现和测试；代码不得反向覆盖获准 Spec。
6. 用实际命令、结果和提交回填证据；设计完成、实现完成、测试通过和获准发布分别记录。

若已开始的任务因 Spec 改动失效，只阻断受影响任务。未受影响任务继续执行，不能把局部变化扩大为全项目停工。

### 机械检查

新增根脚本入口 `pnpm spec:check`，由一个聚焦的 Node 脚本完成以下确定性检查：

- REQ标题唯一，AC、BQ和SD编号集合符合当前声明；
- 文档引用的单项 REQ／SD 必须存在；
- Markdown 表格同一表内列数一致；
- 当前入口不得引用已被后续版本替代的技术基线；历史验证段落不受此规则误报；
- README 声明的当前 SD／TD 版本与 DECISIONS、TECHNICAL-DESIGN、READINESS 一致；
- INPUT、SD、REQ／AC、TD 和 READINESS 的必要追踪入口存在。

脚本只报告结构和当前版本漂移，退出码非零阻断任务拆分和交付。它不判断业务规则是否合理，不得以通过结果替代语义审查。

### 语义检查

每次切片拆任务前，由执行者对目标范围检查：

- 同一字段是否存在两个权威来源；
- 状态、动作、材料、任务和资金是否被混成一个状态；
- 权限是否同时包含动作和数据范围，并覆盖所有查询、文件和后台入口；
- 历史版本、并发、幂等、撤权和失败恢复是否有验收场景；
- 缺外部条件是否只阻断真实依赖范围；
- 待审核规则是否被误当成可编码规则；
- 页面优化是否新增未获准的必填项、页面、审批或确认。

发现问题时先修改 Spec 和追踪状态，再生成或更新任务计划。

## AI 任务留痕

每个实施计划任务包含以下固定字段：

```yaml
task_id: <稳定任务编号>
spec_refs: <REQ/AC/SD/TD>
base_ref: <开始提交>
scope: <允许修改的准确路径>
risk: <Q0/Q1/Q2>
acceptance: <可观察验收>
checks: <实际命令>
status: PLANNED | IN_PROGRESS | BLOCKED | IMPLEMENTED_UNVERIFIED | VERIFIED
result_ref: <完成提交或工作区快照>
evidence: <验证记录位置>
```

执行规则：

- 开始前读取项目状态、任务卡、关联 Spec，运行`git status`和`pnpm context:check`。
- 开始时在`project-status.md`登记当前任务、基线、范围和门禁；实施计划勾选真实进度。
- 每个可独立验收任务使用测试先行，相关实现与测试在同一任务中完成。
- 中断时记录最后成功动作、失败证据和唯一下一步，不把未验证实现写成完成。
- 完成时记录真实检查、结果提交、未运行项和阻断项；Git提交信息包含任务编号或明确功能范围。
- 恢复时以文件、Git和验证证据为准，不以聊天记忆为唯一来源。

不记录或提交秘密、完整终端日志、真实证件内容、模型隐藏推理或无法观测的额度数据。

## 准入状态

首批闭环使用三层状态，避免“可以计划”和“已经能真实联调”混淆：

| 状态                   | 含义                                                                    |
| ---------------------- | ----------------------------------------------------------------------- |
| `PLAN_READY`           | 需求、设计、依赖和验收足以拆成任务；不表示允许编码                      |
| `IMPLEMENTATION_READY` | 已获得编码授权，相关安全门禁和本任务内部依赖已满足；可以实现明确范围    |
| `INTEGRATION_BLOCKED`  | 内部接口和受控替身可开发，但真实SSO／对象存储／外部系统联调等待明确条件 |

权限、共享库部门隔离、敏感证件、文件访问和数据库结构属于Q2。它们进入`IMPLEMENTATION_READY`前必须完成独立安全设计复核；E01／E02 未齐时不得把受控替身写成真实接入完成。

## 文件清理边界

批准删除以下位于项目根目录内、已核验为忽略且可再生成的目标：

- `.tmp/`
- `.local/`
- `frontend/.local/`
- `playwright-report/`
- `test-results/`
- `backend/dist/`
- `frontend/dist/`

删除前再次解析绝对路径，确认每个目标都位于项目根目录内且与上述精确路径一致。删除后记录文件数、总大小和可恢复性：这些目录不受Git跟踪，不能从提交恢复，但可由对应构建、测试或临时检查重新生成。

明确保留：根、前后端`.env`文件，`node_modules/`，`backend/src/generated/`，Demo，锁文件，补丁，源码，数据库卷，以及承担历史证据或当前引用的文档和实施计划。不使用通配符扩大清理范围。

## 首批计划边界

书面设计复核通过后，实施计划只覆盖以下最小闭环：

> 授权语境与部门隔离基础 → 客户草稿 → 编辑与判重 → 客户证件版本 → 正式准入 → 权限内列表／详情 → 自动审计与历史投影。

计划必须把实际SSO和实际对象存储适配任务标为外部条件任务；在条件未齐时，其他已通过Q2门禁的内部规则、数据库约束、接口契约和受控集成测试可以独立安排。案件、结算、报表、OCR和通用权限平台不进入首批。

## 错误和恢复

- Spec检查失败：不刷新快照掩盖错误；修正文档或追踪关系后重跑。
- 任务执行发现规则矛盾：将任务标为`BLOCKED`，保留失败证据，只暂停受影响范围。
- 清理目标路径不一致、超出仓库或出现未核验文件：停止删除并重新审计。
- 已清理生成物后需要运行：通过锁定项目命令重新生成，不从不明来源恢复旧产物。
- 活Spec变更造成实现不兼容：新增迁移／兼容任务和恢复策略，不静默修改历史数据。

## 验收

本治理范围完成时必须满足：

1. SA-01～06全部在现有唯一Spec入口修正，历史验证记录未被伪改。
2. `pnpm spec:check`在故意制造重复REQ、无效SD引用和当前版本漂移时失败，在当前Spec上通过。
3. 项目状态、活Spec规则、实施计划任务字段和验证记录职责没有重叠冲突。
4. 七个批准清理目标已删除；保留项仍存在，Git跟踪文件无误删。
5. `pnpm context:check`、`pnpm format:check`和Git差异检查通过；检查脚本变化还须运行对应单元测试及`pnpm verify`。
6. 首批计划的每个任务都能指向具体REQ／AC／SD／TD、准确文件、风险级别、测试和外部阻断，且无占位任务。

完成以上事项仍不表示首批业务已实现、真实SSO／存储已接入或生产获准发布。
