# CORE-LD-004 客户判定不侵权并归档设计

状态：业务方向、后续撤回顺序和本设计已由用户确认；待按实施计划开发验证。依据为 REQ-LD-003、SD-13／37／38／40、[核心业务字段与材料契约](2026-09-21-core-flow-field-material-contract.md)以及已运行的 CORE-LD-003 客户审核实现。

## 目标与边界

本切片只完成一项客户结论和一次主要状态变化：本企业当前有效的客户账号对已推送的 `WAITING_REVIEW` 线索填写不侵权原因，提交 `NO_INFRINGEMENT`，线索原子进入 `ARCHIVED`。服务端记录 `archiveType=NO_INFRINGEMENT` 和归档时间；客户与获权运营均能回看结论、原因、时间、审核人和允许查看的附件。成功后普通审核入口不能再次提交。

已确认的纠错流程按 SD-40 在紧随其后的 CORE-LD-007 交付：运营申请不改变原归档，原客户企业的有效获权账号确认后才撤回，保留历史并允许重新审核。CORE-LD-004 不实现申请、确认、重开或第二次审核，不显示尚不可用的撤回按钮，也不以本切片完成冒充客户审核及纠错闭环完成。CORE-LD-005／006、其他归档类型、批量审核和完整客户门户继续后置。

## 方案选择

1. **复用现有客户审核 Command 与不可变决定（采用）**：`POST /client/leads/:id/reviews` 增加明确的 `NO_INFRINGEMENT` 分支；同一客户身份、企业范围、推送事实、当前状态、版本、事务、幂等和一条线索一次有效审核规则继续复用。原因、归档类型和归档时间保存在现有不可变 `LeadReviewDecision`，避免在线索主档另存可被覆盖的归档原因。
2. **另建客户归档 Command（不采用）**：同一次审核选择被拆成两套权限、并发和幂等逻辑，容易使两种结论在授权与回放上漂移。
3. **通用撤回／工作流引擎（不采用）**：会把 CORE-LD-007 的跨角色纠错和其他域的重开规则提前并入本切片，超出已确定的单次正常状态变化。

现有 `LeadReviewDecision.leadId` 一对一唯一约束在本切片仍表示“尚未撤回前一条线索仅有一次客户决定”。CORE-LD-007 的验收必须包含前向迁移：去除这一阻碍多轮审核的唯一约束、保留全部旧决定与回执，并用新的不可变撤回记录区分当前有效决定；不得删除或改写 CORE-LD-003／004 历史。此要求是 CORE-LD-007 的明确交付门槛，不在 CORE-LD-004 预建空表或未启用入口。

## 请求、事实与迁移

沿用现有端点与 `Idempotency-Key` 请求头（1～128 字符）：

```http
POST /api/v1/client/leads/:leadId/reviews
Idempotency-Key: <唯一请求键>

{
  "result": "NO_INFRINGEMENT",
  "reason": "经核对，该商品未使用我司权利标识",
  "expectedVersion": 2
}
```

`reason` 按 `LongText` 规则去首尾空白，规范化后须为 1～5000 字符；空白、超长、非字符串均返回 `VALIDATION_ERROR`。`INFRINGEMENT` 请求保持原结构，不接受原因。服务端指纹对原 `INFRINGEMENT` 请求保持 CORE-LD-003 的既有计算方式，以便已存在的成功回执继续原样重放；`NO_INFRINGEMENT` 指纹加入规范化原因。相同键异结论、异原因或异版本均为 `IDEMPOTENCY_CONFLICT`。

以前向、分阶段 PostgreSQL 迁移扩展 `LeadReviewResult.NO_INFRINGEMENT`，并为 `LeadReviewDecision` 增加可空的 `reason`、`archiveType`、`archivedAt`。数据库约束要求：旧 `INFRINGEMENT` 决定的三个新字段均为空；新 `NO_INFRINGEMENT` 决定的原因非空且不超过 5000 字符、`archiveType=NO_INFRINGEMENT`、归档时间非空。已有不可变触发器继续拒绝决定的 UPDATE／DELETE；回执不可变约束、企业／部门／账号绑定外键继续有效。旧决定无损升级，无需回填伪造归档事实。

`Lead` 仍只承载当前状态和版本。审核决定是结论、原因和归档事实的唯一权威来源；同一服务端时间写入决定与归档时间。响应对原 `INFRINGEMENT` 分支维持既有结构；不侵权分支返回 `status=ARCHIVED`、新版本及 `reviewDecision={result,reason,reviewerDisplayName,decidedAt,archiveType,archivedAt}`。不另存可与决定漂移的线索归档原因副本。

## Command 与失败语义

在现有 Serializable 审核事务中：重新读取真实 `CLIENT` 账号、当前有效企业绑定与客户 `ADMITTED` 状态；先按操作者／动作／幂等键检查回执；再锁定目标线索并确认同企业、同部门、已推送、`WAITING_REVIEW` 和 `expectedVersion`；条件更新状态及版本，创建不可变决定和回执，最后提交。成功审计以不可变决定为准，回执保存首次成功响应快照。序列化冲突沿用有限重试，不跳过任何重新校验。

同键同请求返回原快照，不产生第二次归档或决定。不同键竞争仅一方成功；旧版本返回 `VERSION_CONFLICT`，已改变的状态返回 `INVALID_STATE`，跨企业／未推送对象返回不泄漏存在性的 `RESOURCE_NOT_FOUND`。账号、绑定或客户准入失效从下一次请求起拒绝，包括重放请求。决定、回执或状态写入失败时全部回滚；原因绝不只停留在前端或审计日志。

## 查询、附件与页面

客户端“待我审核”仍仅包含本企业 `WAITING_REVIEW`；“已处理”增加本企业 `ARCHIVED` 且具有 `NO_INFRINGEMENT` 不可变决定的线索，并继续包含既有 `WAITING_EVIDENCE_DECISION`／`INFRINGEMENT`。详情与截图下载同步扩展这一精确条件，仍由服务端逐次校验当前账号、企业绑定、客户准入、线索归属与材料版本；不能让其他归档类型或其他企业借 `ARCHIVED` 状态进入客户范围。客户端 DTO 不包含内部负责人、团队、备注或内部审计字段。

客户详情明确提供“确认侵权”和“判定不侵权”两个实际分支；不侵权要求填写有红色必填提示的原因，提交前说明“本次提交后线索将归档，当前版本不能在页面直接撤回”。取消确认不写数据。提交期间禁用动作并显示加载；网络结果不明时保留原因和幂等键安全重试；版本／状态冲突提示刷新，成功后重新读取并显示归档结论、原因、时间和审核人。对已归档详情只读，不显示未实现的撤回操作。

运营列表沿用已有 `ARCHIVED` 阶段；获 `lead.read` 范围覆盖的运营详情显示相同客户决定和归档事实，不向运营开放代录客户结论。内部列表、详情、客户端 API 类型和响应解码器都必须识别新增分支，但原侵权回执响应继续可解析。

## 验证与后续交接
