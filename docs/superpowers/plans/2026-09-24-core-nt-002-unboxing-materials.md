# CORE-NT-002 开箱材料实施计划

**目标：** 真实上传开箱照片并由有权运营提交，事项从`WAITING_UNBOX`进入`UNBOX_REVIEW`，刷新后仍可查看及下载。

**基线：** 本地`main@eb7df602`；唯一Current为CORE-NT-002。业务边界见[小粒度设计](../specs/2026-09-24-core-nt-002-unboxing-materials-design.md)。

1. 先补后端失败测试：开箱Command的状态、版本、权限、材料版本、幂等、并发和回滚；材料上传／读取的事项授权及格式限额。确认测试因能力缺失而失败。
2. 添加前向Schema迁移：开箱事实、材料所有者／类别、权限动作和`UNBOX_REVIEW`阶段；在独立测试库随机临时schema先运行迁移链、上一支持schema、失败回滚及重试探针，再部署到正式测试schema。
3. 扩展既有材料服务与公证事项Command、DTO、Controller、审计／回执和详情读取；保持事务内当前Actor、来源范围及材料可用性重校验。运行后端聚焦测试、权限目录契约及类型检查。
4. 同步前端严格API解码与事项详情：真实文件上传、必填提示、提交加载／错误反馈、开箱记录与下载。运行API与组件聚焦测试。
5. 增补隔离数据库和真实浏览器主链：运营登录→已有待开箱事项→上传→提交→刷新→下载；加入跨范围与重放反例。运行`check:fast`及受影响检查。
6. 高风险迁移／授权／事务任务独立Review；修复后形成稳定候选并作最终Review。按实际风险执行正式Level 3门禁、迁移专项和数据库型浏览器验收；结果写入既有VALIDATION，门禁通过后才更新路线图完成态和Current／Next，最后做上下文与文档检查。

**不做：** CORE-NT-003审核、外部公证处门户、OCR／人工改号、混包／ZIP批量、出证或案件动作；不触碰开发／生产数据库，不推送或合并。
