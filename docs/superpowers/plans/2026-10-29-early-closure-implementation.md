# 提前结案至待归档：数据与后端实施草案

> 2026-10-29 只读核对后的实施计划。此文件不表示迁移、接口或真实 PostgreSQL 已实施或验收。依据为同日[需求检查点](../specs/2026-10-29-case-closure-archive.md)；现有 `archive_note` 与停用旧提前归档的未提交修改是本轮现场，实施时保留并合并，不回退、不重写旧迁移。

## 目标、边界与先决决定

案件从 `PENDING_MATCH`（案件待匹配）至 `EXECUTING`（强制执行中），有权用户提交结案日期、结案金额、结案文书、付款类型及付款记录后，案件进入 `WAITING_ARCHIVE`。后续结算更新追加资料及付款事实，正式归档才写入 `ARCHIVED`。不得补造执行结束、变造历史提前归档事实或覆盖既有文书/财务版本。已从外部录入 `WAITING_ARCHIVE` 的案件继续使用原合法根；旧提前归档 `case_early_archives`/回执的同键回放继续有效，新键一律拒绝。

**需要业务确认后才能固定字段和迁移的事项：**需在实施时核对有效付款的来源及既有记录关联，并接入客户回款、律师开票及被告诉讼退费的真实状态来源；是否涉及结算按用户提供的表单记录。提前结案不以已付款为前提，允许尚未付款。确认前不将账单创建、费用登记、截图上传等同收款或开票。金额比较采用本案有效、未撤销、可审计的同币种实收记录之精确十进制合计；明确 `KNOWN 0.00` 与 `PENDING/UNKNOWN` 分开。用户已明确有效付款合计达到结案金额即结清，故金额比较采用 `>=`；是否需要独立提示超额不在当前要求中。

## 分片实施

1. **契约与数据来源。** 确认上列未决项，并逐项标注既有表是否有真实“到账/开票/转成本”事实。若无，新增独立的本案实收、诉讼退费状态、客户回款与律师开票的不可变事件表和当前投影；“不涉及”也作为有操作者、时间和版本的明确决定记录。不要在既有 `FeeRefundReconciliation`、账单或 `CaseSettlementLaunch` 上偷换语义。
2. **前向迁移。** 增 `case_early_closures`（case/department 唯一；源阶段和源版本；结案根/操作者/审计/时间）及命令回执；在 closure head/version 建合法根引用和复合 FK。付款记录表至少含 case/department、金额 decimal(16,2)、付款日期、付款人、收款人、付款类型/关联、精确截图 content version、状态与撤销/冲正来源、操作者和审计；不直接 UPDATE/DELETE 历史付款。为结案更新版本绑定所选付款事实版本/集合，防止更新时漏失或跨案引用。为财务确认建立独立带版本来源的行/事件及“不涉及”决议。增加早结案 transition/final/stop-litigation 守卫，前向接续各阶段终点函数与原 source checks；保留旧早归及外录 `ARCHIVED` 数据原状。`archive_note` 只使用本轮现有未提交迁移，不另造冲突列。
3. **命令与权限。** `POST /cases/:id/early-closures` 录入必填结案资料及所选材料版本、`POST /cases/:id/closure-settlement-updates` 在待归档追加付款/结算资料、现有 `POST /cases/:id/archive` 做正式归档。读取接口返回当前结案/付款/财务来源、版本和逐项阻断原因；旧 `early-archives` 只保留历史回放。内部身份、部门/负责人/团队范围、现有 `case.closure.record/correct` 与 `case.archive` 权限须逐项映射；早结案如需新 Action，应同步授权配置和数据库 actor guard，不能仅靠按钮隐藏。
4. **单事务顺序。** 以 `Serializable` + `cases ... FOR UPDATE` 开始；服务端授权、按 actor+command+key 查旧回执并核验 fingerprint；重读 stage/version/source chain；验证文书与截图精确版本；写审计、早结案/付款事实及 closure 版本/引用，CAS 案件版本与阶段，再写回执。`CORRECT`/结算更新只追加版本、保留前文书及付款事实，更新后仍 `WAITING_ARCHIVE`。正式归档锁同一案件及本案财务/付款状态，核对 closure 当前版本和所有状态版本，在同一事务内复算有效付款；未知金额拒绝，已知零金额免三项资金校验，正金额先结清再逐项核对。归档前后都要以同一 DB 谓词防止并发付款撤销/状态回退，不能靠客户端预检；冲突按现有 `P2034/40001` 策略有限重试，重试重读所有条件。回执唯一约束承担并发同键去重；异 payload 同键报冲突，跨账号/跨部门不得借回执越权读取，归档后可回放原结案/更新回执而不得再次写事实。
5. **读模型与批量。** 待归档结算更新和归档能力由服务端计算；未合并案件逐案办理，合案主案一次办理；逐案权限、状态及版本校验，不把单案失败当作其他案成功，也不调用停用旧批量早归入口。合案主案应结金额已包含原案金额；只累计原案实际回款及开票的分配记录，每条分配计算一次。原账和材料保留在原案，不凭截图推定收款。

## 必须覆盖的真实 PostgreSQL 反例（以后获准的独立库）

- 空库完整迁移链、上一支持 schema 的合成旧数据升级、迁移中途失败原子性与前向重试；旧提前归档事实/回执同键回放、外录 `WAITING_ARCHIVE` 正常结案归档、外录 `ARCHIVED` 及旧历史均不回填/改状态。
- 对 `PENDING_MATCH`、起诉各阶段、开庭、判决/二审/重审、执行申请、`EXECUTING` 各取一条合法源，提交新结案后版本连续、stage 变待归档，原诉讼 facts 不变；缺 fact/receipt/audit、伪造 `case_execution_finishes`、跨案/跨部门锚、漏字段、非当前版本、非法日期与直接 SQL stage 跳变均拒绝。
- 已提前结案的案尝试后台 `advanceDue`、手动开庭推进、补造判决/执行 fact 或旧早归新键；必须拒绝。正常未结案案件的后台推进仍成功。新旧早归互斥；历史旧归档无需新增 closure。
- 文书和付款截图使用非本案材料、过期/不可用版本、错误类别/MIME、同一材料混合版本、上传后材料替换；直接 SQL 绕过 DTO 亦拒绝。结算更新后原结案版本、材料引用、付款和审计可查询。
- 金额 `PENDING/UNKNOWN`、明确 `KNOWN 0.00`、正金额零付款、分期不足/刚好/超额、撤销付款、跨案付款、并发重复付款；三项资金状态分别缺失/不涉及/未满足/已满足；被告转成本通过、法院转成本拒绝，`SETTLED` 不能冒充 `RECEIVED`，账单/上传凭证不能冒充回款或开票。
- 正式归档与结算更新、付款撤销、退费/回款/开票状态变化并发：只允许可串行化的合法结果；预检通过后状态变更，归档事务必须拒绝或重读。相同键同 payload 只回放，异 payload 拒绝；部门/负责人权限撤销后回放也须先重新授权；审计/引用/回执写入失败时整笔回滚。

## 验收口径

本草案为高风险状态机与迁移，实施时按三级规则进行独立 Review、迁移专项、真实 PostgreSQL 权限/事务/并发 E2E、最终稳定候选正式门禁。纯计算单测仅证明金额函数，不证明历史链、触发器和并发成立。最值得人工核查的是：任意在办阶段提交真实资料后待归档，随后追加分期付款，未结清不得正式归档；结清且三项真实状态满足后才能归档，同时旧历史事实和回执仍可读取。
